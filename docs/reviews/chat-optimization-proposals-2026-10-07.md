# Overlord chat speed and cost optimization proposals

Mission **coo:1127**, objective **coo:1127.6xq3**. Prepared 2026-10-07 against **CONTRACT.md v159**. This is a recommendation deliverable, not an implementation or contract revision. Baseline: [completed audit](chat-diagnostics-audit-2026-10-07.md) and its [aggregate metrics](chat-diagnostics-audit-2026-10-07.metrics.json).

Prioritize reducing serial provider decisions and repeated context. Next improve durable publication overhead, then evaluate explicit caching against the existing implicit-cache baseline. Preserve complete diagnostics and the checkpoint/receipt barriers throughout. Estimates below are engineering scenarios for experiments, not measured speedups; they overlap and must not be added together.

## Baseline and confidence

The audit covers 538 diagnostic rows, three owner threads and 36 exchanges; only two completed runs have usage/timing measurements. Research run A took **269.024 s**, used 27 tools over 28 provider exchanges, and consumed **978,429 prompt tokens**, including **699,210 cached tokens** (71.5%). Status run B took 74.686 s with seven tools over eight exchanges. All 34 tool turns contained one call despite existing four-way read concurrency.

A's requests grew from 28.7 KB to 217.2 KB. Its 24 tool declarations occupy 23,632 JSON bytes, versus 4,664 bytes of system prompt; sixteen declarations are Knowledgebase tools that neither run used. Initial input is approximately 7,925 tokens, but field-specific token counts were not measured. A's request snapshots comprise 80.4% of diagnostic payload bytes, versus 3.2% for raw chunks. Optimizing chunks alone cannot substantially reduce stored bytes in this sample.

Request-to-first-chunk median is 3.440 s in A. Provider observation intervals sum to 204.256 s, but include synchronous persistence. Tool execution totals 21.599 s; completion-to-next-request gaps total 24.019 s. Neither those intervals nor chunk-to-message gaps isolate database time or browser paint. There is no measured invoice, lock wait, query duration or production percentile baseline.

## 1. Reduce the number of provider turns first

Owner: `backend/chat/gemini-runtime.ts` (prompt, `resolvePending`, `request`, `streamTurn`), existing gateway and repository-read service. The current prompt already asks for parallel reads; repeating that sentence alone is unlikely to solve the observed one-call behavior. Evaluate examples that explicitly request several known, independent paths in one turn, use `search_text` before broad file reads, and stop after enough evidence satisfies the user's question. Keep model quality, correct citations and draft proposals in the evaluation.

After project/target discovery, independent reads of known files can share a turn. A read selecting the path for a subsequent read cannot. A shared-turn batch still records each original operation id and source independently. Use the existing pool capped at four; do not raise concurrency beyond the repository service limit or violate the upstream Knowledgebase limit of 120 calls/minute, including source checks. [Google documents parallel function calling](https://ai.google.dev/gemini-api/docs/function-calling/) for independent calls; the runtime must continue to retain signed parts and join responses in original order.

The estimate uses `(3.440 s median first-chunk interval + 0.874 s median join proxy) × eliminated rounds`, excluding possible read overlap. Four to eight rounds yield 17.3–34.5 s. Mean A prompt input is 34,944 tokens/exchange; eliminating four to eight average-sized exchanges yields 139,776–279,552 tokens. This is a sensitivity model, not a replay: batched responses can change later context, output, thinking and implicit-cache behavior. Outliers make a median-based latency scenario incomplete.

Do not dispatch a function from an unfinished streamed turn. Persist the entire tool request/checkpoint and requested receipts before execution; keep read completion, sequential writes, then the question; join every receipt before the next request. Proposal preparation is stateful even if treated in the existing read path: do not invent speculative proposal calls to fill a batch.

## 2. Make history budgets effective without damaging recovery

Owner: runtime `contents`, `maybeSummarize`; `packages/core/service/chat/runs.ts` summary/input projection. Today the summary and all fetched messages are sent together. Select only messages after `summaryCoversMessageId` when the coverage boundary is present and the summary remains usable. If the boundary is outside the 100-message page, resolve its ordering from storage; do not guess coverage from an absent index. If the summary is missing, invalidated or unusable, fall back to authorized message history.

Retain the current trigger message, unresolved question/answer context, current proposal cards, creation receipts, decisions and evidence needed for the current request. A summary's immutable conservative dependency union still applies even when covered messages are omitted. Revocation must withhold/fence summary-derived input; a short summary is not permission to discard its source dependencies. Keep all active-run provider turns verbatim, including empty parts, thought signatures and call ids. [Google's thought-signature guidance](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures) reinforces retaining signed function parts in their original sequence.

Use a compact summary-specific system instruction that treats the transcript as untrusted data, asks only for the existing summary fields, and forbids tools. Set a model-verified output bound (experiment with 1k–2k tokens), handle truncated/invalid JSON as a failed optional summary, and retain the last valid summary. Count authorized input tokens against model capacity with reserved tool/output/thinking headroom; character counts and 1 MiB gathered-result limits are not token budgets. Preserve the existing eight-message summary cadence initially. Do not add an undocumented token-limit failure code or silently remove context to force a request through.

New requests may select a smaller authorized conversation prefix. Compaction of an active run's signed function history is a separate design requiring checkpoint/schema/digest/recovery amendments; it is not part of this recommendation. Likewise, moving summary generation after completion would alter fencing, dependencies and crash recovery and needs a separate contract design.

## 3. Improve prompt structure and retrieved payloads

Keep safety/authorization, untrusted-data treatment, citation requirements, user-only Create, frozen assignments, Feature exact-reference lookup and write conflict/uncertain rules explicit. Correct the current request-only Knowledgebase write wording to cover both a per-message workspace grant and a live `all_workspaces` connection setting. Tool presence is not authorization; the gateway remains authoritative on every call. Bump `SYSTEM_PROMPT_VERSION` and recompute the digest so old checkpoints recover through the existing fresh-generation path when incompatible.

Count prompt and declaration tokens separately using the exact model and request representation before deleting prose. Shorten duplicate tool descriptions without changing validation, property names or required fields. Put stable instructions/schema representation before dynamic user content, with deterministic declaration ordering; this is a candidate to improve existing implicit-cache reuse, not a guaranteed cache hit.

For repository research, retrieve focused line ranges with enough surrounding context, search narrowly, and expand deliberately. For Knowledgebase queries select supported filters/limits upstream; large-query refusal must remain refusal where policy forbids truncation. Do not summarize raw diagnostics, omit fields from capture, or replace recorded function responses with compressed versions during continuation. Raw gateway output and the actual SDK request must remain visible in their diagnostic observations. The 30% scenario uses `0.30 × (978,429 − 28 × 7,925) = 226,959` tokens; 7,925 is only an approximate static baseline. Actual savings require tokenization and task-quality checks.

## 4. Filter tools carefully, then evaluate explicit caching

**Tool subsetting.** Owner: backend gateway declarations plus runtime request/recovery state. Start with stable task families: Overlord status, repository research, Knowledgebase research, and Feature handoff. Always retain the question path and discovery needed to correct routing. An explicit notes request includes the Knowledgebase discovery/read family; a write request includes only live authorized writes; Feature handoff includes exact-reference lookup and proposal preparation. Never decide whether a tool is authorized from model classification. Avoid an extra routing-model call initially.

The fixed tool-list language and “reviewed reads are always available” clause prevent silently shipping relevance filtering under v159. Proposed amendment: **the authorized reviewed catalog remains fixed; a provider request may expose a recoverably expandable relevance subset, while live gateway authorization and closed-schema validation remain unchanged**. Define how a hidden capability is discovered, how the selected manifest is reconstructed on recovery, and how historical calls remain valid when the current subset changes. Count the schema savings against any added expansion rounds. Fail open for relevance uncertainty by offering the full authorized catalog; fail closed for authorization.

**Explicit cache.** Owner: `gemini-client.ts` SDK seam, runtime request builder and cache manager. Use the existing Generate Content API rather than migrate API families. Google supports [cached system instructions/tools and immutable cache manifests](https://ai.google.dev/api/caching). The [Generate Content caching guide](https://ai.google.dev/gemini-api/docs/generate-content/caching) lists a 4,096-token minimum for Gemini 3.8 Flash, cached-input and storage charges, and usage metadata. Count the exact proposed manifest: a 4,664-byte prompt alone is not evidence that it reaches the minimum. Do not pad a small manifest with irrelevant content just to qualify.

Start with static instructions and the exact declarations, **no conversation, repository content, source results or credentials**. Connection-specific names/scopes make many manifests owner-specific; key entries by deployment/provider credential identity, model, prompt version/hash, canonical declaration hash and relevant policy/owner scope. Share only demonstrably identical nonprivate manifests. Bound cache count and TTL (trial 5–15 minutes), single-flight creation, delete retired entries, and avoid creating once per request. Prefer warm reuse for repetitive workloads; fall back to the ordinary full request on expiry/unsupported manifests before any turn arrives. Never replay a partially consumed stream or retry an uncertain write.

Cache references never authorize tool execution. All cached declarations still face the gateway's live membership/grant/connection checks. A changed prompt/manifest cannot reuse an incompatible cache. Account for the cache's immutable tool configuration: verify AUTO and the allowance-closing NONE request with the installed SDK; use a compatible separate manifest or uncached closing request if overrides are unsupported. A small relevance subset may fall below the minimum, making implicit caching preferable.

Capture cache-create request/response/error observations in the owner's private thread diagnostics, alongside each actual generation request and raw chunks. Keep the manifest available for owner inspection so a cached-content handle does not conceal effective provider input. Do not duplicate another owner's manifest into the requesting thread. Define digest coverage and cache reconstruction on restart; a transient handle should not by itself invalidate otherwise compatible local history. This lifecycle needs a contract clarification before implementation, even if DTOs remain unchanged.

Let `U` and `C` be uncached and cached input prices per million tokens, `S` storage price per million token-hours, `K` counted cache tokens, `h` TTL hours, `n` reuses, and `p` the counterfactual implicit-hit fraction on those same tokens. Net savings are approximately `nK(1−p)(U−C)/1e6 − KhS/1e6 − creation/management charges − savings lost elsewhere`. Evaluate actual billing treatment. A's entire remaining uncached bucket is only **279,219 tokens**; `0.279219(U−C)` is an optimistic whole-run upper bound before expenses, not a static-cache forecast. Existing 699,210 cached tokens cannot be counted as new savings. Total context tokens and context-window occupancy do not shrink when replaced by cache references. Compare marginal cost after prompt/subset changes, which may disrupt implicit prefix hits.

## 5. Improve durable publication without losing observations

Owner: runtime capture/`flushStreaming`, `packages/core/service/chat/{store,diagnostics,runs}.ts` and diagnostics routes. First time lock acquisition, serialization, SQL and commit separately. Inspect real query plans for `MAX(seq)+1`; its existing primary key does not prove a scan. Serialize a frozen payload once outside the lock where safe, reuse already-loaded immutable event state within the same transaction, and avoid redundant round trips while retaining owner/fence checks and raw state at the transition. Evaluate paging diagnostics in an authorized read transaction without the writer's no-op thread update; preserve live membership, deletion races, ordered 100-row pages and no-store responses.

For text publication, test 250/500/750 ms and 400/800/1,600-character thresholds. A genuine timer can bound sparse-stream delay, but requires one serialized flush queue, bounded buffering, cancellation handling and no overlapping text writes. Keep immediate first-text publication, durable event commit before SSE, final flush, monotonically ordered cursors and snapshot/replay recovery. Larger buffers may reduce event writes but worsen perceived responsiveness. Saving 17 of A's 35 text deltas at an isolated 50 ms/write would save only 0.85 s; prefer an evidence-based threshold to simply increasing delays.

Raw chunk persistence remains independent of text coalescing. Do not sample chunks, suppress diagnostics when the UI is off, truncate payloads, apply normal chat-event retention to diagnostics, or release tool execution before its checkpoint/receipt transaction commits. An in-memory asynchronous queue plus a shutdown flush loses data on crashes and cannot satisfy complete v159 capture.

Lossless batching is a later conditional proposal: durably admit **every** observation before releasing dependent runtime work, order chunk observations and intervening domain events on one thread sequence, bulk-materialize individual rows, and recover/idempotently drain after crashes. A durable admission journal may cost as much as the current insert; only measured round-trip reductions justify it. It requires a schema/contract amendment describing durability, sequencing, deduplication, deletion cascades, cross-worker ordering and page visibility. Do not claim the 91 chunk transactions can become a handful for free. Repeated large request capture can benefit from transparent database compression, but replacing raw payloads with client-visible references is a different diagnostics contract and is not recommended here.

## Contract impact ledger

All options retain owner/organization scope, fail-closed provider input and source projection, private checkpoints, complete raw observations, thread-lifetime diagnostics, persisted-before-send events, fenced domain writes and ordered idempotent receipts. Knowledgebase writes remain sequential with revision/conflict/uncertain guards. Create alone produces drafts with normal mission transaction/audit/change/webhook invariants; chat and diagnostics never gain global search, webhook, change-feed or provider-history publication.

This objective changes only this proposal document.

## Implementation order and release gates

1. Instrument and establish a replay/evaluation corpus: status queries, repository research, Knowledgebase reads/writes under both grant modes, Feature handoff, long conversations, cancellation and restart. Use several repetitions and owner-private raw diagnostics; publish only aggregates. Track SDK first-chunk arrival, first non-thought text, first committed text, browser paint, complete-run time, provider rounds, prompt/cached/candidate/thought tokens, schema bytes and capture/lock/authorization times.
2. Evaluate parallel-read examples, prompt corrections and focused retrieval with the current catalog. Proceed only with equal task correctness/citation/creation behavior, no increase in unnecessary calls, and a measured latency or input-cost improvement. Then implement usable-summary coverage after its contract clarification. Keep each experiment separate before evaluating combinations.
3. Amend/evaluate tool subsets with capability-discovery and checkpoint-recovery tests; compare with the full-catalog fallback. Evaluate explicit static caching only on the resulting stable manifests and sufficient reuse, including cold creation, expiry, changed grants and NONE closing mode. Require positive net cost after storage/creation and no material latency regression.
4. Measure/tune transaction and coalescing paths. Consider durable admission batching only if capture remains a material bottleneck. Virtualize the viewer separately; retain the full owner-accessible history.

Runtime verification must cover out-of-order concurrent read completion with ordered joins; crash before/after request checkpoint and receipt commit; stale fences; cancellation during flush; source revocation during generation/summary/cache reuse; v158 grant removal; uncertain writes with no blind retry; cache miss/expiry without duplicated calls; diagnostics completeness/order/cascade with the display off; and unchanged Create/idempotency behavior. Exercise both database adapters where persistence changes. No runtime test is claimed by this documentation-only delivery.
