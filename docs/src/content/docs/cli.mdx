description: Reference for the ovld command-line interface.
---

Install the CLI with `npm install -g --no-fund overlord-cli`. Run `ovld help`
for the short command summary and `ovld protocol help` for the agent lifecycle
reference. Management commands support `--json` where noted; protocol commands
return JSON by default.

## Setup, configuration, and diagnostics

| Command                                                       | What it does                                                                  |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `ovld help`                                                   | Show the top-level help.                                                      |
| `ovld version [--json]`                                       | Show the installed version.                                                   |
| `ovld update [--check] [--force] [--json]`                    | Check for or install the latest published CLI.                                |
| `ovld init [--json]`                                          | Create `overlord.toml` for a local backend.                                   |
| `ovld serve [--host <h>] [--port <p>] [--db <path>] [--json]` | Start the local web and REST server.                                          |
| `ovld doctor [--json]`                                        | Check the backend, connectors, agent binaries, and credentials.               |
| `ovld prune [--force] [--json]`                               | Delete temporary contents under `.overlord/tmp` (keeps live session scratch unless `--force`). |
| `ovld setup [--json]`                                         | Interactive first-run setup for backend, agents, and terminal.                |
| `ovld contract check <manifest-path> [--json]`                | Validate a component conformance manifest. This is for component maintainers. |

### Backend configuration

| Command                                | What it does                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------ |
| `ovld config list [--json]`            | Show resolved local configuration.                                                         |

`--no-terminal` to run the agent inline instead of spawning a terminal window.

`--pre-command <cmd>` to run a shell command before the agent launches.

## Live sessions and decisions

These commands cover the [agent-session](/agent-sessions/) surface — the live observe/decide/inject
channel between a running agent harness and Overlord, separate from the durable mission protocol.
As of the Latch v2 cutover, no launch path creates the credentialed session channel the hook
commands below need, and `inputs send` always fails. Blocking questions still work: an attached
agent's `ovld protocol ask` opens the request, and `requests resolve` answers a **question** or
**choice** while the mission's attached objective has a live Latch terminal session. A resolved
request reports delivery separately (`delivery.stage`: `queued`, `dispatched`, `confirmed`,
`unconfirmed`, or `failed`); recorded is not the same as delivered. See
[Live agent sessions](/agent-sessions/#answering-a-held-question) for the current state.

| Command                                                                                                    | What it does                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `ovld requests [--mission-id <id>] [--objective-id <id>] [--json]`                                         | List open and recent agent decisions, optionally restricted to one mission or objective.                                        |
| `ovld requests resolve <id> --revision <n> --decision allow\|deny\|ask [--text <text>]`                    | Answer a held decision; `--text` carries a question's answer. `--decision allow\|deny` answers a Codex app-server approval (launching member only). Redelivery after a failed delivery is in the web app only. |
| `ovld inputs list --mission-id <id> [--objective-id <id>] [--json]`                                        | List session instructions and the effective channel for one mission or objective; an objective display id supplies the mission. |
| `ovld inputs send --channel-id <id> --body <text> [--kind <kind>] [--json]`                                | Retired: the backend rejects every call with `session_controls_gone` (410 error). No launch path currently creates a live session channel to address. |
| `ovld agent-session capabilities [<agent>] [--json]`                                                       | Print the fixture-backed capability descriptor for a harness — offline, authoritative.                                          |
| `ovld agent-session bind --agent <key> --native-session-id <id> [--mission-id <id>] [--objective-id <id>]` | Correlate a harness-native session id with this process's channel.                                                              |
| `ovld agent-session event --agent <key> --payload-file -`                                                  | Push one native harness event (connector-internal; silent, never blocks).                                                       |
| `ovld agent-session request --agent <key> --payload-file -`                                                | Wait for a remote decision or defer to the harness (connector-internal).                                                        |
| `ovld agent-session inbox --agent <key> --payload-file - [--wait-ms <ms>]`                                 | Claim one pending instruction and emit it natively (connector-internal). A final Claude Stop in a headless session polls up to 60 s. |
| `ovld agent-session sidecar --agent <key> --port <port>`                                                   | Drive a control-plane harness event stream, such as OpenCode (connector-internal).                                              |
| `ovld agent-session sidecar --agent codex-app-server [--socket <path>] [--thread-id <id>] [--prompt-file <path>] [--working-directory <dir>]` | Drive a private Codex app server (connector-internal, experimental: requires `OVERLORD_CODEX_APP_SERVER=1` and a session channel; `ovld launch` and runners start it in Codex app-server mode). |
| `ovld agent-session attach [--objective-id <ref>] [--channel-id <id>]` | Open the Codex TUI on a running Codex app-server session on this machine (`codex --remote … resume <thread>`); approvals can be answered there or in the web app. |

`agent-session event`, `request`, `inbox`, and `sidecar` are the adapter runtime commands
connectors invoke from hooks and extensions; `capabilities` and `bind` are the ones you would
run directly while diagnosing a connector. See
[Agent-session adapters](/docs-for-agents/agent-sessions/) for per-harness behavior.

## Agent protocol

The `ovld protocol` commands are primarily used by connectors and agent
runtimes. They create the durable mission lifecycle that you see in Overlord.
Every command below is available from `ovld protocol help`.

| Command                            | Purpose                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `auth-status`                      | Check backend and authentication readiness.                                                               |
| `discover-project`                 | Resolve a project from the working directory, project ID, or directory.                                   |
| `create-project`                   | Create a project in one authorized workspace.                                                              |
| `register-target`                  | Register this machine as an execution target.                                                              |
| `attach`                           | Start a full mission session and return its working context.                                              |
| `connect`                          | Start a lightweight session without full context assembly.                                                |
| `load-context`                     | Read mission context without starting a session.                                                          |
| `list-deliveries`                  | Read one mission's normalized deliveries as `{ items, total, limit }` (items capped at 200). An objective display id supplies the mission. |
| `launch-objective`                 | Queue a runner execution for one objective. Requires `--objective-id` (UUID or display id) and `--agent`. |
| `reorder-objectives`               | Replace one mission's complete draft/submitted order.                                                     |
| `run-queue`                        | Read live Run Queues; project scope can come from project, objective, or mission.                         |
| `reorder-run-queue`                | Atomically replace every entry in one Run Queue.                                                          |
| `queue-objective`                  | Add or move one objective in the Run Queue. Requires `--objective-id` (UUID or display id).               |
| `dequeue-objective`                | Remove one objective from the Run Queue. Requires `--objective-id`.                                       |
| `retry-queue-entry`                | Retry one held Run Queue entry. Requires `--objective-id` or `--entry`.                                   |
| `create-run-queue`                 | Create a paused queue definition. Requires `project:update`.                                              |
| `update-run-queue`                 | Rename, pause, or resume a queue definition. Requires `project:update`.                                   |
| `delete-run-queue`                 | Delete a queue, optionally moving its entries. Requires `project:update`.                                 |
| `reorder-project-run-queues`       | Replace the project's complete queue-definition order. Requires `project:update`.                         |
| `search`                           | Find grouped mission, objective, and delivery matches by text, state, or project. `--reference <token>` with `--project-id` runs an exhaustive exact-token lookup (`--limit`, `--cursor`; follow `nextCursor` until `complete` is true).                          |
| `statuses`                         | List one project's board columns.                                                                         |
| `discuss-objective`                | Submit the latest draft objective for discussion without execution.                                       |
| `add-objectives`                   | Append ordered objectives to a mission; each item has `instructions` and may carry a `summary`.                              |
| `update-objective`                 | Turn auto-advance on or off, edit instruction text or the summary (`--summary`, `--summary-request`), or reassign with `--objective-agent` (`manual`/`human` for a person). Requires `--objective-id`.|
| `delete-missions`                  | Confirmed bulk soft-delete of one to 100 missions (requires `--confirm`).                                  |
| `delete-objectives`                | Confirmed bulk soft-delete of one to 100 objectives (requires `--confirm`).                                |
| `create`                           | Create a draft mission without attaching.                                                                 |
| `prompt`                           | Create a mission and attach immediately.                                                                  |
| `record-work`                      | Record completed chat work as a review mission.                                                           |
| `update`                           | Post progress and activity; `--paths`/`--paths-file` declare uncaptured paths.                            |
| `heartbeat`                        | Send liveness information without creating a feed event.                                                  |
| `ask`                              | Raise a blocking question for a human reviewer and open an answerable request (`--options-json` + `--no-free-text` for a fixed choice). |
| `deliver`                          | Finish the session with summary, artifacts, optional declared paths, and an optional mission summary write (`--mission-summary-file`; see [Agent protocol](/docs-for-agents/agent-protocol/#mission-summary)). |
| `resume-follow-up`                 | Reopen completed work for a follow-up.                                                                    |
| `hook-event`                       | Record a connector lifecycle event (`UserPromptSubmit`, or read-only `Stop` delivery status). `--agent <key> --payload-file -` reads a native hook payload and prints `hookOutput`. |
| `capture-change`                   | Locally capture direct, objective-bound native edit paths (connector use).                                |
| `sync-changes`                     | Synchronize one bounded objective-ledger batch.                                                            |
| `changes`                          | Local-only read of this checkout's recorded paths and hook health for an objective.                       |
| `objective-changes`                | Server read of an objective's changed files across sessions, resources, and devices.                      |
| `read-context` / `write-context`   | Read or store persistent mission context.                                                                 |
| `add-artifact`                     | Create a mission artifact mid-turn without delivering.                                                    |
| `update-artifact`                  | Revise an existing mission artifact in place (label / content / URL).                                     |
| `attachment-list`                  | List mission attachments.                                                                                 |
| `attachment-download-url`          | Retrieve one attachment's download URL.                                                                   |

Common protocol flags are `--mission-id <id>`, `--objective-id <id>`,
`--session-key <key>`, `--agent <identifier>`, and `--model <identifier>`. Most
payload fields accept either inline JSON or a matching `--*-file`; inline
`--*-json` values are limited to about 8 KB, and at most one file input per call
may read standard input (`-`). Run `ovld protocol help <subcommand>` (or
`ovld protocol <subcommand> --help`) for one command's flags.

`load-context`, `read-context`, `attachment-list`, and `attachment-download-url`
treat an explicit mission as authoritative: an inherited `OVERLORD_OBJECTIVE_ID`
applies only when no mission is named or its parent mission display id matches.
For a mission UUID, pass `--objective-id` to pin the read. These reads never
change your active execution binding:

```bash
ovld protocol load-context --mission-id coo:700
```

`ovld create`, `ovld prompt`, and `protocol add-objectives` return the persisted
mission and objectives, and human-readable output echoes each objective's agent,
model, resource, and queue/auto-advance settings.

`--objective-id` is accepted anywhere `--mission-id` is, and takes an objective
UUID or a display id such as `coo:8.k7xm`. A display id already names its
mission, so `--mission-id` is optional whenever you pass one:

```bash
ovld protocol update --objective-id coo:8.k7xm --summary "Refactored the parser."
ovld protocol launch-objective --objective-id coo:8.k7xm --agent claude
ovld protocol queue-objective --objective-id coo:8.k7xm
ovld protocol list-deliveries --objective-id coo:8.k7xm
```

`launch-objective`, `queue-objective`, `dequeue-objective`, and
`update-objective` **require** `--objective-id` as the primary argument — a
display id is enough on its own. Use it when reconnecting to a mission that is
running more than one objective — there, the mission id alone no longer
identifies a unit of work. An objective UUID names no mission, so it still needs
`--mission-id` beside it.

Run Queue entry operations (`queue-objective`, `dequeue-objective`,
`retry-queue-entry`, and `reorder-run-queue`) require
`execution_request:create`. Queue-definition
operations (`create-run-queue`, `update-run-queue`, `delete-run-queue`, and
`reorder-project-run-queues`) require `project:update`, so a
mission-lifecycle-scoped token cannot perform them. `run-queue` accepts
`--project-id`, `--objective-id`, or `--mission-id`, plus optional `--queue`.
New queues start paused; resume one explicitly or directly launch a queued
objective to start it. The exception is queueing an objective behind a sibling
that is already running: its new mission queue shows that sibling in flight
ahead of it and starts running, so the queued objective launches as soon as
the sibling delivers.

### Objective instructions and summary

An objective has two texts. Do not swap them.

- **Instructions** (`--objective-instructions`, item `"instructions"`): the
  complete brief the executing agent receives, usually the long text.
- **Summary** (`--objective-summary`, item `"summary"`): a short overview for
  people, never sent to the executing agent, usually the short text: one to
  three prose paragraphs in Simplified Technical English style that open with
  the goal and close with the done-when sentence, about 120 words. Omit it and
  Overlord writes one for long (280+ characters) agent-written objectives.

Overlord never refuses a create over this, but it warns when the texts look
swapped: the response carries an `objective_fields_swapped` warning that names
both fields when the summary is at least 3 times as long as its instructions
(and 400+ characters), or more weakly when it is 1.5 times longer or has
headings, numbered steps or a `Done when:` label over short instructions. Both
texts are stored as written; fix a swap with `update-objective`. The old names `--objective`, `--objective-description` and item keys
`objective` / `description` are refused with their replacement.

- `create` / `prompt`: `--objective-instructions <text>` (or
  `--objective-instructions-file <path|->`) and `--objective-summary <text>`
  (or `--objective-summary-file <path|->`); with `--objectives-json`, set
  `"instructions"` and `"summary"` on each item instead.
- `add-objectives`: per-item `"summary"`.
- `update-objective`: `--summary <text>` or `--summary-file <path|->`
  (empty removes the summary), or `--summary-request summarize|regenerate|retry`
  (not combined with `--summary`).

Agents may change summaries or request them only on `draft` objectives
(400 `summary_not_editable`); people edit them in any state in the app.
`retry` re-requests only a failed generation (409 `summary_not_failed`), and
instructions under 280 characters are not summarized (409
`summary_not_eligible`). When a person removed the summary, agent text is
not stored and summary requests are refused (`summary_suppressed`) until
that person selects Summarize. Responses carry advisory `warnings` (code
`summary_style` or `summary_suppressed`): on the matching created
objective for `create`/`add-objectives`, top-level for `update-objective`. The
text is stored as written.

## Environment variables

| Variable                                                         | Use                                                                                                                                                                                                      |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OVERLORD_USER_TOKEN`, `OVLD_USER_TOKEN`, `USER_TOKEN`           | Authentication token, checked in that order.                                                                                                                                                             |
| `OVERLORD_BACKEND_URL`, `OVERLORD_BACKEND_URL_DEV`               | Backend URL fallback.                                                                                                                                                                                    |
| `OVERLORD_EXECUTION_REQUEST_ID`                                  | Link an agent protocol attach to a runner request.                                                                                                                                                       |
| `OVERLORD_OBJECTIVE_ID`                                          | Pin protocol attach to this objective display id (for example `coo:8.k7xm`).                                                                                                                             |
| `OVERLORD_DEVICE_FINGERPRINT`                                    | Pin this process to a stable execution-target identity. Use when disposable containers (e.g. AgentPod) share one host environment and must not each register a new target from their ephemeral hostname. |
| `OVERLORD_DEVICE_LABEL`                                          | Override the human-facing device name for this machine's execution target. Optional; falls back to the hostname. Does not affect the fingerprint unless `OVERLORD_DEVICE_FINGERPRINT` is also set.       |
| `SESSION_KEY`                                                    | Session-key fallback for protocol commands.                                                                                                                                                              |
| `OVLD_HOME`                                                      | Relocate the CLI's credentials and configuration.                                                                                                                                                        |
| `OVERLORD_WEB_HOST`, `OVERLORD_WEB_PORT`, `OVERLORD_SQLITE_PATH` | Defaults for `ovld serve`.                                                                                                                                                                               |
