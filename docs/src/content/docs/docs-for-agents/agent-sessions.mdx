title: Agent-session adapters
description: Diagnose Overlord observe, decide, and inject behavior across each supported harness.
---

This page is for an AI agent or maintainer diagnosing live session behavior. Do not infer a
capability from an adapter name or from a hook that happens to exist. Start with the compiled,
fixture-backed truth:

```bash
ovld agent-session capabilities <agent> --json
ovld doctor
```

The four capability states are operational instructions: `supported` is fixture-proven,
`unsupported` means do not attempt it, `not-implemented` is buildable work, and `unverified`
means establish evidence before changing behavior. Source descriptors live at
`connectors/adapters/<agent>/harness-capabilities.yaml`; generated `CAPABILITIES.md` files must
not be edited.

## Shared diagnostic order

1. Confirm `OVERLORD_SESSION_CHANNEL_ID` exists in the launched process. Without it, the hook
   must exit before spawning `ovld`; silence is correct. As of the Latch v2 cutover, the only
   launch that mints a channel is a Codex objective in app-server mode (ADR 0092: `POST
   /api/objectives/{id}/session-channels`, `launch_kind = 'control_plane'`, adapter
   `codex-app-server` only; any other key answers 400 `adapter_not_control_plane`). Expect the
   variable to be absent for every other session — that is the current state of launch wiring,
   not evidence of a broken adapter. Do not spend time debugging a specific
   connector on this signal alone. A channel with `launch_kind = 'protocol'` is not a launch
   channel: `ovld protocol ask` creates it, without a credential or lease, so a blocking
   question has a request to hang off (ADR 0065). Its existence does not mean hooks can
   authenticate.
2. Run `ovld doctor` and repair stale managed files with `ovld agent-setup <agent>`.
3. Read the adapter's static capability maximum, then verify the installed descriptor and live
   binding separately. The catalog alone does not prove that the installed harness invoked a
   hook or that project policy enabled an optional path.
4. Identify the path: callback script, in-process extension, or control-plane sidecar.
5. Keep mission lifecycle hooks (`ovld protocol`) separate from live session hooks
   (`ovld agent-session`). The former can work while the latter is intentionally unbound.
6. For a decision failure, verify exact native stdout and timeout before investigating REST. A
   malformed or timed-out callback must emit nothing.

## Blocking questions and answer delivery

The blocking-question path does not depend on any connector hook. It works the same for every
harness and is the only Decide path live today:

1. The attached agent runs `ovld protocol ask` (`--options-json` plus `--no-free-text` makes it a
   **choice**). The ask opens an answerable request, creating a correlation-only channel when the
   session has none.
2. A person answers in the mission panel or with `ovld requests resolve`. Answerability is decided
   per read from the mission's Latch terminal session: `AgentRequestDto.delivery.mode` is `latch`
   or `read_only`. A request on a live `control_plane` channel instead reads `control_plane` and
   bypasses steps 3 and the Latch diagnostics below (see the Codex app server section).
3. The backend queues a `sendLatchMessage` job for the execution target's runner, which posts the
   answer into the agent's Latch conversation. Latch must have a conversation connector for the
   harness that accepts `send_message`: Claude Code, Codex and Cursor do; other harnesses are
   refused and the delivery reports `failed`.

Diagnose a missing answer from `delivery`, not from `resolved`:

- `stage` is `recorded`, `queued`, `dispatched`, `confirmed`, `unconfirmed` or `failed`;
  `failureCode`, `failureMessage`, `attempt`, `canRedeliver`, `confirmationRequired` and
  `sessionState` explain it. Resolve waits about 25 seconds; a job no runner claimed by then is
  withdrawn as `failed` / `not_dispatched`.
- `failed` with an unreachable gateway: the runner tries the standalone `latch serve` gateway and
  the Remote Link supervisor's gateway
  (`$LATCH_HOME/remote-access/runtime/remote-link-gateway-ready.json`), loopback only. An explicit
  environment override is then the only candidate.
- `sessionState: exited` returns 409 `request_not_deliverable`; `lost` is still attempted. An
  offline target refuses before anything is recorded.
- Recovery is `POST /api/agent-requests/:id/redeliver` with `expectedAttempt`; an `unconfirmed`
  attempt also needs `confirmUnconfirmed: true` and is resent only if Latch kept no delivered
  receipt for the earlier attempt. Overlord never resends on its own.
- A dismissed card (`dismissed: true`) is a per-member view preference. It does not close,
  answer, or hide the request from `status=open` reads.

## Claude Code

**Shape:** callback plugin. **Observe (supported):** `UserPromptSubmit` and `PostToolUse` file edits;
`PreToolUse`, tool results, and `SessionStart` lifecycle are `not-implemented`.
**Terminal status surface (supported):** the opt-in status line (`ovld agent-setup claude
--status-line`, `ovld status-line --agent claude`).
**Decide (not-implemented — target shape):** `PermissionRequest`. **Inject
(not-implemented — target shape):** `asyncRewake` during a turn plus a Stop boundary.

All `decide.*` and `inject.*` capabilities are `not-implemented` for Claude today
per `connectors/adapters/claude/CAPABILITIES.md`; the wire shapes below describe
the design to build against, not live behavior. Run
`ovld agent-session capabilities claude --json` to confirm current status before
relying on either path.

Claude Code **2.1.328 or later** is required. Every Overlord Claude hook is an `mcp_tool` hook:
Claude Code calls a tool on the plugin's bundled local MCP server
(`plugin:overlord:overlord-hooks`), and the tool runs the same `ovld` command as the CLI
fallback. The server lists no tools, so the model never sees them. No shell or Python hook script
ships.

| Hook | Runs | On failure |
| --- | --- | --- |
| `UserPromptSubmit` | `ovld protocol hook-event --hook-type UserPromptSubmit`: records follow-up activity | continues |
| `PostToolUse` | `ovld protocol capture-change`: only an objective-bound event that the Claude codec normalizes as `file.edited` records `declared_edit` / `direct` path evidence | continues |
| `Stop` | `ovld agent-session inbox`, then `ovld protocol hook-event --hook-type Stop`: a delivery reminder, at most once per session and objective | continues |
| `PermissionRequest` | `ovld agent-session request`: the remote decision | **denies** |

- The first three hooks are in the plugin and do nothing until the session is bound to a
  mission. The `PermissionRequest` hook is never in the plugin: `ovld launch` registers it through
  `claude --settings` only for sessions it launched with a session channel, with
  `onFailure: "block"`. If Claude Code cannot reach the hooks server, it denies the request. If
  the CLI or backend fails, the tool returns no decision, so Claude shows its normal prompt. No
  failure manufactures an approval.
- Subagent and fork hooks carry the parent's session id and bind to the parent's mission.
  `SubagentStop` is not registered. While background subagents run, the Stop reminder waits for
  the later Stop, and the harness's `<task-notification>` prompt is not recorded as a follow-up.
  A nested `claude -p` does not inherit the launch binding (file capture excepted).
- In a headless session (`claude -p`, Agent SDK) the final Stop polls the inbox for up to 60 s
  (`ovld agent-session inbox --wait-ms` overrides, up to 120 s). Interactive sessions never wait.
- The decision response is Claude's `hookSpecificOutput.decision: { behavior }` shape. Cursor's
  flat `permission` response is never valid here.
- **CLI fallback.** Claude Code has no automatic fallback from a failed `mcp_tool` hook. If the
  hooks server is not connected, follow-up capture, file capture and the Stop reminder are off
  but the session keeps working. Use `ovld protocol attach`, `update`, `ask`, `deliver` and
  `changes` directly, and declare changed files with `--paths`. `ovld doctor` reports a Claude
  Code version below 2.1.328, a disabled plugin, or a disconnected hooks server, and names the
  fix (`ovld agent-setup claude`).
- Cursor imports Claude plugin hooks but copies only `command` hooks, so it runs none of these.
- Fork/subagent native identity remains a declared hazard. Do not bind a child session by cwd or
  assume it shares the parent's native id.

## Codex

**Shape:** callback plugin using documented hooks. **Observe (supported):** `UserPromptSubmit`
and `PostToolUse` file edits; pre-tool, tool-result, and `SessionStart` lifecycle are `not-implemented`.
**Terminal status surface (supported):** the status line provider in Codex 0.171+ (feature
`tui_extensions_statusline`, selected by `ovld agent-setup codex --status-line`).
**Decide (not-implemented — target shape):** `PermissionRequest`. **Inject
(not-implemented — target shape):** Stop-boundary delivery.

All `decide.*` and `inject.turnBoundary` are `not-implemented` for Codex today
per `connectors/adapters/codex/CAPABILITIES.md`; treat the details below as the
design to build against, not live behavior.

- Codex hooks require a supported hook-era version. An installed plugin on an older binary can
  look healthy while never invoking hooks.
- `PostToolUse` sends its native payload to local `capture-change`; only an objective-bound
  event that the Codex codec normalizes as `file.edited` records path evidence. Shell and
  no-path callbacks record unavailable health without scanning the worktree.
- The response is nested `hookSpecificOutput.decision.behavior`; `ask` deliberately emits no
  bytes so Codex owns the native prompt.
- Do not start an app-server decision subscriber beside the hook adapter. That creates two
  authorities capable of resolving one permission. The private app server Overlord launches sets
  `OVERLORD_CONTROL_PLANE_SURFACE`, which keeps this plugin's own hooks silent inside its threads
  (hazard `plugin-hooks-fire-inside-app-server-threads`).
- The plugin root fallback is `~/.codex/plugins/overlord`. If managed scripts exist elsewhere,
  refresh with `ovld agent-setup codex` rather than editing generated paths.
- Stop injection is turn-boundary behavior, not mid-turn steering.

## Cursor

**Shape:** callback scripts. **Observe (supported):** `beforeSubmitPrompt`, `postToolUse` tool results
and file edits; pre-tool and `sessionStart` are `not-implemented`. **Decide
(not-implemented — target shape):** per-tool shell, MCP, and generic pre-tool events.
**Inject (supported):** `stop` returning `followup_message`.

Per `connectors/adapters/cursor/CAPABILITIES.md`, `decide.shell`/`decide.mcp`/
`decide.anyTool` are `not-implemented` and `decide.universal` is `unsupported` —
none of the Decide paths below are live yet. `inject.turnBoundary` and
`inject.nextTurn` are fixture-proven and accurate as described.

- `postToolUse` is the file-evidence path. The Cursor codec admits exact Write/Edit paths,
  leaves known read/search/fetch callbacks silent, and records unavailable health without a path
  for shell, generic, unmapped, or mutation-capable no-path callbacks.
- Cursor has no universal `PermissionRequest` event. Never restore the old manifest claim; use
  `beforeShellExecution`, `beforeMCPExecution`, or `preToolUse` according to the descriptor.
- Native output is flat: `{ "permission": "allow|deny|ask" }`. Claude's nested response may be
  accepted only by an optional compatibility shim and is not Overlord's contract.
- Keep `failClosed` unset. Otherwise a missing CLI, timeout, or backend loss becomes a denial
  instead of Cursor's native fallback.
- Cursor can read Claude hook configuration. Inspect both namespaces when commands duplicate or
  a Claude-shaped response appears.
- `followup_message` is recorded as **Queued (turn boundary)**, never Delivered. Cursor's command
  allowlist may also take precedence over a hook response; an emitted allow is not proof it was
  decisive.

## Pi

**Shape:** in-process TypeScript extension. **Observe:** only `input` (prompt) is supported; tool call,
tool result, file edit, and agent start are `not-implemented`.
**Decide (not-implemented — target shape):** optional async `tool_call` interceptor.
**Inject (not-implemented — target shape):** `sendUserMessage` with confirmation.

`decide.shell` and every `inject.*` capability are `not-implemented` for Pi today
per `connectors/adapters/pi/CAPABILITIES.md`; the details below describe the
design to build against, not live behavior.

- Pi has no native permission dialog. A timeout, CLI failure, or transport failure lets the tool
  run. Remote decisions require both `OVERLORD_PI_REMOTE_DECISIONS=enabled` and
  `OVERLORD_PI_PROJECT_REMOTE_DECISIONS=enabled`.
- Current builds do not expose those two gates as workspace/project settings. Treat the
  decision interceptor as a development path unless the launcher deliberately supplies both;
  observation and injection do not require them.
- The extension uses an owner-only temporary payload file because `pi.exec` has no stdin API. It
  must remove the file in `finally`; payload values must never move into argv.
- Delivered is confirmed only after `sendUserMessage` succeeds and the input lease is confirmed.
- The extension API is version-coupled. Treat an unsupported Pi version as a disabled extension,
  not permission to guess at event shapes.

## OpenCode

**Shape:** supervised control-plane sidecar. There are no callback scripts. Per
`connectors/adapters/opencode/CAPABILITIES.md` (capability tier 3), tool results, session idle
lifecycle, `decide.shell`/`decide.mcp`/`decide.anyTool` via `/permission`, all three `inject.*`
paths via `prompt_async`, and concurrent terminal answers are `supported`; prompt, tool-call,
file-edit, structured-question, and persistent-allow are `not-implemented`.

- A supervised launch must start `ovld agent-session sidecar --agent opencode --port <port>`,
  bind OpenCode to loopback, and protect the control port with a per-launch password. The bundled
  agent catalog does not yet start this sidecar automatically. Never expose the port to the LAN
  or browser.
- On reconnect, the sidecar re-reads `/permission` and `/question` before resubscribing to
  `/event`. Replays are expected and deduplicate by producer event id.
- The TUI and Overlord can truly answer concurrently on the event bus. A TUI win must mark the
  request resolved elsewhere; do not apply callback-only waiter assumptions.
- Injection uses `POST /session/{id}/prompt_async`. OpenCode's standing `always` permission is
  intentionally hidden from remote controls.

## Codex app server (experimental)

**Shape:** supervised control-plane sidecar, a JSON-RPC client of a private `codex app-server`.
Per `connectors/adapters/codex-app-server/CAPABILITIES.md` (capability tier 3): prompt, tool call
and result, file edit (paired pre/post), lifecycle, `decide.shell`, `decide.fileWrite`, all three
`inject.*` paths and concurrent terminal answers are `supported`; `decide.mcp` and
`answer.structuredQuestion` are `unverified`; `decide.anyTool` and `decide.universal` are
`unsupported`. User-started Codex sessions keep the hooks adapter in the Codex section above.

- **Launch (ADR 0092).** A Codex launch uses app-server mode when the per-machine harness mode
  (Settings → Terminal & IDE, `harnessMode: appServer`), the launching process's
  `OVERLORD_CODEX_APP_SERVER=1`, or the project's launch env var of that name selects it. It falls
  back to the hooks terminal launch, with a warning, when Codex is missing or older than 0.170.0,
  the launch has no objective, or minting the channel fails. User-started Codex sessions always
  use hooks.
- Launch mints a `control_plane` channel, stages its credential in the owner-only cache (never
  argv), and starts `ovld agent-session sidecar --agent codex-app-server` detached with
  `OVERLORD_CODEX_APP_SERVER=1`, after the project's pre-launch commands. The supervisor starts one
  private server and a persistent thread with the launch's model, effort, approval policy and
  sandbox, and sends the objective prompt as the first turn. Other Codex flags and the
  pre-command are reported as ignored. Protocol attach inside the thread binds this channel by
  objective.
- The visible terminal runs `ovld agent-session attach [--objective-id <ref>] [--channel-id <id>]`,
  which waits for the thread's rollout and runs `codex --remote unix://<socket> resume <thread>`.
  A runner with no terminal needs none; a person can attach later.
- **Lifecycle.** A crashed server is respawned up to three times and the thread resumed, with one
  continuation turn when none is running. The supervisor stops when the objective is `complete` or
  `deleted`, or when the session delivered and the thread has been idle for 15 minutes. On every
  exit it interrupts a running turn, ends the channel, stops the server, and removes its state,
  credential cache, and any implicit `trust_level = "trusted"` entry the thread start added.
  `ovld doctor` reaps orphaned servers and reports which Codex sessions run in app-server mode.
- **Answers (ADR 0094).** Its requests read `delivery.mode = 'control_plane'` while open and the
  channel is `preparing`, `online` or `degraded`; otherwise `read_only` with `request_closed` or
  `channel_ended`. Resolve records the answer with no Latch delivery; the supervisor applies it and
  `delivery.stage` moves from `recorded` to `confirmed` (`emitted`/`applied`), `failed`
  (`not_applied`) or `unconfirmed` (`unknown`). `/redeliver` refuses every control-plane request.
  A `permission` answer is only the card's own `allow` or `deny` (`{ optionId }`, or `--decision
  allow|deny`; anything else is 400 `invalid_resolution`) and only from the launching member
  (403 `not_session_owner`). Session inputs still answer 410 for every channel; type follow-ups
  in the attached TUI.
- The private server listens only on `unix://` in `~/.ovld/cx/`; its environment carries no
  Overlord token or objective scope, plus `OVERLORD_CONTROL_PLANE_SURFACE`, which silences
  Overlord's own Codex plugin hooks inside it. Never point it at the user's shared daemon.
- Every thread uses `approvalsReviewer: "user"`. A deny is `decline`, or `cancel` when Codex did
  not offer decline; standing grants are never sent.
- A TUI attached with `codex --remote unix://<socket> resume <thread>` can answer first; the card
  then closes as resolved elsewhere.
- Instructions go in with `turn/steer` while a turn runs and `turn/start` otherwise. Ending the
  channel or signalling the sidecar interrupts the running turn.

## Antigravity

**Shape:** callback plugin (agy 1.5.4+), capability tier 1 (Observational) per
`connectors/adapters/antigravity/CAPABILITIES.md` and ADR 0090. **Observe (supported):**
`PreInvocation` prompt (`lastUserInput`), and `PostToolUse` tool results and file edits; tool
call and session lifecycle are `not-implemented`. **Inject (supported):** `Stop` turn boundary,
`decision: "continue"` with `reason`. **Decide:** `not-implemented` or `unverified`; mid-turn
inject is `unsupported`.

- `PreInvocation` fires before every model call. `hook-event` records a prompt only when it
  differs from the last one recorded for the conversation (only a hash is kept); the launch
  prompt is skipped. The payload's `conversationId` is the native session id, a correlation alias
  only.
- `PostToolUse` (matcher `write_to_file|replace_file_content|multi_replace_file_content|run_command`)
  runs the core capture callback, which forwards to local `capture-change --agent antigravity`
  only when `OVERLORD_OBJECTIVE_ID` is in the launch environment. The payload never carries tool
  output; error text is not retained.
- The live `Stop` path is the once-per-objective delivery reminder from `hook-event`, skipped while
  `continuation_active` is true or `fullyIdle` is false.
- No `PreToolUse` hook is registered, so Antigravity's native permission flow is the only
  authority. The decision codec still pins `auto_approve` / `deny` / silence bytes for a future
  session-channel path; never emit `overwrite`.
- Hooks fail open: a non-zero exit is logged and ignored.

## Development verification

```bash
yarn connectors:capabilities:check
yarn test:core
yarn test:cli
yarn test:backend
```

The capability check executes recorded payload, script I/O, source guard, normalized-event, and
decision-codec fixtures. A callback/extension decision claim requires a decision-codec fixture
that pins its redacted card and exact allow/deny/defer bytes.
