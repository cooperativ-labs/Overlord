---
title: Live agent sessions
description: Observe agent activity, answer held decisions, and send instructions without replacing your agent harness.
---

Overlord can connect a running agent session to its mission. This live connection is separate
from the mission protocol: the protocol records attach, progress, questions, and delivery;
the agent-session connection handles activity, time-bounded decisions, and instructions while
the harness is running.

:::caution
As of the Latch v2 cutover, no launch path (manual `ovld launch` or a runner-dispatched launch)
creates the credentialed session channel this page describes, so `OVERLORD_SESSION_CHANNEL_ID`
is not set in a launched agent's environment and the connector hooks exit immediately without
reaching Overlord. **Observe** activity events and **Inject**ed instructions are effectively
inactive today. Of the four **Decide** request kinds, only a blocking **question** or a fixed
**choice** can be answered remotely. Since contract 173.6.0 (ADR 0065), `ovld protocol ask`
opens that answerable request for any attached session, and the answer is delivered to the
agent through the mission's live [Latch](https://latch.sh) terminal session — see
[Answering a held question](#answering-a-held-question). **Permission** and **retry** requests
cannot be answered remotely; they fall back to native harness behavior.
:::

## The three live paths

```text
Agent harness
   │
   ├─ observe ──► activity events in Overlord       (never blocks)
   ├─ decide  ◄── allow or deny while a hook waits  (bounded wait)
   └─ inject  ◄── instruction for this live session (delivery varies by harness)
```

- **Observe** reduces native events on the execution target before sending them. Tool inputs,
  outputs, file contents, environment variables, and transcript paths are not uploaded. A
  prompt is the deliberate exception because the activity feed exists to show it; secret
  redaction still runs first.
- **Decide** creates a short-lived request when the harness can pause for an answer. A callback
  never advertises an answer window beyond the time it can actually wait; Overlord reserves 20%
  of the native timeout for fallback. Many callback harnesses therefore allow only tens of
  seconds even though Overlord's general away-user policy permits a longer window. If Overlord,
  the network, or the waiter fails, Overlord emits no answer and returns control to the harness.
  Pi is different and is described below. A held decision renders in the mission panel as one of
  four request kinds — a plain allow/deny **permission**, a blocking **question**, a **choice**
  among fixed options, or a **retry** intent — depending on what the harness asked for. Only
  **question** and **choice** requests can currently be answered remotely, and only when the
  mission's objective has a live Latch terminal session Overlord can reach
  (`AgentRequestDto.delivery.mode === 'latch'`); a **permission** or **retry** request always
  falls back to the harness's own native prompt or policy.
- **Inject** sends an instruction to a specific live session. The result is honest about what
  the harness proved: **Delivered**, **Queued (turn boundary)**, **Queued (next turn)**, or
  **Unsupported**. An instruction already emitted to a harness is never automatically retried.

## Why a session channel exists

When wired up, the channel is created before the agent process starts, so startup events have
somewhere authorized to land before the mission protocol attaches. Its credential is scoped to
one channel and stored hash-only by the server. It cannot read mission context or act as a
human, and a normal user token cannot impersonate an adapter.

```text
runner/manual launch
    └─ creates channel + one-time credential
          └─ starts harness
                └─ protocol attach binds channel to agent session
```

As the caution above notes, this creation step is not currently called from either launch
path, so a launched session today runs without a credentialed channel (an `ask` may later add a
credential-free, correlation-only one) — the diagram describes the intended
shape, not current behavior. The native harness session id is only a correlation label in any
case. Neither it nor the checkout path grants access. This matters when several missions,
worktrees, or agents are active on the same machine.

## Answering a held question

When an attached agent runs `ovld protocol ask`, Overlord opens an answerable **question** (or a
**choice** when the agent passed fixed options with `--no-free-text`). If the session has no
channel, the ask creates a correlation-only channel for it (`launch_kind = 'protocol'`). That
channel has no credential and no lease: nothing can authenticate as it, and it exists only so the
request has somewhere to live. Launch still mints no channel.

The question appears at the top of the mission panel and in its objective. Answer it there, or
from a terminal:

```bash
ovld requests --mission-id coo:312        # id, status, kind, summary, revision
ovld requests resolve <id> --revision <n> --decision allow --text "Block only the panel."
```

Whether a request can be answered is decided each time it is read, from the mission's Latch
terminal session (`AgentRequestDto.delivery`). A request whose delivery mode is `read_only` (no
reachable Latch session) cannot be answered remotely — resolve it in the native harness instead.
Answers reach agents whose Latch conversation connector accepts messages: Claude Code, Codex and
Cursor. Latch refuses other harnesses and the delivery is reported `failed`.

### Recorded is not delivered

Recording your answer and delivering it to the agent are reported separately. Do not treat
`resolved: true` as proof that the agent received the answer; read `delivery.stage` instead:

| Stage         | Meaning                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------- |
| `recorded`    | The answer is stored; delivery has not started.                                          |
| `queued`      | A delivery job waits for the execution target's runner.                                  |
| `dispatched`  | A runner holds the job; its outcome arrives later.                                       |
| `confirmed`   | Latch accepted the message, or queued it behind the agent's current turn.                |
| `unconfirmed` | The send may have happened (ambiguous reply, lost socket, or a claimed job that expired). |
| `failed`      | The answer did not reach the agent (refused, unreachable gateway, absent session, or a job no runner claimed). |

Resolve waits about 25 seconds. A job that no runner claimed in that time is withdrawn and reported
`failed` / `not_dispatched`, so nothing is sent later when the runner comes back online. Every
delivery also has a five-minute deadline the runner enforces before it contacts Latch. An offline
target refuses the answer before anything is recorded. A session whose terminal has confirmed exit
never receives an answer (409 `request_not_deliverable`); a `lost` session is still attempted.

After a `failed` delivery, the mission panel's **Send again** action (REST
`POST /api/agent-requests/:id/redeliver`, `session:attach`) resends the recorded answer. The
answer cannot be edited and the request stays resolved. Overlord never resends an `unconfirmed`
delivery on its own: check the session first, then confirm. Overlord asks Latch for the earlier
attempt's receipt and sends again only when that attempt was refused or no receipt was kept.
`ovld requests` does not yet expose redelivery.

### Dismissing a question card

The dismiss (X) control on a question card hides the card from the top of the mission for you
only. The question stays open, stays listed in its objective, and can still be answered. Other
members still see it, and the card returns if the request changes. REST:
`POST` / `DELETE /api/agent-requests/:id/dismissal` (`session:read`).

The static capability catalog is diagnostic evidence; it does not manufacture a request when the
live harness never opened one.

Sending an arbitrary instruction into a running session (`ovld inputs send`) and the mission
panel's session-instructions control are retired along with the session channel above; the
backend now rejects both with `session_controls_gone`. `ovld inputs list` still reads historical
rows for a mission but cannot be used to queue a new one.

## Mission terminal sessions

A mission lists the Latch terminal sessions its execution requests started. A session reads
`running`, `stopping`, `lost` (no reliable contact — it can recover and is never treated as
ended), or `exited` (process termination confirmed). Overlord inspects open sessions in the
background about every 30 seconds through the execution target's runner, so an exit can take a
little while to appear, and longer when a runner is offline. A session that Latch no longer knows
is removed from the list without being recorded as ended.

**End session** (`POST /api/missions/:id/terminal-sessions/end`, `mission:update`) stops the
terminal for one execution request. An unfinished current attempt returns to `submitted` and its
Run Queue is paused; completed work stays complete. Only a confirmed exit reports `ended`; an
offline target, an unreachable session, or an unconfirmed stop reports `unconfirmed`, and
retrying inspects again rather than sending a second stop. Ended sessions keep their end time and
reason (`ended_by_person`, `exited`, or `unknown`). The mission shows up to five recent ones, and
`GET /api/missions/:id/terminal-sessions/history` pages the rest.

## Conflicts with hooks outside Overlord

Overlord installs hooks additively and preserves existing configuration, but two valid hooks can
still conflict because the harness decides ordering, timeout, and response composition.

### Two hooks answer the same decision

An external policy hook may auto-allow, deny, or rewrite a request while Overlord is holding the
same callback for a human. Depending on the harness, first response, last response, or a merged
response may win. Do not run two decision owners for the same native event unless that harness's
composition rule is documented and tested.

```text
Permission event
   ├─ Overlord hook ── waits for remote answer
   └─ team hook     ── auto-allows immediately
                         ▲ effective winner is harness-specific
```

For Codex, do not combine the hook adapter with an experimental app-server decision subscriber;
select one integration shape. For Cursor, avoid routing Claude-shaped permission output into
Cursor's flat decision contract.

### A hook changes failure behavior

Overlord's decision callbacks fail toward native behavior: no response means the harness shows
its normal prompt or follows its normal policy. Settings such as Cursor's `failClosed` can turn a
script error into a denial and invert that guarantee. Leave fail-closed behavior off for the
Overlord hook and apply mandatory policy in a separate, deliberately tested control.

Pi has no native permission prompt. Its optional decision interceptor therefore fails toward
**running the tool**. It is disabled unless both workspace policy and project opt-in enable it;
do not enable it without accepting the named fail-open deadline. Current builds do not expose
those gates in Settings, so normal connector setup leaves Pi decisions disabled.

### Timeouts stack

Each callback, wrapper shell, and hook manager may impose a timeout. The shortest timeout wins.
If another hook consumes most of the budget, an Overlord card can disappear just before it is
answered. Keep unrelated observational hooks non-blocking and set decision timeouts from one
policy owner.

### Duplicate observation and side effects

Overlord reduces each connector callback through that connector's compiled codec. Only an exact
normalized `file.edited` path can enter the objective/session ledger; read-only callbacks are
silent, and mutation-capable callbacks without a usable path record unavailable hook health.
Duplicate hook registrations can still run arbitrary external commands twice, so remove duplicate
registrations even though ledger synchronization itself is idempotent.

### Shared configuration namespaces

Some harnesses read compatibility configuration belonging to another harness. Cursor may read
Claude hook configuration in addition to Cursor's own file, which can make a Claude callback run
inside a Cursor session. Keep connector installations current, avoid copying generated hook
blocks between harnesses, and inspect both configurations when a hook fires twice.

### Stdout is part of the decision protocol

A decision hook's stdout is machine-readable native response data. Debug `echo` output, shell
banners, or a wrapper that combines stderr with stdout can corrupt the response. Send custom
diagnostics to stderr, redact them, and keep them bounded. Overlord itself stays silent on every
failure-to-decide path.

## Diagnose a live session

```bash
ovld doctor
ovld agent-session capabilities <agent> --json
```

`ovld doctor` detects missing or stale managed connector files. The capabilities command is
offline and shows what is fixture-proven, unsupported, not implemented, or still unverified.
After an Overlord upgrade, refresh the connector with `ovld agent-setup <agent>`.

Given the caution at the top of this page, expect `OVERLORD_SESSION_CHANNEL_ID` to be absent
from every launched session's environment today — that reflects the current, unwired state of
launch, not a misconfigured connector. A question that stays `read_only` points at the Latch
terminal session (is it still running, and is its execution target online?), not at the
connector hooks.
