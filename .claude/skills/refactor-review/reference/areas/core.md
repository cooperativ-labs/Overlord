# Area Playbook — `core`

## Roots

```
packages/core/service/       # the service layer: protocol, missions, projects, targets, workers
packages/core/service/local-target/   # git/worktree provider abstraction + registry
packages/core/repository/    # git-tree helpers
packages/core/types/         # db.ts (generated) + hand-written type surface
packages/contract/src/       # shared DTOs, closed enums, launch flags, resource paths
```

Excluded from review: `packages/core/dist/`, `packages/contract/dist/`, and
`packages/core/types/db.ts` (generated by `yarn db:codegen` — never hand-edit; if it looks
wrong the finding is about the migration or the codegen invocation).

## Read first

- `CONTRACT.md` → **Protocol Layer** (§1), plus the *Agent → Protocol*, *Protocol → Database*,
  *MCP Server → Service Layer*, and *Service → Automations* interaction surfaces.
- `packages/core/README.md`.
- The **Closed** vs **Open** enum sections of `CONTRACT.md` — closed values live in
  `@overlord/contract` and adding one requires a version bump.

This is the highest-leverage and highest-risk area: the backend, CLI, MCP server, and runner all
depend on it. Every signature change here is at least `M` effort, and anything reaching a
declared stable interface is `XL`.

## Known hot spots (baseline, contract v35)

| File | Lines | Why it is a standing candidate |

| `packages/core/service/missions.ts` | ~1200 | Mission CRUD, search, board position, launch defaults |

## Area-specific checks

### `ServiceContext` discipline
Every service function takes an explicit `ServiceContext` (`db`, `workspace`, actor, `source`).
Flag:
- functions that reach for a database client or workspace by any other route
- context objects being reconstructed mid-call-chain rather than threaded through
- `source` being inspected to branch business logic — a service that behaves differently for
  `cli` vs `webapp` is surface drift wearing a service-layer costume, and is a high-value finding

### `protocol.ts` decomposition
Group the verbs by lifecycle stage (attach/session, progress/update, delivery, objectives,
follow-up) and measure each group's lines and shared-helper usage. The test files already
suggest the seams — `protocol.deliver.test.ts`, `protocol.objectives.test.ts`,
`protocol.record-work.test.ts` — so an extraction that matches the existing test split is
cheap and reviewable. Verify no verb loses its event-emission or coverage-aggregation step in
the move; those side effects are the contract, not incidental.

### Contract barrel vs. deep entry points
`@overlord/contract` exports `.`, `./ext/everhour`, `./ext/github`. Flag:
- consumers importing from `@overlord/contract` when a narrower entry exists
- extension types leaking into the root barrel (which makes every consumer depend on every
  extension)
- a closed enum from `CONTRACT.md` re-declared as a local string union somewhere in `core`,
  `backend`, `cli`, or `webapp` — this is the single most common type-duplication finding here:

```bash
grep -rn "'draft' *| *'execute'\|'execute' *| *'review'" packages backend cli webapp \
  --include='*.ts' --include='*.tsx' | grep -v node_modules
```

### Generated vs. hand-written types
`packages/core/types/db.ts` is generated. Flag hand-maintained row interfaces that shadow a
generated table type (`interface ScheduleRow`-style declarations are the tell), and evaluate
whether each can derive from the generated type via `Selectable<...>` instead. Where a local
interface exists deliberately — because the query selects a projection, or the shape crosses a
boundary — say so and leave it.

### Provider abstraction fit
`service/local-target/` is a registry over git/worktree providers with real alternates
(`in-process-provider`, `runner-queue-provider`, `desktop-bridge`, `fake-provider`). Judge fit by
counting implementations per abstraction: several implementations justify the indirection; one
implementation plus a fake usually means the interface is shaped around its only caller. Check
whether each provider method is used by every consumer or whether the interface has grown a
union of unrelated needs.

### Worker job modules
`worker-jobs.ts`, `queue-runtime.ts`, `live-activity-jobs.ts`, `push-notification-jobs.ts`
share an enqueue/claim/complete shape. Compare their retry and idempotency handling; divergence
is a high-value duplication finding because it produces different failure behavior per job type.

### Cycles
`backend/repository.ts` imports deep into `packages/core/service/*` while service modules import
each other. Before proposing any extraction, check that it does not create a cycle:

```bash
grep -n "^import .*from '\./" packages/core/service/protocol.ts
grep -rn "from './protocol.js'" packages/core/service | grep -v test
```

### Test helpers
`packages/core/service/test-helpers.ts` is the shared harness. Flag inline fixture construction
duplicated across three or more test files, and Postgres conformance assertions that belong in
`postgres-conformance.test.ts` rather than scattered.

## Verification for refactors in this area

```bash
yarn lint
yarn typecheck:core
yarn test:core
yarn contract:build:prod   # when packages/contract changed
```

Because every other workspace consumes this one, a `core` refactor also needs
`yarn typecheck:backend`, `yarn typecheck:cli`, and `yarn typecheck:webapp` — list them in the
finding's verification step, not as an afterthought.
