## For Users

### Requirements

- Claude Code **2.1.328 or later**. The plugin's hooks are `mcp_tool` hooks, and the
  permission-decision hook needs `onFailure: "block"`, which 2.1.328 added. `ovld doctor`
  reports an older version as an error.
- Overlord CLI (`ovld`) and `node` on `PATH`. The hooks server is a Node script, and every hook
  runs an `ovld` command. See the Overlord docs / Settings → Agents & MCP.
- `MISSION_ID` is exported automatically when a Claude session is launched from Overlord.

### Install (recommended)

```bash
ovld agent-setup claude
```

`ovld agent-setup claude` materializes the plugin into a local marketplace under
`~/.ovld/claude/marketplace` (the plugin tree lands in `plugins/overlord`, with a
generated `.claude-plugin/marketplace.json` beside it), then drives the Claude
CLI to register and enable it:

```bash
claude plugin marketplace add ~/.ovld/claude/marketplace
claude plugin install overlord@overlord-local --scope user
```

Claude Code only loads plugins published through a registered marketplace — a
plugin directory dropped into `~/.claude/plugins` is not discovered — so this
marketplace registration is what makes the Claude desktop app and CLI pick up
the connector. If the `claude` CLI is not on `PATH`, setup still writes the
marketplace manifest and prints the two commands above to run once Claude Code
is installed.

After installing, setup checks the Claude Code version, that the plugin is enabled, and that
its `plugin:overlord:overlord-hooks` MCP server connects (`claude mcp get`), and prints any
problem with its fix.

The plugin prompts for `overlord_url` at install time. It no longer has a `user_token`
setting: the hooks and the CLI authenticate the same way, through `ovld auth repair` when a
shared session already exists, then `ovld auth login`, Overlord Desktop, or
`Overlord_USER_TOKEN` / `OVLD_USER_TOKEN` in the environment Claude Code starts from.

### Install (local dev)

```bash
claude --plugin-dir /absolute/path/to/Overlord/connectors/adapters/claude
```

### Namespaced components

Inside Claude Code the components are surfaced with the plugin prefix:

- skill → `overlord:overlord-mission`
- commands → `/overlord:attach`, `/overlord:connect`, `/overlord:load`, `/overlord:create`, `/overlord:prompt`, `/overlord:discuss-objective`, `/overlord:add-objectives`, `/overlord:record-work`

Prompts generated by the runner should reference these names in bundle instruction mode.

### Hooks and the CLI fallback

Every Overlord hook is an `mcp_tool` hook. Claude Code calls a tool on the plugin's bundled local
MCP server `overlord-hooks`, and that tool runs the same `ovld` command you could run yourself:

| Hook | Tool | Runs | On failure |
| --- | --- | --- | --- |
| `UserPromptSubmit` | `overlord_hook_user_prompt_submit` | `ovld protocol hook-event --hook-type UserPromptSubmit` (records follow-ups) | continues |
| `PostToolUse` (`Edit\|Write\|MultiEdit\|NotebookEdit\|Bash`) | `overlord_hook_post_tool_use` | `ovld protocol capture-change` (local changed-file ledger) | continues |
| `Stop` | `overlord_hook_stop` | `ovld agent-session inbox`, then `ovld protocol hook-event --hook-type Stop` (delivery reminder, once per objective) | continues |
| `PermissionRequest` | `overlord_hook_permission_request` | `ovld agent-session request` (remote decision) | **denies** |

The first three are in the plugin's `hooks/hooks.json`, run in every session, and do nothing
until the session is bound to an Overlord mission. The `PermissionRequest` hook is not in the
plugin: `ovld launch` adds it through `claude --settings` only for sessions it launched with a
session channel, and only when the plugin and its hooks server are installed. If Claude Code
cannot reach the hooks server for that hook, it denies the request rather than approve it. If
the backend is slow or fails, the tool returns no decision and Claude shows its normal prompt.

Subagents, nested runs and headless runs:

- Hooks inside a subagent or fork carry the parent's session id, so their follow-ups and file
  edits belong to the parent's objective. `SubagentStop` is not registered. While background
  subagents are still running, the Stop reminder waits for the Stop that follows their
  completion notice, and that notice is never recorded as your follow-up.
- A `claude -p` started from inside a launched session does not inherit the launch binding: its
  prompts, Stop and decisions are not attributed to the parent's mission (its file edits still
  are). It binds only if its own agent attaches.
- In a headless session (`claude -p`, Agent SDK), the final Stop waits up to 60 s for an
  instruction sent from Overlord before the run ends. Claude Code shows a heartbeat every 30 s
  meanwhile. Interactive sessions never wait. The Stop hook timeout is 100 s.

Claude Code has no automatic fallback from a failed `mcp_tool` hook. If the hooks server is not
connected (`/mcp` shows `plugin:overlord:overlord-hooks` as failed, `node` is not on `PATH`, or
the plugin is disabled), follow-up capture, file capture and the Stop reminder are off, but the
session keeps working. The **`ovld protocol` CLI is the supported fallback** and is unchanged:
`ovld protocol attach`, `update`, `ask`, `deliver` and `changes` all work without the hooks.
Declare the files you changed with `--paths` on `update` or `deliver`. To fix the hooks, run
`ovld doctor`, which names the problem, then `ovld agent-setup claude`.

### Status line (optional)

A plugin cannot set Claude Code's status line, so it is opt-in at setup:

```bash
ovld agent-setup claude --status-line
```

This adds `ovld status-line --agent claude --payload-file -` to `~/.claude/settings.json`
(refreshing every 10 s) only when you have no status line. It shows the session's mission and
objective and whether it is awaiting your answer or approval, blocked on a question, or
delivered. It prints nothing in a session that is not bound to a mission. To combine it with your
own status line, pipe the same stdin into that command from your script.

## For Developers

### Overlord layer map

This connector is intentionally reviewable against the four connector layers in `connectors/README.md`:

- Connector Core: `../../core/overlord-mission/SKILL.md` and its `reference/` files carry the durable attach, update, ask, and deliver workflow.
- Connector Plugins: `skills/overlord-mission/SKILL.md`, `commands/`, `hooks/hooks.json`, `.mcp.json`, and the rendered `scripts/overlord-mcp.mjs` hooks server extend the core for Claude Code.
- Plugin Adapters: `.claude-plugin/plugin.json` declares the Claude-native plugin package and install-time config.
- Prompt Wrappers: `prompt-wrapper.md` describes the launch-time context-file prompt shape for Claude.

### What ships

- `skills/overlord-mission/SKILL.md` — Claude adapter template with a `<!-- @connector-core -->` marker; setup interpolates shared core content at install time.
- `commands/*.md` — slash commands for session routing, objective discussion, mission creation, and work recording.
- `hooks/hooks.json` — three fail-open `mcp_tool` hooks: mission follow-up (`UserPromptSubmit`),
  local objective-ledger capture (`PostToolUse`), and the Stop delivery reminder. No shell or
  Python hook script ships.
- `.mcp.json` + `scripts/overlord-mcp.mjs` — the `overlord-hooks` local stdio server, started
  with `--hooks`. `scripts/overlord-mcp.mjs` is rendered at setup from the shared
  `connectors/core/scripts/overlord-mcp.mjs`. In `--hooks` mode it lists no tools, so the model
  never sees the hook tools, and each tool forwards the rebuilt native payload to a fixed `ovld`
  command. Only a path normalized by the Claude codec as `file.edited` records non-exclusive
  `declared_edit`/`direct` evidence; normalized read, search, and fetch callbacks are silent
  no-ops. Mutation-capable callbacks without a normalized edit path, plus shell, generic,
  unknown, and unmapped callbacks, record unavailable evidence health.
- `userConfig` for `overlord_url`.
- `conformance-manifest.yaml` — connector conformance declaration for the Overlord contract.
- `prompt-wrapper.md` — Claude launch context-file guidance.

The shared Connector Core source lives at `connectors/core/overlord-mission`. `ovld agent-setup claude` interpolates that core into the adapter skill template and installs core reference files so the runtime package is self-contained.

### Deliberate omissions

- **No model-facing local MCP shim.** The Claude plugin reaches Overlord's hosted MCP server for the model's tools. The bundled shim runs only in `--hooks` mode and lists no tools.
- **No decision hook in the plugin.** A fail-closed `PermissionRequest` hook in the plugin would run in every Claude session on the machine, so a broken local install would deny every permission prompt. `ovld launch` registers it per launch instead.
- **No native resume flag.** Sessions are re-entered through the plugin's own surfaces rather than a `--session` launch flag.

See the [adapter capability matrix](../../README.md#adapter-capability-matrix) for how this compares across adapters.
