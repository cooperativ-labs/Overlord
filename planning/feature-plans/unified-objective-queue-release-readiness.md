## Corrections verified here

- Run Queue write-through previously compacted every mission row, including
  launching, active and completed objectives. It now moves only waiting/blocked
  draft/submitted objectives across their existing slots. Explicit removal moves
  only the removed objective to the end. Lifecycle dequeue preserves positions
  before reopen redistributes the original slots.
- Run Queue mutations now acquire mission locks before changing queue entries,
  consistently ordering multi-mission locks. A real PostgreSQL reorder race
  reproduced a deadlock before this fix and passes afterward. Position updates
  also publish matching revision/change-feed evidence.
- A failed SQLite rebuild previously left a transaction open and foreign keys
  disabled. The runner now rolls back and restores the prior FK setting before
  propagating the error. Historical migration files are untouched.
- Corrected the stale web assertion that expected cumulative file-list metadata
  when file tracking was unavailable; retained the unavailable-state assertion.
- Removed obsolete future-state descriptions from current source comments.

The position, deadlock and migration-cleanup defects have regressions that failed before the correction and
passed afterward. A new integration test uses real protocol attach/deliver and
the dispatch worker, proving that an out-of-order delivery dispatches the queued
successor while the earlier unqueued draft stays unqueued and receives the
informational approval notice.

## Coordinated cutover procedure — not executed

Do not release while an acceptance row or applicable full-suite gate is unresolved.
The separately scheduled `coo:1274.91mn` discussion-state correction must also land
before releasing; this objective does not implement that future objective.

1. Select one primary release SHA and a matching mobile SHA. Preserve the previous
   CLI/desktop/mobile artifacts and backend deployment identifier. From a clean
   release checkout, run the commands below and `yarn release:preflight major`.
   A working-tree test pass does not satisfy the committed-SHA release gate.
2. Stop all old writers before migration: quit installed Desktop instances and
   local dev backends, stop runner processes and queued agent launches, stop the
   hosted `overlord-backend` service and any separately running dispatch workers,
   and close web/mobile clients. Keep writers stopped through backup and restore
   rehearsal. Pausing queues alone does not prevent old clients from writing.
   Confirm the target Railway project/service against `.railway/railway.ts`:
   `overlord-cloud` / `overlord-backend`. The live deployment identity and exact
   stop/restart control must be recorded at release time; no live infrastructure
   was inspected here.
3. Back up each affected SQLite instance and the hosted PostgreSQL database.
   Resolve each SQLite path with `node --import tsx scripts/print-db-path.ts`
   under that instance's actual configuration. Use SQLite's backup API rather
   than copying an open database or omitting WAL contents. With writers stopped:

   ```sh
   umask 077
   sqlite3 "$RELEASE_SQLITE_PATH" ".backup '$RELEASE_SQLITE_BACKUP'"
   sqlite3 "$RELEASE_SQLITE_BACKUP" 'PRAGMA integrity_check; PRAGMA foreign_key_check;'
   pg_dump --dbname="$RELEASE_DATABASE_URL" --format=custom --file="$RELEASE_PG_BACKUP"
   pg_restore --list "$RELEASE_PG_BACKUP" > "$RELEASE_PG_BACKUP.list"
   ```

   directories and retain remote object storage with the backup. Record migration

   `yarn desktop:publish`, keeping all writers stopped. Apply the hosted migration

   target before proceeding; do not assume a private Railway URL is reachable
   from the operator's workstation. The CLI script documents the public-proxy
   invocation when needed. For Local, only the matching new binary may open and
   migrate the backed-up database.
5. Before enabling writes, verify ledger version `20261114120000`, zero objective

6. Deploy the matching backend using `yarn server:deploy`, then finish the gated

## Rollback procedure — not executed

1. Stop all new writers/dispatchers and close all clients. Preserve the failed
   candidate database for diagnosis. Restoring loses writes since the backup;
   establish that boundary before accepting new production writes.
2. Restore PostgreSQL into an empty replacement database using
   `pg_restore --exit-on-error --dbname="$RESTORE_DATABASE_URL" "$RELEASE_PG_BACKUP"`.
   Restore required roles/grants separately if not already provisioned, then
   verify ownership, RLS, evidence counts and ledger against the backup inventory.
   Switch the backend to that verified restored database using the normal secret
   configuration workflow. Do not restore on top of a live candidate database.
3. With Local processes stopped, archive the candidate SQLite database and its
   `-wal`/`-shm` sidecars. Restore the backup to the configured path with the proper
   owner/mode; ensure candidate WAL sidecars cannot replay onto the restored file.
   Verify `integrity_check`, `foreign_key_check`, ledger and evidence counts.
4. Restore matching pre-cutover backend, CLI, connectors, Desktop, web and mobile
   versions, and attachment storage where applicable. Only then restart writers.
   Never roll back binaries alone against multi-draft data. Do not reverse the
   conversion with an ad hoc `UPDATE draft -> future`.
