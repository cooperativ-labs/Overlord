## Summary

The backend absorbed fifteen contract versions in three weeks and came out structurally better on
every tracked metric that the last four reports pushed on: every 2026-10-05 finding landed, the
largest file shrank by 700 lines, all nine background loops share one base with graceful shutdown,
and the Postgres bootstrap duplication is gone. The growth (+6,500 non-test lines) is all feature
surface, built in the sanctioned shape — thin routers, injected `db`, core-owned rules, conformance
tests from day one. The findings below are therefore seams the new features left rather than decay.
The single highest-value refactor is **F1**: the credential store now has two complete OAuth
connect-and-callback flows over the same table — the organization-scoped Knowledgebase flow in
`AccountConnections` and the profile-scoped provider flow in `ProfileConnections` — that have
already diverged in outcome shape, scope checks, and the nineteen hand-written
`INSERT`/`UPDATE account_connections` statements they share between them. Below it: the extension
modules still construct their own `ProfileConnections` per call beside the composition root's
singleton (F2), delivery presentation persistence sits in a backend worker while its mission-summary
sibling lives in core (F3), the "current run" delivery rule has three implementations (F4), and two
Postgres `LISTEN` modules are 70 lines of copy (F5).

## Findings

### F1. One OAuth connect/callback sequence for both connection scopes in `backend/connections/`
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Types and contracts
- **Evidence**:
  - `backend/connections/service.ts:209-262` (`AccountConnections.start`) and
    `backend/connections/profile.ts:508-553` (`ProfileConnections.beginOAuth`) — the same
    transaction: select the live row for the scope, else `INSERT … state = 'pending'`, then
    `beginAuthorization(tx, …)`. Two `INSERT INTO account_connections` statements with different
    column lists (`:239` sets `tool_policy_version`; `:534` sets `credential_kind`).
  - `service.ts:270-357` (`complete`) and `profile.ts:560-660` (`completeOAuth`) — the same
    callback: validate `state` against `AUTHORIZATION_STATE_PATTERN`, `consumeAuthorization`,
    `query.error` → `authorization_denied`, bounded `code`, open the PKCE verifier with
    `verifierAad`, exchange, `UPDATE … SET state = 'connected', credential_* …` guarded by
    `state <> 'disconnected'`, and the "disconnected while signing in → revoke the new grant"
    branch (`service.ts:340-349`, `profile.ts:654-659`).
  - Already diverged: the profile flow adds `requiredScopes`, `describeAccount`,
    `uniqueExternalAccount` (`profile.ts:618-636`) and returns `ProfileCallbackOutcome`
    (`:151-160`: `returnUrl`, `connectionId`, `errorCode`), while the organization flow runs
    `access()` and `listWorkspaces` and returns the narrower `CallbackOutcome` (`service.ts:68-73`).
    The two refresh persists (`service.ts:491`, `profile.ts:731`) and the two grant persists
    (`service.ts:327`, `profile.ts:639`) are four `UPDATE` statements over 12–20 positional `?`
    each that must stay column-for-column aligned by hand.
  - Nineteen `INSERT`/`UPDATE account_connections` statements across `service.ts` (6),
    `profile.ts` (8), and `credential-rows.ts` (5); only the five in `credential-rows.ts` are
    shared.
  - `profile.ts:470-473` casts `row.credential_format as Parameters<typeof
    missingKeyIsConfiguration>[2]` because the closed `credential_format` vocabulary
    (`CONTRACT.md` "Controlled Vocabularies", v153) has no type in `@overlord/contract`.
- **Problem**: The Credential Surface (`CONTRACT.md` "Extension → Account Connections") makes the
  connections module the single owner of OAuth state, the refresh lease, and credential
  persistence, but inside the module that ownership is implemented twice. The next provider in
  either scope (an organization-scoped provider other than Knowledgebase, or a profile-scoped one
  that lists workspaces) copies one of the two flows, and a fix to the callback's failure handling
  (the `account_in_use` race, the revoke-on-late-disconnect branch) has to be made in both. The
  2026-10-05 review's security note that each credential boundary "is implemented in exactly one
  module" no longer holds inside that module.
- **Proposed change**: Add `backend/connections/oauth-flow.ts` owning the scope-independent
  sequence, parameterised by a small adapter the two classes already have most of:
  `beginConnectionOAuth(db, { findLiveRow(tx), insertPendingRow(tx), key, returnTo, returnUrl,
  authorizeUrl })` and `completeConnectionOAuth(db, { providerFilter?, key, exchange, afterExchange?
  (scopes/account/workspace checks returning a failure code or extra columns), revoke })`
  returning one `ConnectionCallbackOutcome` (the profile superset; the organization flow fills
  `returnUrl`/`connectionId`/`errorCode` with `null`). Move the two grant-persist `UPDATE`s into
  one `storeConnectionGrant(tx, row, { credential, key, expiresAt, refreshExpiresAt, extra })` in
  `credential-rows.ts` beside `eraseCredential`. Add a `CredentialFormat` type to
  `@overlord/contract` for the closed vocabulary and drop the cast.
- **Sequenced steps**:
  1. Add `CredentialFormat` to `packages/contract` and type `missingKeyIsConfiguration`,
     `openCredential`, and `ConnectionCredentialRow.credential_format` with it. No runtime change.
  2. Extract `storeConnectionGrant` and point the two callback persists and the two refresh
     persists at it, keeping each caller's extra columns as a parameter. The four `UPDATE`s become
     one; `connections.postgres-conformance.test.ts` and `profile-connections.postgres-conformance.test.ts`
     assert the stored row shape.
  3. Unify the outcome type (additive on the organization side) and extract
     `completeConnectionOAuth`; convert `ProfileConnections.completeOAuth` first (it is the
     superset), then `AccountConnections.complete`.
  4. Extract `beginConnectionOAuth`; convert both `start` paths.
- **Contract impact**: None to routes or DTOs. `CallbackOutcome` is internal to the backend
  (`createConnectionsPublicRouter` maps it to redirects). Adding `CredentialFormat` to
  `@overlord/contract` is additive and needs no version bump.
- **Risk**: Credential handling. The three conformance suites (`connections` 1,536 lines,
  `profile-connections` 675, `github-connections` 745) cover both flows' success, denied,
  expired, disconnected-mid-flow, and refresh paths; run `yarn test:backend` and
  `yarn test:conformance`. Keep each step's SQL byte-identical to one of the existing statements
  so review can diff it.

### F2. Compose the extension services only from the connections runtime; delete the per-call default instances
- **Value / Effort**: Medium / S
- **Dimension**: Abstraction fit (excess); Layering and boundary leaks
- **Evidence**:
  - `backend/ext/everhour/service.ts:1281-1301` and `backend/ext/github/user-oauth.ts:407-417` —
    each module ends with `export const { … } = create…Service(() => profileConnections(
    requireDatabaseClient(), [provider]))`. The thunk is invoked on every call site
    (`connections()` ×6 in the Everhour service, ×7 in the GitHub one), and
    `profileConnections` (`profile.ts:173-179`) constructs a **new** `ProfileConnections` each
    time: a fresh `lockOwner` (`profile.ts:182`) and a fresh key-ring parse from `process.env`
    (`keyring.ts:80`).
  - The routers already receive the composition root's singleton:
    `backend/index.ts:1729` (`() => connectionsModule().profiles`) and `:1737`;
    `connections/index.ts:110` builds that one instance with the configured providers.
  - The only production consumer of the module-level defaults is
    `backend/repository.ts:213` → `createPrivateGitHubRepository` at `:3468` (composite project
    initialization, called from `index.ts:1351`). The Everhour defaults are consumed only by
    `backend/mission-secondary-workspace.test.ts`; the GitHub ones also by
    `backend/project-initialization.test.ts`.
  - Importing either extension module therefore imports `db.ts` at module load (the eager SQLite
    open the 2026-10-05 review traced for the legacy test preamble).
- **Problem**: The credential store has two composition paths. A GitHub token refreshed during
  project initialization and one refreshed by `/ext/github/*` in the same process run under
  different `lockOwner`s against the same `refresh_lock_owner` column — `withRefreshLease` keeps
  this correct by waiting, but the contract's "serialises refresh" is now a property of two
  instances rather than one. Any instance-level state the module gains later (a key-ring reload,
  an adapter cache, metrics) silently splits the same way, and the per-call construction re-parses
  `ACCOUNT_CONNECTIONS_ENCRYPTION_KEY` on every Everhour timer call.
- **Proposed change**: Delete both `export const { … } = create…(…)` blocks. `initializeProject`
  takes its GitHub repository creator as a parameter (`deps: { createPrivateGitHubRepository }`),
  supplied by `backend/index.ts:1351` from
  `createGitHubUserOAuth(() => connectionsModule().profiles)`; `repository.ts` loses its import of
  `ext/github/user-oauth.ts`. The two tests build their own service with
  `create…Service(() => profileConnections(db, [provider]))`, which `backend/AGENTS.md` already
  describes as the standalone composition.
- **Sequenced steps**:
  1. Thread the creator into `initializeProject` with the existing default as the parameter's
     default value (zero behavior change); update `project-initialization.test.ts` to pass it.
  2. Switch `index.ts:1351` to the runtime-backed creator and remove the default value and the
     `repository.ts` import.
  3. Delete the Everhour default block; update `mission-secondary-workspace.test.ts`.
- **Contract impact**: None. The Extension → Core surface is unchanged; this removes an unsanctioned
  second instantiation, it does not add a route or a table.
- **Risk**: Low. `yarn test:backend` (`project-initialization.test.ts`, `ext/github/routes.test.ts`,
  `ext/everhour/{service,routes}.test.ts`, `mission-secondary-workspace.test.ts`) and
  `yarn typecheck:backend`, which fails on any remaining import of the deleted names.

### F4. One "current-run delivery" rule for the mission summary read path, its worker, and core
- **Value / Effort**: Medium / M
- **Dimension**: Duplication with divergence
- **Evidence**:
  - `backend/mission-summary.ts:47-48` — `CURRENT_RUN_PREDICATE` (SQL:
    `o.reopened_at IS NULL OR d.delivered_at >= o.reopened_at`, with `workspace_id` and
    `deleted_at`), used by three loaders at `:115-160`, one of which also computes latest-per-
    objective with `ROW_NUMBER() OVER (PARTITION BY d.objective_id …)`.
  - `backend/mission-summary-compose-worker.ts:122-131` — the same predicate inlined a second
    time, after which `:138` hands the rows to core's `splitMissionSummaryRuns`.
  - `packages/core/service/mission-summary-compose.ts:102-130` — the third implementation, in
    memory: `Date.parse(delivery.deliveredAt) < Date.parse(boundary)` → superseded, and a
    `seenObjectives` set for latest-per-objective. The worker therefore applies the run boundary
    twice (SQL then memory); the read path applies it once in SQL and never calls the core
    splitter.
  - Both compare `timestamptz` columns (`database/postgres/migrations/002_initial_core.sql:584`)
    in SQL but ISO strings via `Date.parse` in core; equal today because every writer uses
    `nowIso()`, but nothing pins that.
- **Problem**: Whether a delivery is "current" decides what the summary shows, which suggestions
  are projected, and what the watermark may advance to. The rule lives in two SQL fragments and one
  TypeScript function that must agree to the millisecond, and the read path and the worker select
  evidence through different queries, so a change to the boundary (for example counting a
  re-opened objective's own re-delivery differently) is three edits and a conformance test can only
  catch the pair it exercises.
- **Proposed change**: Move the worker's `loadMissionSummaryEvidence` (`worker:70-200`) to core as
  `readMissionSummaryEvidence(db, missionId, { workspaceId? })` and have `mission-summary.ts`'s
  `loadSourceDeliveries`/`countCurrentRunDeliveries`/`loadCurrentRunDeliveries` consume
  `runs.latestByObjective` and `runs.currentRun` from it instead of their own SQL. Export the SQL
  predicate once from `mission-summary-compose.ts` (`currentRunDeliveryPredicateSql`, the pattern
  `jsonTextFieldSql` already set) for the single remaining place that must filter in the database.
  `splitMissionSummaryRuns` stays the in-memory authority and gains a unit test for the boundary
  equality case.
- **Sequenced steps**:
  1. Export the predicate from core; replace the two SQL copies. Zero behavior change.
  2. Move `loadMissionSummaryEvidence` to core (the worker already passes `db`); worker imports
     it. `mission-summary-compose-worker.test.ts` unchanged.
  3. Rewrite the three read-path loaders over the core reader; keep `requireMissionPermission`
     and the `workspace_id` guard in the backend. `mission-summary.postgres-conformance.test.ts`
     (576 lines) covers evidence selection, caps, and the watermark.
- **Contract impact**: None. `MissionSummaryResponse` and the `MISSION_SUMMARY_EVIDENCE_LIMIT`
  cap are unchanged; evidence is still "selected in the database before limits" via step 1's
  predicate.
- **Risk**: Medium — the read path's `ROW_NUMBER` query and core's splitter must produce the same
  latest-per-objective ordering on `delivered_at DESC, id DESC`; add that case to the conformance
  suite before step 3. `yarn test:backend`, `yarn test:core`, `yarn test:conformance`.
