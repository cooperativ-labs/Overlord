## Summary

The backend absorbed eight contract versions in six days and the trend numbers are still moving
the right way where the previous reports pointed: `repository.ts` is 317 lines smaller,
`launch.ts` and `everhour/service.ts` shed the code the last report asked to move, every open
finding landed, and `index.ts` shrank even while gaining the profile-connection wiring. The new
debt is concentrated in two places the previous report could not see. First, contract v153 added a
second account-connections class (`ProfileConnections`, 933 lines) beside the v152 one
(`AccountConnections`, 655 lines) over the same table, and the two now carry parallel copies of the
security-sensitive mechanics the contract says the module owns once: the single-use authorization
start/consume transactions, the refresh lease and its release, re-sealing, reauthorization, and
error recording. They have already diverged in four places. Giving those mechanics one home (F1)
is the highest-value refactor available. Second, `GeminiRunSession` grew from ~600 to ~1,030
lines in a week by absorbing performance accounting and thread summarization alongside the run
loop (F3); the previous report's "one responsibility, leave it" verdict no longer holds. Below
those: the two OAuth callback handlers in the connections router are the same twelve-line shape
twice (F2), four evaluation harnesses totalling 1,922 lines sit beside production modules with
already-divergent statistics helpers (F4), and the v153 migration left three unreferenced exports
behind, one of which is the only read of `account_connections` outside the module (F5).

## Findings

### F1. Give the connection authorization lifecycle, refresh lease, and row-state transitions one owner shared by `AccountConnections` and `ProfileConnections`
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence
- **Evidence**:
  - Constants: `backend/connections/service.ts:73-77` and `backend/connections/profile.ts:150-154` (`AUTHORIZATION_TTL_MS`, `MAX_OPEN_AUTHORIZATIONS`, `ACCESS_EXPIRY_SKEW_MS`; the profile copy adds two more).
  - Clock trio `now()/timestamp()/sleep()`: `service.ts:149-157` and `profile.ts:207-216`, byte-identical.
  - `verifierAad`: `service.ts:80-85` (`…:${row.organization_id}:…`) and `profile.ts:180-190` (`…:-:…`). The contract (`CONTRACT.md:476`, "`-` when profile-scoped") makes these one rule: `organization_id ?? '-'`.
  - Authorization start transaction (find-or-insert the pending row, prune consumed/expired authorizations, count open, insert the hashed state and sealed verifier): `service.ts:209-287` (`start`) and `profile.ts:518-581` (`beginOAuth`). ~45 lines each; they differ only in the scope predicate and two insert columns.
  - Callback consume transaction (look up by `state_hash`, mark consumed, load the row, `fresh`): `service.ts:288-330` (`complete`) and `profile.ts:583-625` (`completeOAuth`), including the duplicated state regex `/^[A-Za-z0-9_-]{40,80}$/` (`service.ts:296`, `profile.ts:601`) and the `code.length <= 2048` guard.
  - Refresh-lease loop (`stale`/`fresh` computation, the `UPDATE … refresh_lock_owner` lease, `REFRESH_LEASE_MS * 2` deadline, 100 ms sleep): `service.ts:446-514` (`accessToken`) and `profile.ts:710-760` (`oauthAccessToken`).
  - `refreshLeased` (release-on-failure SQL, `invalid_grant` → reauthorization, persist-before-use SQL): `service.ts:516-556` and `profile.ts:762-816`.
  - `requireReauthorization`: `service.ts:558-564` and `profile.ts:920-925`, identical SQL. `recordError`: `service.ts:573-578` and `profile.ts:927-932`, identical. Disconnect/erase transaction: `service.ts:415-444` and `profile.ts:907-918`. `reseal`: `service.ts:611-631` and `profile.ts:888-894`.
  - Divergence already present: (a) `profile.ts:909` guards the erase with `AND state <> 'disconnected'`; `service.ts:434` does not; (b) `service.ts:303-306` looks up the authorization by `state_hash` alone, while `profile.ts:605-608` joins on provider and `organization_id IS NULL`, so a profile-scoped state presented at the Knowledgebase callback is consumed by the wrong class; (c) only `service.ts:448` honours an `AbortSignal` in the lease loop; (d) only `service.ts:563` fires `onAccessLost`. (b) and (d) are behavior, see *Adjacent findings* and *Contract impact*.
- **Problem**: `CONTRACT.md:3240` says "the connections module owns storage, encryption, the key ring, re-sealing, OAuth state, the refresh lease, state, and DTOs". The module does, but twice. The lease and the single-use state consumption are the two mechanisms whose correctness the Knowledgebase and GitHub flows depend on, and a fix to one copy (a lease deadline change, a lost-lease handling change, a new column to persist on refresh) is now two edits with no test that asserts the copies agree. The 2026-10-05 report recorded that these boundaries were "each implemented in exactly one module"; v153 undid that.
- **Proposed change**: One `backend/connections/lifecycle.ts` (new, ~200 lines) holding the scope-agnostic mechanics as functions over `(db | tx, clock, row)`: `connectionClock(options)` (the trio), the three constants, `verifierAad(row)` with `organization_id ?? '-'`, `beginAuthorization(tx, { row, provider, state, verifier, key, returnTo, returnUrl })`, `consumeAuthorization(tx, { stateHash, scope })`, `leaseRefresh(db, { row, lockOwner, clock })`, `releaseLease(db, { row, lockOwner, code })`, `persistRefreshedCredential(db, { row, lockOwner, envelope, keyId, expiries, extraColumns })`, `markReauthorizationRequired(db, { id, code, lockOwner? })`, `recordConnectionError(db, id, code)`, and `eraseConnection(tx, id)`. Both classes keep their public API, their scope predicates, their key policy (`readKey` vs the ring, which the contract deliberately keeps different), and their DTO lists; they call the shared functions. `AccountConnections.requireReauthorization` stays a wrapper that adds `onAccessLost`.
- **Sequenced steps**:
  1. Extract `connectionClock`, the constants, and the unified `verifierAad` into `lifecycle.ts`; both classes import them. Pure move; AAD strings are byte-identical for both scopes.
  2. Extract `markReauthorizationRequired`, `recordConnectionError`, `eraseConnection`, and the reseal SQL. `AccountConnections.disconnect` keeps its unguarded erase unless the owner confirms the profile guard is the intended rule (then that is a one-line behavior fix to flag in the PR).
  3. Extract `leaseRefresh` / `releaseLease` / `persistRefreshedCredential` and rewrite both `accessToken` and `oauthAccessToken` over a shared `withRefreshLease(…, refresh)` loop, keeping `signal` support as an optional argument both can pass.
  4. Extract `beginAuthorization` and `consumeAuthorization`, parameterised by `{ organizationId: string | null, provider, serverUrl }`. `consumeAuthorization` takes the scope predicate as a required argument, so step 4 is where divergence (b) is resolved; flag it in the PR as the intended fix.
- **Contract impact**: None — no route, DTO, column, envelope format, or AAD string changes. Step 4 changes which class consumes a cross-scope state (currently the Knowledgebase callback would consume a GitHub state and return `failed`; afterwards it returns `expired` without consuming). That is the only behavioral delta and it should be stated in the PR.
- **Risk**: An AAD or lease regression would make stored verifiers or credentials unreadable, or allow two concurrent refreshes. `backend/connections/connections.postgres-conformance.test.ts` (1,536 lines; the Knowledgebase lease, callback, disconnect, and re-seal cases), `backend/connections/profile-connections.postgres-conformance.test.ts` (654), and `backend/connections/github-connections.postgres-conformance.test.ts` (743; four lease/`staleRevision` cases) seal and open under both scopes and both keys. Run `yarn test:backend` and `yarn test:conformance` with `TEST_DATABASE_URL`.

### F2. One OAuth callback handler and completion page for both connection scopes in the connections router
- **Value / Effort**: Medium / S
- **Dimension**: Abstraction fit (missing); Duplication with divergence
- **Evidence**:
  - `backend/connections/routes.ts:123-135` (`completionPage`, Knowledgebase-only text) and `:193-205` (`profileCompletionPage`, parameterised by label; same four branches).
  - `routes.ts:155-183` (the Knowledgebase `CALLBACK_PATH` handler inside `createConnectionsPublicRouter`) and `:242-280` (`createProfileConnectionCallbackHandler`): both set `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, run the service `complete*` call under a catch that yields `failed`, compute a redirect target from `returnTo` and the web origin, then either `302` or send the status page with `200`/`400`.
  - `profileCallbackTarget` (`routes.ts:207-231`) already computes exactly the Knowledgebase target (`provider=knowledgebase&status=…` on `MOBILE_RETURN_URL` or `WEB_RETURN_PATH`) when `returnUrl` is null, so the Knowledgebase branch at `:162-170` is a special case of it.
  - `CallbackOutcome` (`service.ts:57-61`, `{ status, returnTo }`) is a strict subset of `ProfileCallbackOutcome` (`profile.ts:159-167`).
- **Problem**: The callback is the one route where a mistake (a missing `no-store`, a redirect that leaks a code, a wrong status) matters most, and it is written twice with two page functions and two target computations that must be kept in step by hand. A third profile-scoped OAuth provider adds nothing; a change to the callback policy is two edits.
- **Proposed change**: One `createConnectionCallbackHandler({ provider, label, gate?, complete })` in `routes.ts` used by both: the Knowledgebase mount passes `gate: options.cloud` and `complete: q => runtime.connections.complete(q)`; `AccountConnections.complete` returns the full `ProfileCallbackOutcome` shape (the three extra fields null). One `completionPage(label, status)`. `createConnectionsPublicRouter` keeps the client-metadata route and mounts the shared handler at `CALLBACK_PATH`.
- **Sequenced steps**: 1. Widen `CallbackOutcome` to the profile shape in `service.ts` (additive; the two callers in `routes.ts` ignore the new fields). 2. Add the `gate` option and the label to the profile handler, mount it for Knowledgebase, delete the inline handler and `completionPage`. 3. Rename `profileCompletionPage` → `completionPage`.
- **Contract impact**: None. Redirect URLs, query parameters, status codes, and page text are unchanged for both providers.
- **Risk**: Low. `connections.postgres-conformance.test.ts` builds an Express app around the public router and asserts the callback's redirect and status for every outcome; `github-connections.postgres-conformance.test.ts` does the same for the profile handler. `yarn test:backend`.
