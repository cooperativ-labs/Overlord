## Summary

Backend absorbed 35 contract versions of feature work in the seven days since the last review —
Run Queue phase work, the Latch v2 legacy-integration removal, objective cross-resource
parallelism, workspace authorization hardening, project status CRUD, `searchMissionsV3`, and

lead finding.

That lead finding is the same shape as F4, on a different file: `backend/protocol.ts` grew by
930 lines in one week — almost entirely the eleven-function Run Queue protocol-adapter cluster
(`queueObjectiveFromProtocol`, `dequeueObjectiveFromProtocol`, the four `*RunQueueFromProtocol`
CRUD handlers, `reorderProjectRunQueuesFromProtocol`, and their shared address-resolution
helpers) — and it is now the single largest contributor to backend's "files over 800 lines"
table growth this cycle. It is a clean, low-coupling extraction candidate by the same test the
last review applied to Latch: minimal shared state with the rest of the file, contiguous in both
the helper-function section and the `handlers`/`SUBCOMMAND_PERMISSIONS` maps.

The other finding worth landing is smaller but sharper: `backend/repository.ts` and
`packages/core/service/missions.ts` each export a function named `searchMissionsV2` (and
`searchMissionsV3`) with materially different signatures — one takes `projectIds: string[]` and
does ambient cross-workspace fan-out, the other takes `projectId: string` and a resolved `ctx`
for a single workspace. `backend/protocol.ts` already has to alias-on-import to tell them apart
(`searchMissionsV2 as searchMissionsAcrossWorkspaces`), which is itself evidence the shared name
is a hazard, not a coincidence.

## Findings

### F1. Run Queue protocol-adapter cluster is a clean extraction seam out of `backend/protocol.ts`
- **Value / Effort**: High / M
- **Dimension**: Module size and cohesion
- **Evidence**:
  - Helper-function cluster: `backend/protocol.ts:867-1169` — `oneBasedQueuePosition` (:867), `queueByRef` (:876), `runQueueProjectIdFromProtocol` (:888), `reorderRunQueueFromProtocol` (:916), `addressedRunQueue` (:965), `createRunQueueFromProtocol` (:976), `updateRunQueueFromProtocol` (:989), `deleteRunQueueFromProtocol` (:1012), `reorderProjectRunQueuesFromProtocol` (:1025), `queueObjectiveFromProtocol` (:1048), `dequeueObjectiveFromProtocol` (:1151-1169) — all added this cycle (contract v100-v103 Run Queue phase work), contiguous, ~300 lines.
  - `handlers` map entries: `backend/protocol.ts:1561-1584` — `'queue-objective'`, `'dequeue-objective'`, `'reorder-run-queue'`, `'create-run-queue'`, `'update-run-queue'`, `'delete-run-queue'`, `'reorder-project-run-queues'`, `'run-queue'` — also contiguous, immediately after the `reorder-future-objectives` entry and before `connect`.
  - `SUBCOMMAND_PERMISSIONS` map entries: `backend/protocol.ts:1909-1919`, with the explanatory comment at `:1912-1914` ("Queue definitions are project configuration, matching the REST mapping in `backend/run-queue.ts`... these four are full-token operations by design") — also contiguous.
  - Coupling check: every Run Queue helper's actual persistence call goes to `packages/core/service/run-queue.ts` (`listProjectRunQueues`, `reorderRunQueue`, `removeRunQueueEntry`, `createRunQueue`, `updateRunQueue`, `deleteRunQueue`, `reorderProjectRunQueues`, `enqueueRunQueueEntry`, `moveRunQueueEntry`) — the same module `backend/run-queue.ts` (the REST-side sibling) already imports from, confirming no duplication was introduced alongside the size growth.
  - Cross-cluster dependencies that would need importing rather than hoisting: `resolveObjectiveRef`, `resolveProjectId`, `resolveMissionId` (all already imported into `protocol.ts` from `packages/core/service/*`, not locally defined — a new file can import them directly, no hoist needed) and `ApiError` (`backend/protocol.ts:68`, from `./errors.ts` — likewise a direct import). The only local-to-`protocol.ts` dependencies are the flag parsers `strFlag`, `requireFlag`, `intFlag`, `csvFlag` (`backend/protocol.ts:345-724`, none currently exported) and the `ProtocolRequestBody` type (`:97`, already exported).
- **Problem**: `backend/protocol.ts` grew +930 lines in seven days, more than double any single file's growth in either of the last two review cycles, and the Run Queue cluster accounts for nearly all of it. The cluster has essentially no remaining coupling to the file's other responsibility groups (session lifecycle, mission creation/discovery, shared context, auth/discovery) beyond the generic flag-parsing helpers every handler uses — the same "near-zero coupling, contiguous in both the function section and the dispatch map" shape the previous review used to justify extracting the Latch cluster from `execution/launch.ts` (that review's F4, now landed). Left in place, `protocol.ts` keeps growing at the same rate every time Run Queue work lands in the same reading unit as unrelated mission/session handlers, at zero cohesion benefit.
- **Proposed change**: Export `strFlag`, `requireFlag`, `intFlag`, and `csvFlag` from `backend/protocol.ts` (or hoist them to a small shared `backend/protocol/flags.ts`, mirroring how `parseMetadataJson`/`asRecord` were hoisted for the Latch extraction). Move the eleven Run Queue helper functions plus their eight `handlers` entries and eight `SUBCOMMAND_PERMISSIONS` entries into a new `backend/protocol/run-queue.ts`, exporting a `runQueueHandlers` and `runQueueSubcommandPermissions` object that `protocol.ts` spreads into its own `handlers`/`SUBCOMMAND_PERMISSIONS` maps.
- **Sequenced steps**:
  1. Export `strFlag`, `requireFlag`, `intFlag`, `csvFlag` from `backend/protocol.ts` (no behavior change, zero new imports needed yet) — a self-contained first commit.
  2. Create `backend/protocol/run-queue.ts`, moving the eleven functions at `:867-1169` into it verbatim, importing `strFlag`/`requireFlag`/`intFlag`/`csvFlag`/`ProtocolRequestBody` from `../protocol.ts` and `resolveObjectiveRef`/`resolveProjectId`/`resolveMissionId`/the `packages/core/service/run-queue.ts` functions/`ApiError` from their existing locations.
  3. Move the eight `handlers` entries (`:1561-1584`) into an exported `runQueueHandlers: Record<string, Handler>` in the new file; move the eight `SUBCOMMAND_PERMISSIONS` entries (`:1909-1919`, keeping the explanatory comment) into an exported `runQueueSubcommandPermissions`.
  4. In `backend/protocol.ts`, replace the moved `handlers`/`SUBCOMMAND_PERMISSIONS` entries with `...runQueueHandlers` / `...runQueueSubcommandPermissions` spreads, and delete the now-unused local function definitions.
- **Contract impact**: None — pure file move, no signature or behavior change to any of the eleven functions or eight subcommands. `protocol-run-queue.test.ts` and `run-queue-mission-scope.test.ts` exercise behavior through the subcommand dispatch, not the file layout, so they should pass unchanged.
- **Risk**: Low. The main risk is an incomplete move leaving a stale duplicate definition (caught immediately by TypeScript's duplicate-export error) or a missed import (caught by `yarn typecheck:backend`). Run `yarn typecheck:backend` after step 2 before touching the maps in step 3, then `yarn test:backend` (specifically `protocol-run-queue.test.ts`, `run-queue-mission-scope.test.ts`) after step 4.

### F2. `searchMissionsV2`/`searchMissionsV3` name two different-shaped functions across layers, forcing disambiguation at every import site
- **Value / Effort**: Medium / S
- **Dimension**: Types and contracts; Abstraction fit
- **Evidence**:
  - `backend/repository.ts:3953` — `searchMissionsV2({ query, projectIds, statusTypes, resourceKeys, dateField, from, to, limit })`: no `ctx` parameter, resolves workspace scope itself from ambient request context (`requireDatabaseClient()`, `callerAuthorizedWorkspaceScopes`), fans out across every authorized workspace when `projectIds.length !== 1` (cross-workspace aggregate search). Same shape for `searchMissionsV3` at `:4019`.
  - `packages/core/service/missions.ts:928` — `searchMissionsV2({ ctx: ServiceContext, query, statusTypes, projectId, resourceKeys, dateField, from, to, limit })`: singular `projectId`, requires a resolved `ctx` for exactly one workspace, delegates to `searchMissionsWorkspace`. Same shape for `searchMissionsV3` at `:962`.
  - `backend/protocol.ts:82-83` — `searchMissionsV2 as searchMissionsAcrossWorkspaces, searchMissionsV3 as searchMissionsV3AcrossWorkspaces` — the import is forced to alias both names to disambiguate from the (also imported, unaliased) `searchMissions` from core at `:41`; the chosen alias, `searchMissionsAcrossWorkspaces`, is the accurately descriptive name that `repository.ts`'s function does not itself carry.
  - `backend/index.ts:215` imports `searchMissionsV2` directly from `repository.ts` (no alias needed there only because `index.ts` does not separately import core's version).
  - `webapp/web/lib/api.ts:536` names its client SDK method `searchMissionsV2` — this one is a REST-endpoint-facing name, not affected by an internal rename.
- **Problem**: Two functions with the same name and version suffix but different parameter shapes (`projectIds: string[]` ambient-scoped vs. `projectId: string` + explicit `ctx`) live one import away from each other in the same request path (`backend/protocol.ts` imports both). Today `protocol.ts` catches the collision by aliasing on import, but that only works because whoever wrote that import noticed the clash; `index.ts` imports only one of the two and would silently compile a wrong-shape call if a future edit added the other import without the same care. The identical version suffix (`V2`/`V3` on both) also wrongly suggests these are the same endpoint's revision history rather than two different scopes of the same underlying search.
- **Proposed change**: Rename `backend/repository.ts`'s `searchMissionsV2`/`searchMissionsV3` to `searchMissionsAcrossWorkspacesV2`/`searchMissionsAcrossWorkspacesV3` — adopting the name `protocol.ts` already had to invent as an import alias — and drop that alias at the one import site that needed it.
- **Sequenced steps**:
  1. Rename the two function declarations in `backend/repository.ts` (`:3953`, `:4019`) and their internal self-references, if any.
  2. Update the two import/call sites: `backend/index.ts:215` (and its call site at `:1742`) and `backend/protocol.ts:82-83` (drop the `as searchMissionsAcrossWorkspaces` alias since the import now already reads that way; keep the two call sites at `:1611`, `:1632` referring to the same local names, now unaliased).
  3. Run `yarn typecheck:backend` to confirm no remaining reference to the old names.
- **Contract impact**: None — this is an internal function name only; the REST route and its `searchMissionsV2`/`searchMissionsV3` response shape (and the webapp SDK method name that mirrors the route, not the backend internal) are untouched.
- **Risk**: Low. Purely mechanical rename with two call sites; `yarn typecheck:backend` catches any miss immediately. `backend/repository.searchMissionsV2.test.ts`-style tests (if present) should be checked for hardcoded import names.

### F3. Dead export `getResolvedWorkspaceId` in `backend/db.ts`
- **Value / Effort**: Low / S
- **Dimension**: Dead and vestigial code
- **Evidence**: `backend/db.ts:387-389` — `export function getResolvedWorkspaceId(): string | null { return requestContext().resolvedWorkspaceId; }`. Repo-wide search (`backend`, `packages`, `webapp`, `cli`, `mcp`, `connectors`, `auth`, `automations`, `scripts`) finds exactly one occurrence of the identifier in the entire tree: the declaration itself. Its paired setter, `setResolvedWorkspaceId` (`:392`), is actively called elsewhere and is not implicated. Introduced in commit `2b3e80c` ("workspace authorization handling", contract v95) and never called in the 26 contract versions since.
- **Problem**: An exported, unreferenced ambient-context getter sitting next to actively-used workspace-scoping infrastructure is exactly the kind of thing a future reader assumes is load-bearing (it reads a value something else sets) and hesitates to touch. It is not in `scripts/check-workspace-scoping.mjs`'s allowlist, so it carries no special scoping sanction either — it is simply unused.
- **Proposed change**: Delete `getResolvedWorkspaceId` from `backend/db.ts`.
- **Sequenced steps**: 1. Delete the function. 2. Run `yarn typecheck:backend` to confirm nothing referenced it via a dynamic import or re-export this search would miss.
- **Contract impact**: None — not part of any stable interface.
- **Risk**: None found; `yarn typecheck:backend` is sufficient verification for a single dead export.

New this cycle:

A full per-route audit of whether each omission is correctly scoped by its service function is real work, but it is a `code-review`/`security-audit` question (is this specific route's authorization correct?), not a refactor-shape question, and the pattern itself is not decaying.
