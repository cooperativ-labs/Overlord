## Summary
The area is in reasonable shape: the API boundary is clean, query keys are centralized, and the
hook-location split from the last known baseline is resolved. The two live problems are size,
not leakage. `InboxMissionCard.tsx` carries two ~230-line components
(`UnassignedInboxMissionCard`, `PromotedInboxMissionCard`) that duplicate the same
data-fetching/selection/submit orchestration with small, already-drifted differences — this is
the highest-value refactor available, and it currently has zero test coverage of its own.
`queries.ts` has grown to 2,130 lines and 165 exported hooks in one module; it is still a single
well-factored list (no logic duplication within it), so splitting it is real but lower-urgency
tidiness work. `api.ts` (966 lines) and `MissionBranchControl.tsx` (1,023 lines) are also over
800 lines but are each single-responsibility with a clear reading order, so no split is proposed
for either.

## Findings

### F1. Extract the shared Inbox-card state hook out of the two duplicated card components
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence (also container/presentation split)
- **Evidence**: `webapp/web/components/InboxMissionCard.tsx:76-321` (`UnassignedInboxMissionCard`)
  and `webapp/web/components/InboxMissionCard.tsx:323-549` (`PromotedInboxMissionCard`)
- **Problem**: Both components independently call the same seven hooks in the same order
  (`useAllProjects`, `useAccessibleWorkspaces`, `useAgentCatalog`, `useLaunchPreference`,
  `useProjectResources`, `useProjectExecutionTarget`, `useUpdateLaunchPreference`, plus
  `useLaunchSettings`), build the same `projectGroups`/`showWorkspaceGroups` derivation
  (`:113-120` vs. `:356-363`, byte-identical), the same `defaultSelection` fallback chain
  (`:136-149` vs. `:382-402`, diverging only in an extra `objective.assignedAgent` branch), the
  same resync-on-change `useEffect` (`:155-158` vs. `:408-411`), and the same
  `canSubmit`/`canRun` gating (`:172-178` vs. `:424-426`). The two `submit()` bodies
  (`:188-264` vs. `:428-489`) have already drifted: the unassigned path does
  `persistInboxText` → `promote` → conditional `updateObjective`, while the promoted path folds
  `instructionText`/`resourceKey` into one `updateObjective` call — a real behavioral divergence
  hidden inside ~250 lines of otherwise-identical scaffolding, which is exactly the shape that
  produces a bug when only one copy gets fixed. Neither component has a test file today
  (`grep -rl InboxMissionCard webapp/web --include='*.test.*'` returns nothing), so the
  duplication is currently unguarded.
- **Proposed change**: Extract a `useInboxCardState(missionOrItem)`-style hook (new file, e.g.
  `webapp/web/components/inbox-mission-card/use-inbox-card-state.ts`) that owns the shared
  queries, `projectGroups`, `defaultSelection`, `selection`/`explicitLaunchConfigs` state and
  their resync effect, and the `primaryConnection`/`targetAvailability`/`canSubmit`/`canRun`
  derivations. Leave `submit()`/`handleDelete()` — the genuinely divergent orchestration — in
  each component, built on top of the hook's returned state and setters. `InboxCardShell` stays
  as is; it already isolates presentation.
- **Sequenced steps**:
  1. Add characterization tests for both existing components' current behavior (submit/save/run
     flows, resync-on-prop-change) — this file has none today, and Standing Rule "behavior
     preserving" needs something to preserve against.
  2. Extract the shared hook with the two components as its only two call sites; no behavior
     change, verified against the new tests.
  3. Wire `UnassignedInboxMissionCard` and `PromotedInboxMissionCard` to call the hook and keep
     only their distinct `submit`/`handleDelete` bodies.
  4. Re-run the characterization tests plus `yarn typecheck:webapp` and `yarn test:webapp`.
- **Contract impact**: None — internal SPA restructuring only, no REST/DTO/query-key shape
  change.
- **Risk**: The `defaultSelection` divergence (the `objective.assignedAgent` branch in the
  promoted variant) is the one behavior the extraction must preserve exactly — a test asserting
  that a promoted mission with an assigned agent pre-selects it, and that an unassigned item
  falls back to the catalog default, is the concrete regression to guard. `MissionBranchControl`
  and other consumers of `InboxCardShell`'s prop surface are unaffected since that component does
  not change.

### F2. Split `queries.ts` into per-resource-family modules
- **Value / Effort**: Medium / L
- **Dimension**: Module size and cohesion
- **Evidence**: `webapp/web/lib/queries.ts` (2,130 lines, 165 exported hooks — counted via
  `grep -c "^export function use\|^export const use"`)
- **Problem**: One module holds every query/mutation hook for the app. The file is not
  internally duplicated or tangled — reading it top to bottom, it runs in clean, contiguous
  resource blocks (profile/account `:838-932`, organizations `:932-1003`, user-tokens
  `:1003-1036`, webhooks `:1036-1087`, workspaces `:1087-1167`, projects `:1167-1360`, missions
  including inbox/schedule/worktree actions `:1360-1727`, objectives `:1727-1806`,
  agent-launch-config `:1806-1958`, Everhour integration `:1958-2130`) — but at 2,130 lines it is
  the single largest file in the area and every unrelated feature change touches the same file,
  which maximizes merge-conflict surface and makes the module boundary invisible to `git blame`
  and review tooling.
- **Proposed change**: Split along the resource-family boundaries already visible in the file
  (the ten blocks above), each into its own module under `webapp/web/lib/queries/` (e.g.
  `queries/missions.ts`, `queries/projects.ts`, `queries/webhooks.ts`, …), re-exported from a
  thin `webapp/web/lib/queries.ts` barrel so existing `import { useX } from '../lib/queries'`
  call sites across the app are unaffected. `keys` (already extracted to `query-keys.ts`) and the
  shared `api` client stay as the common imports each module pulls from.
- **Sequenced steps**:
  1. Move the Everhour block (`:1958-2130`, self-contained, lowest fan-in) to
     `queries/everhour.ts` and re-export from the barrel; confirm `yarn typecheck:webapp` and
     `yarn test:webapp` are unaffected.
  2. Move webhooks, user-tokens, organizations (small, low fan-in) the same way.
  3. Move workspaces, objectives, agent-launch-config.
  4. Move projects, missions (largest, highest fan-in — do these last so the pattern is proven
     first).
  5. Reduce `queries.ts` to the barrel re-export, or remove it and update imports directly if the
     team prefers explicit per-module imports (a separate, larger follow-up — not required by
     this finding).
- **Contract impact**: None — pure module reorganization, no hook signature, query-key, or DTO
  change.
- **Risk**: `realtime-invalidation.ts` and `query-invalidation.ts` import `keys` (already
  separate) rather than anything from `queries.ts`, so the split does not touch invalidation
  matching. The main risk is import-cycle regressions from splitting a file that some hooks
  within it call into each other (e.g. mutations that read another hook's query key) — the
  existing `realtime-invalidation.test.ts` and `yarn webapp:build:prod` (which the playbook notes
  catches import-cycle regressions) are the checks that would catch this, and should run after
  each step above, not just at the end.

## Explicitly not recommended
- **Splitting `api.ts` (966 lines).** It is a flat, mechanical 1:1 mapping of REST endpoints to
  thin `request(...)` wrappers with no branching logic or state — the size comes from breadth
  (211 methods), not from tangled responsibilities. Splitting it would multiply import
  boilerplate across ~all of `queries.ts` for no reduction in duplication or cognitive load.
  Low value / L effort (every call site's import would need updating) — leave it alone unless
  it starts acquiring per-domain logic beyond thin wrappers.
- **Splitting `MissionBranchControl.tsx` (1,023 lines).** It reads as one cohesive
  responsibility (branch UI) in a clear top-to-bottom order: small presentational helpers
  (`CopyIconButton`, `BranchCopyMenu`, `BranchModeToggle`, `BranchIdentity`) → the setup form
  (`MissionBranchSetupForm`) → error formatting (`describeBranchError`) → the stateful panel
  (`BranchPanel`) → the exported `MissionBranchControl` wrapper. Only 4 `useState` and 1
  `useEffect` in the whole file, no duplicated logic. Length alone is not a finding here.
- **`WebhooksPage.tsx` (816 lines).** Already split into `WebhookSubscriptionRow`,
  `WebhookDialog`, `CopyField`, `DeliveryLogSheet` within the file; each sub-component owns a
  distinct piece of the CRUD screen. A cross-file split is possible but Low value for the
  clarity gained — not worth the churn this run.
