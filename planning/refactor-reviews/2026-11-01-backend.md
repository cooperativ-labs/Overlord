## Summary

The backend is in the best structural shape the rotation has recorded: all seven previous
findings landed within two days of the report, the over-800-line file count fell, and the
cycle's one feature (v168 Inbox attachments) was built in the sanctioned shape — raw-body routes,
resource-scoped authorization, a conformance-style test from day one. What the feature left
behind is concentrated in one module. `backend/storage.ts` grew by half in a single commit
because the Inbox flow was written as a second copy of the objective-attachment flow inside the
same file, and the two copies have already diverged (only the new one compensates for a failed
metadata write). Around it, the `storage_buckets` row shape and the remote-object cleanup policy
are each declared in three modules, the closed bucket-key vocabulary is spread across three
parallel registries plus string branches, and the three storage test suites each stand up their
own fake S3. Separately, the core storage service that `backend/AGENTS.md` says the REST layer
should be calling has **zero** production callers and had to be edited by v168 anyway. The single
highest-value refactor is **F1**: decide that module's fate — delete it — so the backend's
storage ownership is documented where it actually is. **F2** (shared attachment primitives, then
move the Inbox owner out) is the structural fix for the growth.

## Findings

### F1. Retire the unused core storage service and record `backend/storage.ts` as the storage owner
- **Value / Effort**: High / S
- **Dimension**: Dead and vestigial code; Abstraction fit (excess); Layering and boundary leaks
- **Evidence**:
  - `packages/core/service/storage.ts:1-733` exports `listStorageBuckets`,
    `create/list/update/deleteWorkspaceImage`, `create/list/update/deleteUserImage`, and
    `create/list/update/deleteAttachment`. A repo-wide search for the module specifier
    (`service/storage`) across `backend`, `cli`, `mcp`, `connectors`, `desktop`, `scripts`,
    `packages`, `webapp` finds one importer: its own `storage.test.ts` (211 lines).
  - Every production write to `user_images`, `workspace_images`, and `attachments` is in the
    backend: `backend/storage.ts:241-296` (user image), `:313-368` (workspace image),
    `:532-597` (objective attachment), `:826-865` (inbox attachment), plus the tombstones at
    `:650-656`, `:923-929` and the re-point at `:1083-1127`. The only core read that is used is
    the *other* `listAttachments` in `packages/core/service/missions.ts:1524-1560`, consumed by
    `backend/protocol/artifacts.ts:113,130` and `packages/core/service/protocol.ts:586`.
  - The unused service nevertheless had to change in v168: `inbox_item_id IS NULL` filters were
    added at `packages/core/service/storage.ts:625,667,678,712,723` to keep it "correct"
    (`11068ab`, 14 lines). Its last substantive commit before that was `c37f763` (2026-09-27).
  - Two `AttachmentSummary` types exist in core with different field names:
    `missions.ts:94-101` (`mimeType`, `status`) and `storage.ts:53-62` (`contentType`,
    `uploadStatus`, `checksumSha256`, `revision`).
  - The service's authorization (`loadRoles` over `role_assignments` keyed on
    `ctx.workspace.id`, `storage.ts:86-110`) is the ambient-workspace model that contract v95
    retired for production reads; the backend path authorizes against the *resource's* workspace
    (`requireWorkspacePermission`, `backend/storage.ts:433-438,1303-1307`), which the playbook's
    RBAC paragraph names as the required path for resources that may belong to a workspace
    other than the caller's active one.
  - `backend/AGENTS.md` ("Temporary deviation") says direct-table writers should move onto the
    shared service layer "as those areas are touched"; v168 touched this area and added a third
    direct writer instead, because the service it would have called cannot express profile-owned,
    workspace-less rows.
- **Problem**: The backend carries 733 lines of a parallel implementation that nobody calls, that
  must be edited whenever the `attachments` schema changes, and whose authorization model is the
  one the contract retired. The documentation points at it as the sanctioned home while the code
  has settled the opposite way for five weeks. Both halves cost something: readers of
  `AGENTS.md` look for a service that is not wired, and readers of the service assume it is the
  owner. Porting the backend writers onto it is not a refactor — it would reintroduce
  ambient-workspace authorization — so the honest resolution is deletion, with the deviation note
  updated to say where storage persistence lives and what a future core service would need
  (resource-scoped authorization, profile-owned rows) before a second surface adopts it.
- **Proposed change**: Delete `packages/core/service/storage.ts` and
  `packages/core/service/storage.test.ts`. Keep `missions.ts#listAttachments` as the single core
  attachment read (protocol's only need). Update the `backend/AGENTS.md` deviation paragraph and
  the file-placement list to name `backend/storage.ts` (bytes, buckets, images, attachments,
  serve path) as the storage owner, and state the preconditions for a core storage service.
  No runtime change.
- **Sequenced steps**:
  1. Confirm with `yarn typecheck` (all workspaces) that nothing resolves the module; delete the
     two files.
  2. Update `backend/AGENTS.md` (deviation note + file-placement convention) and
     `packages/core/AGENTS.md` if it lists the service.
- **Contract impact**: None to any stable interface. `CONTRACT.md` does not name the core
  storage functions (searched: `createAttachment`, `listStorageBuckets`, "core upload service"
  appears only as the REST `/uploads` description at `:3244`). The REST → Database rule ("REST
  handlers call the service layer") is already documented as deviated for this area; this
  finding changes the deviation note, not the rule.
- **Risk**: Negligible. `yarn typecheck`, `yarn test:core` (the deleted test is the only
  consumer), `yarn test:backend`.
