## Summary

The backend grew by roughly 15k lines in six weeks, all of it explained by shipped contract work
(v85→v151), and the three prior reports' remediations have all landed, so the area is not
accumulating the debt it was two cycles ago. The two structural problems that remain are the same
species as the last two cycles' top findings — a rule implemented once per surface instead of once
in `packages/core/service/` — now showing up on two newer entities: mission-search parameter
parsing (three REST routes, one Protocol handler, and MCP each parse and validate the same eleven
parameters, and only REST validates `dateField`) and the Run Queue entry state machine (the
dispatch worker and the core service both write `run_queue_entries.state` transitions by hand,
with an already-divergent guard on the objective reset). The single highest-value refactor is
**F2**: moving the six Run Queue entry transitions into `packages/core/service/run-queue.ts`, which
gives the four-state machine the contract lists at `CONTRACT.md:2112` one owner. Below those,
`protocol.ts` crossed 800 lines with a real import cycle against its own `protocol/run-queue.ts`
extraction, and the test suite still carries two bootstrap idioms — both are prerequisites for
doing the bigger refactors safely.

## Findings

### F1. Parse and validate mission-search parameters once, in core, for REST, Protocol, and MCP
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Layering and boundary leaks
- **Evidence**:
  - `backend/index.ts:1701-1727` (`GET /api/missions/search`), `:1727-1791` (`GET /api/missions/search/v2`), `:1791-1863` (`GET /api/search/v3`) — three inline handlers that each re-parse `q`, `limit`, `statusTypes`, `projectIds`/`projectId`, `resourceKeys`/`resourceKey`, `dateField`, `from`, `to`; v2 and v3 both declare the same `uuidRe` literal (`:1753`, `:1818`) and the same `dateField` validation (`:1767-1775`, `:1832-1840`); v3 introduces a local `csv` helper (`:1794-1800`) that v2 open-codes four times.
  - `backend/protocol.ts:1350-1397` (`search-missions`) — parses the same parameters from flags and forwards `dateField` with an unchecked cast (`strFlag(body, '--date-field') as MissionSearchDateField | undefined`, `:1357`); no UUID check on `--project-id`.
  - `mcp/server.ts:362-363` forwards `dateField` to the Protocol handler verbatim; `mcp/tool-catalog.ts:173` documents it as a free string.
  - `packages/core/service/mission-search.ts` already owns `normalizeSearchV3Options` (`:950`) and the V2/V3 merge/allocation helpers, so the natural home exists.
  - Contract text: `CONTRACT.md` REST API → Database surface — "same service layer as CLI and Protocol"; and the backend playbook's explicit rule that business rules implemented in the route layer are what causes surface drift.
- **Problem**: An invalid `dateField` is a clean 400 on REST and silently reaches the search SQL on Protocol/MCP; a non-UUID `projectIds` entry is a 400 on REST v2/v3 and accepted on Protocol. Every search parameter added since v2 (`entityTypes`, `objectiveStates`, `matchesPerResult`) was added in three places. The next parameter will be too.
- **Proposed change**: Add `parseMissionSearchOptions(raw: Record<string, string | undefined>, { version: 1 | 2 | 3 })` to `packages/core/service/mission-search.ts`, returning the typed options object `searchMissionsAcrossWorkspacesV2/V3` already accept and throwing `ServiceError(…, 400)` for the validation REST performs today (closed `dateField` set, UUID-only `projectIds`, CSV splitting with trim/empty filtering, integer `limit`/`matchesPerResult`). REST handlers map `req.query` to that record; the Protocol handler maps flags to it. The `MissionSearchDateField` closed set is imported from `@overlord/contract` rather than re-typed as a literal chain.
- **Sequenced steps**:
  1. Add `parseMissionSearchOptions` to `packages/core/service/mission-search.ts` with unit tests mirroring the exact REST behaviors today (including the v2 vs v3 error strings). Zero call-site changes.
  2. Switch `GET /api/search/v3` to it; run `backend/search-v3.test.ts`.
  3. Switch `GET /api/missions/search/v2` and `GET /api/missions/search`; delete the two `uuidRe` literals and the local `csv` helper.
  4. Switch `protocol.ts` `search-missions` to it, adding characterization tests that an invalid `--date-field` now returns the same 400-class error REST returns (the only observable change, and it is a rejection of input that today produces an undefined SQL comparison).
- **Contract impact**: None to any path, flag, or response shape. Step 4 rejects an invalid `dateField` on Protocol/MCP that is currently accepted; that is the REST behavior already documented for the same parameter, not a new rule.
- **Risk**: The v2/v3 handlers differ in one detail (`resourceKeys` empty-filter uses `.filter(Boolean)` in v2 and `!== ''` in v3 — same result for strings, but the shared function must pick one and the tests must pin it). `backend/search-v3.test.ts`, `backend/mission-search*.test.ts`, and `packages/core/service/mission-search*.test.ts` cover the read paths; `yarn test:core` is required.

### F2. Give Run Queue entry state transitions one owner in `packages/core/service/run-queue.ts`
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Abstraction fit (missing)
- **Evidence**:
  - `backend/run-queue-dispatch-worker.ts:193` (`drop` → `deleted_at`), `:211` (`wait`), `:226` (`block`), `:234` (`mark_running`), `:299` (`dispatched`), `:318` (`retry_pending` after a failed dispatch) — six hand-written `UPDATE run_queue_entries SET state = …` statements applying the pure plan from `planRunQueueDispatch` (`@overlord/automations`).
  - `packages/core/service/run-queue.ts:1180` (`moveRunQueueEntry` → `state = 'waiting'`), `:1229-1240` (`retryRunQueueEntry` → `state = 'waiting', waiting_reason = 'retry_pending', attempt_count = 0`) — the same column set written independently, with a different clearing list (`execution_request_id = NULL` here, absent from the worker's `:318` retry-pending write).
  - Objective reset divergence: the worker resets a wedged `launching` objective to `draft` only when no active `execution_requests` row exists (`:257-268`, guarded by `ACTIVE_EXECUTION_REQUEST_STATUSES`); `removeRunQueueEntry`'s force path (`packages/core/service/run-queue.ts:977-982`) performs the same reset with no such guard.
  - `CONTRACT.md:2112` lists `run_queue_entries.state` as a closed four-value set; `CONTRACT.md:1873` sanctions a backend dispatcher that "resolves target/config at dispatch and creates an ordinary `execution_request`" — the orchestration belongs in the worker, the row-state rules do not.
  - `backend/run-queue.ts` (the REST sibling, 158 lines) already calls only core for every user-initiated transition, so the worker is the one remaining direct writer.
- **Problem**: A four-state machine with `waiting_reason`/`blocked_reason`/`waiting_on_objective_id`/`execution_request_id`/`attempt_count` invariants is maintained in two files by hand. The retry-pending write already differs between them. The next change to what a hold must clear has to be found and made twice, and the Postgres conformance suite only exercises the core copy.
- **Proposed change**: Add transition functions to `packages/core/service/run-queue.ts`, each taking `(db | tx, entryId, now, …)` and owning its column set: `dropRunQueueEntry`, `holdRunQueueEntry({ reason, waitingOnObjectiveId, keepFailureDetail })`, `blockRunQueueEntry({ reason })`, `markRunQueueEntryRunning`, `markRunQueueEntryDispatched({ executionRequestId })`, `recordRunQueueDispatchFailure({ detail })`. Add `resetWedgedLaunchingObjective(tx, objectiveId, now)` carrying the worker's active-request guard, and have `removeRunQueueEntry`'s force path call it too. The worker keeps the planner call, the `entryHoldIsUnchanged` short-circuits, and the launch orchestration inside the transaction.
- **Sequenced steps**:
  1. Characterization tests first: extend `backend/run-queue-dispatch-worker.test.ts` (203 lines today) so every one of the six transitions is asserted on row state, including `retry_pending` keeping `blocked_reason` detail and `execution_request_id` handling.
  2. Add the six transition functions plus `resetWedgedLaunchingObjective` to core with the worker's SQL text moved verbatim; unit-test them in `packages/core`.
  3. Point the worker's six call sites at them; delete the inline SQL.
  4. Point `retryRunQueueEntry` and `moveRunQueueEntry` in core at the same functions, and `removeRunQueueEntry`'s force path at `resetWedgedLaunchingObjective`. This is the one step with a behavior decision: whether the force-path reset should honor the active-request guard. It should (an active request means the objective is not wedged); flag it in the PR as the intended divergence fix.
- **Contract impact**: None to any interface; the state vocabulary, REST family, and Protocol subcommands are unchanged.
- **Risk**: Both dialects. `run-queue-dispatch-worker.test.ts`, `protocol-run-queue.test.ts`, `run-queue-retry.test.ts`, `run-queue-mission-scope.test.ts`, and `workspace-isolation.postgres-conformance.test.ts` must pass; add a Postgres conformance case for the retry-pending write since it now runs through core.
