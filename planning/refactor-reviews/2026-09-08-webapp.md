## Summary

Webapp is in decent shape structurally: prior known hot spots (`queries.ts`, `ResourcesPage.tsx`,
duplicate hook directories) have already been fixed by ordinary feature work, boundary rules
(REST-only access, no raw `fetch` outside the transport layer, no inline Electron detection,
`navigator.clipboard` centralized) hold cleanly everywhere checked, and the SPA has no locally
redeclared DTO types. The area's remaining debt is concentrated in a small number of places: one
container component (`MissionBranchControl.tsx`) that mixes a branch-lifecycle state machine with
its own rendering and is completely untested; one REST client module (`lib/api.ts`) that has grown
into exactly the flat, undivided shape `queries.ts` was split out of, just on the request side
instead of the query side; one settings dialog with the same container/presentation mixing
problem at smaller scale; and a small amount of copy-pasted boilerplate in `lib/queries/`. The
highest-value single move is decomposing `MissionBranchControl.tsx`'s `BranchPanel`, but it
needs characterization tests first since none exist for a component that already has real
lifecycle-transition bugs risk (busy-branch confirmation, dirty-worktree gating).

## Findings

### F1. Decompose `BranchPanel` in `MissionBranchControl.tsx`
- **Value / Effort**: High / M
- **Dimension**: Module size and cohesion (with a Container/presentation split shape)
- **Evidence**: `webapp/web/components/MissionBranchControl.tsx:542-950` (`BranchPanel`, ~410
  lines); `:959-1023` (`MissionBranchControl`, the popover wrapper); the file totals 1,023 lines
  across 8 top-level functions with no internal file split.
- **Problem**: `BranchPanel` alone does four jobs in one function body: (1) reads six hooks and
  derives ~15 boolean visibility flags from `branch.status` (`canConfigureBranch`, `isMerged`,
  `showCommit`, `showIntegrate`, `showPushParent`, `showPublish`, `showCreatePr`, `gitUnavailable`,
  `hasActions`, …) — effectively an inline state machine over the branch lifecycle; (2) two
  action handlers (`runAction`, `handleAction`) with server-side busy-conflict recovery; (3) commit
  message drafting via a separate mutation; (4) ~290 lines of JSX consuming all of the above. There
  is no test file for this component (confirmed: no `*branch*.test.*` under `webapp/web`), so the
  status→visibility derivation is exercised only by manual QA today, and it is exactly the kind of
  logic (closed-set status transitions with several interacting flags) that regresses silently
  when a new branch status or action is added.
- **Proposed change**: Extract the derivation into a pure `useBranchPanelView(mission)` hook
  returning a typed view-state object (`{ status, showCommit, showIntegrate, showPushParent,
  showPublish, showCreatePr, gitUnavailable, hasActions, parent, prCommand, actionLabels }`), and
  a second `useBranchActions(mission)` hook wrapping `runAction`/`handleAction`/commit-message
  state. `BranchPanel` becomes a thin composition of the two hooks plus the existing JSX, split
  into the presentational sub-pieces it already has sitting next to it in the file
  (`BranchIdentity`, `MissionBranchSetupForm`, `BranchCopyMenu` are already separate — the gap is
  only `BranchPanel` itself). Do not change branch statuses, action names, or the busy-confirm
  protocol — this is a pure extraction.
- **Sequenced steps**:
  1. Add characterization tests against the current `BranchPanel` for each `branch.status` value
     crossed with `dirty`/`hasUnpushedCommits`/`executionRequests.length` — pin today's visibility
     flags and the busy-confirm flow before moving anything.
  2. Extract `useBranchPanelView` (pure derivation, no side effects) and swap `BranchPanel` to
     consume it; tests from step 1 must pass unchanged.
  3. Extract `useBranchActions` (the two mutations, `actionError`/`confirmAction`/`commitMessage`
     state); swap `BranchPanel` to consume it.
  4. Optional follow-up: move `BranchPanel` and its now-thin siblings into
     `MissionBranchControl/` as separate files once the hooks carry the logic, if the file is
     still judged too long to navigate.
- **Contract impact**: None. Purely internal to the SPA; no REST shape, DTO, or query key
  changes.
- **Risk**: Branch actions are one of the few flows with real backend side effects triggered from
  a small number of always-visible buttons, so an extraction that silently changes a visibility
  condition would either hide a valid action or expose an invalid one. Step 1's characterization
  tests are the mitigation and are not optional here — see also the Test structure note in the
  Summary.

### F2. Split `lib/api.ts` by resource family, mirroring the `lib/queries/` decomposition
- **Value / Effort**: Medium / M
- **Dimension**: Module size and cohesion / Duplication with divergence (structural, not logic)
- **Evidence**: `webapp/web/lib/api.ts` — 978 lines, a single `export const api = { … }` object
  (`:281-978`) with ~140 methods spanning organizations, profile, notifications, user-tokens,
  webhooks, workspaces, projects, project-statuses, project-tags, missions, objectives,
  execution-requests, agent-requests, Everhour, and GitHub, with only two section comments in the
  whole object (`:845`, `:895`). Compare `webapp/web/lib/queries.ts`'s prior shape (now split
  into `webapp/web/lib/queries/{missions,projects,organizations,workspaces,webhooks,everhour,
  github,run-queues,objectives,...}.ts`, 14 files, largest 660 lines) — `api.ts` is the same
  resource list, on the request side, that never got the same split.
- **Problem**: Every REST resource family's request-shape logic lives in one always-growing file
  (edited as recently as 2026-09-07 per `git log`), so an unrelated change to, say, the webhook
  endpoints requires reviewing a diff against an 978-line file, and it is the one place left in
  `lib/` whose size will keep compounding as new endpoints are added — the exact problem
  `queries.ts` already had and was fixed for.
- **Proposed change**: Split `api.ts` into `lib/api/<family>.ts` files matching the existing
  `lib/queries/` resource families (missions, projects, organizations, workspaces, webhooks,
  everhour, github, run-queues, objectives, agent-requests, user-tokens, profile), each exporting
  its slice of the `api` object; re-export a merged `api` object from `lib/api/index.ts` (or keep
  `lib/api.ts` as a thin barrel) so the ~140 existing call sites (`api.listMissions(...)`, etc.)
  need no changes. Move the shared `request`/`requestDownload`/`parseDownloadFilename` helpers to
  `lib/api/transport.ts` (distinct from the already-existing `api-transport.ts`, which owns
  `fetchApi`/auth — name accordingly to avoid confusion, e.g. `lib/api/request.ts`).
- **Sequenced steps**:
  1. Move `request`, `requestDownload`, `parseDownloadFilename`, and the local `Meta` type into
     `lib/api/request.ts`; re-export from `api.ts` so nothing else changes yet.
  2. Split the `api` object's methods into per-family files one family at a time (start with the
     already-clearly-bounded `everhour`/`github` sections since they have explicit comment
     dividers), each merged back via spread into the exported `api` object. Land as independent,
     reviewable PRs per family rather than one large move.
  3. Once all families are extracted, reduce `api.ts` to the merge barrel.
- **Contract impact**: None — `api.*` call signatures and behavior are unchanged; this is a pure
  file reorganization.
- **Risk**: Low. Mechanical move with no logic change; TypeScript will catch any missed export,
  and the ~140 call sites are typed against the same merged object either way. No new tests are
  needed beyond the type-check passing.

### F3. Split `WebhookDialog` out of `WebhooksPage.tsx`
- **Value / Effort**: Medium / S
- **Dimension**: Module size and cohesion (Container/presentation split)
- **Evidence**: `webapp/web/components/settings/WebhooksPage.tsx:373-699` — `WebhookDialog`,
  ~326 of the file's 816 lines, holding 8 `useState` hooks (`name`, `endpointUrl`, `projectId`,
  `eventTypes`, `payloadMode`, `saveState`, `error`, `revealedSecret`, `testResult`) that together
  cover three concerns: the create/edit form, the one-time secret-reveal flow after creation, and
  an inline "send test event" flow.
- **Problem**: The file already separates `WebhooksPage` (list/page), `WebhookSubscriptionRow`,
  `CopyField`, and `DeliveryLogSheet` into their own functions — the one piece that didn't get the
  same treatment is `WebhookDialog`, which is large enough (326 lines) and mixes concerns enough
  (form vs. secret-reveal vs. test-send) that it is the file's actual size driver.
- **Proposed change**: Extract a `useWebhookDialogForm(existing)` hook covering the form fields
  and save mutation, and a `useWebhookTestSend(subscriptionId)` hook for the test-event flow;
  keep `revealedSecret` display as a small presentational sub-component
  (`WebhookSecretReveal`) since it is a one-shot, non-reusable-elsewhere block. `WebhookDialog`
  itself becomes composition + layout only, following the same shape `WebhookSubscriptionRow`
  already uses.
- **Sequenced steps**:
  1. Extract `useWebhookDialogForm` (state + save mutation only); `WebhookDialog` consumes it,
     JSX unchanged.
  2. Extract `useWebhookTestSend`; wire into the existing test-button JSX.
  3. Pull the secret-reveal block into `WebhookSecretReveal` as a presentational component next to
     `CopyField`.
- **Contract impact**: None.
- **Risk**: Low-Medium. The secret-reveal path only fires once per subscription creation and has
  no test coverage today; add one characterization test for "create → secret shown once → dialog
  reopened shows no secret" before extracting, since that invariant is easy to lose silently in a
  hook split.

### F4. De-duplicate the `invalidateAll` wrapper across `lib/queries/`
- **Value / Effort**: Low / S
- **Dimension**: Duplication with divergence
- **Evidence**: Identical 3-line function repeated verbatim in seven files —
  `webapp/web/lib/queries/{missions,run-queues,objectives,workspaces,projects,organizations,
  agent-launch-config}.ts`, each: `function invalidateAll(qc: QueryClient) {
  invalidateNonEverhourQueries(qc); }`, called 2-13 times per file (51 call sites total).
- **Problem**: Seven copies of a function whose entire body is delegate-to-`invalidateNonEverhourQueries`
  (already imported by name in every one of those files). No drift yet, but it is the kind of
  boilerplate that invites a well-intentioned one-off change in a single file the next time
  someone needs slightly different invalidation there, at which point the seven copies silently
  diverge.
- **Proposed change**: Drop the seven local wrappers and import
  `invalidateNonEverhourQueries` directly under the local alias at the import site:
  `import { invalidateNonEverhourQueries as invalidateAll } from '../query-invalidation.ts';`.
  Call sites (`invalidateAll(qc)`) need no changes.
- **Sequenced steps**: One mechanical commit — replace the 3-line function declaration with the
  aliased import in each of the seven files. No behavior change, independently landable, or safe
  to land in a single small PR since it's the same edit repeated seven times.
- **Contract impact**: None.
- **Risk**: None beyond a missed reference, which `yarn typecheck:webapp` catches immediately.

### F5. Move `NOTIFICATION_CATALOG` out of `packages/core/service/` and into `packages/contract`
- **Value / Effort**: Medium / S
- **Dimension**: Types and contracts / Layering and boundary leaks
- **Evidence**: `webapp/web/components/notifications/NotificationRenderer.tsx:4`,
  `NotificationDrawer.tsx:4`, `settings/NotificationsPage.tsx:20`, and
  `lib/mission-status-catalog.ts:1` all import
  `NOTIFICATION_CATALOG`/`NotificationType`/etc. directly from
  `packages/core/service/notifications/catalog.ts` via a four-level relative path
  (`../../../../packages/core/service/notifications/catalog.ts`). `backend/push-notifications.ts`
  and `backend/notifications.ts` import the same module. `packages/contract/src/` already holds
  exactly this shape of thing (`launch-variables.ts`, `search.ts` — closed `as const` vocabularies
  with derived types) and is the package `webapp/AGENTS.md` names as the sanctioned source for
  SPA-facing shared types (`webapp/shared/contract.ts` re-exports `@overlord/contract`).
- **Problem**: `catalog.ts` is pure, side-effect-free declarative data (notification labels,
  icons, sounds, transports, mode defaults) — not service logic — so importing it isn't a
  DB-access violation, but it reaches four SPA files directly into `packages/core/service/`, a
  path documented as backend/protocol-service internals, via a raw relative path rather than
  through the one package (`@overlord/contract`) the SPA is documented to depend on. Nothing marks
  `catalog.ts` as client-safe, so a future change to anything else under
  `packages/core/service/notifications/` risks being bundled into the SPA by accident, and the
  boundary is invisible to anyone not reading these four import lines.
- **Proposed change**: Move `NOTIFICATION_TYPES`, `NotificationType`, `NOTIFICATION_MODES`,
  `NotificationMode`, `NOTIFICATION_TRANSPORTS`, `NotificationTransport`,
  `NotificationDescriptor`, and `NOTIFICATION_CATALOG` into `packages/contract/src/notifications.ts`,
  re-exported from `packages/contract/src/index.ts` (and from `webapp/shared/contract.ts`
  automatically via its `export *`). Re-export the same symbols from
  `packages/core/service/notifications/catalog.ts` for the two `backend/` importers and the
  package's own test, so this is a pure move plus a compatibility re-export rather than a
  multi-file rename in the same change.
- **Sequenced steps**:
  1. Move the catalog content to `packages/contract/src/notifications.ts`; add the export to
     `packages/contract/src/index.ts`.
  2. Turn `packages/core/service/notifications/catalog.ts` into
     `export * from '@overlord/contract'` (scoped to the notification symbols) so
     `backend/push-notifications.ts`, `backend/notifications.ts`, and
     `packages/core/service/notifications/catalog.test.ts` keep working unchanged.
  3. Update the four `webapp/web` import sites to `import { NOTIFICATION_CATALOG } from
     '@overlord/contract';` (or the `webapp/shared/contract.ts` shim), dropping the
     `packages/core` relative path.
  4. Optional follow-up (separate change, not part of this refactor): once nothing outside
     `packages/core` imports the old path directly, drop the compatibility re-export.
- **Contract impact**: None to the REST/DTO surface — this moves an internal source location, not
  a wire shape. Flagging for awareness since it touches `packages/contract`, which is also the
  `core` rotation area: if `core`'s own review disagrees with this placement, resolve there rather
  than in webapp.
- **Risk**: Low. Compatibility re-export keeps both `backend/` importers working during the move;
  `yarn typecheck` across workspaces catches any missed import.
