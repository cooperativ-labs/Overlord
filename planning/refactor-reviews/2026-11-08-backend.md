## Summary

The execution cluster is in sound shape at the boundary that matters most: every state
transition on `execution_requests`, the claim CAS, the launch-config resolution order, and the
Run Queue coupling already live in `packages/core/service/`, and `backend/execution/` is mostly
the REST adapter the contract asks for. What it is not is *one* adapter. The same objective read
path — resolve the ref, load the row, find the caller's membership in the objective's own
workspace, check a permission, 404 — is open-coded four times in `launch.ts` and a fifth time
for execution targets in `branching/`, while the shared `requireObjectivePermission` sits
private inside `repository.ts` and the inline copies skip two things the shared helper does
(the authorized-workspace snapshot check and `setResolvedWorkspaceId`). `launch.ts` itself holds
four unrelated owners (agent catalog CRUD, per-user launch settings, project launch preference,
execution requests and copyable commands) and still carries its own workspace-settings writer
beside `workspace-settings.ts`'s. Around the runner, the branch-prepared path re-implements the
core branch-observation upsert with a dialect-fragile boolean, the claim payload the CLI depends
on is `Record<string, unknown>` on both ends, and two closed vocabularies are re-typed by hand.
The single highest-value refactor is **F1**: one exported objective authorization helper in
`rbac.ts`, used by the four launch read paths — it removes the one real boundary inconsistency
this run found. **F2** (two extractions out of `launch.ts`) is the structural fix for the size.

## Findings

### F1. One objective-scoped authorization helper in `rbac.ts`, and one launch-resolution read for the command/effective-config pair
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Layering and boundary leaks
- **Evidence**:
  - `backend/execution/launch.ts:1310-1324` (`getObjectivePrompt`), `:1390-1404`
    (`getObjectiveEffectiveLaunchConfig`), `:1465-1479` (`getObjectiveLaunchCommand`), and
    `:1079-1089` (`launchObjective`, inside the transaction) each open-code the same sequence:
    `resolveObjectiveIdForRest` → `SELECT … FROM objectives` → `resolveActiveProfileId` →
    `findActiveMembershipId(row.workspace_id, …)` → `actorCan(PERMISSIONS.OBJECTIVE_READ |
    EXECUTION_REQUEST_CREATE, …)` → `throw new ApiError(404, 'Objective not found')`. The
    comment at `:1294-1298` says it is "mirroring `requireObjectivePermission` in repository.ts".
  - That helper exists — `backend/repository.ts:7067-7088` — and is private. It delegates to
    `requireWorkspacePermission` (`backend/rbac.ts:118-148`), which the inline copies do not:
    they bypass the `getAuthorizedWorkspacesContext()` snapshot check (`rbac.ts:128-137`), skip
    `setResolvedWorkspaceId` (`rbac.ts:138,146`), and return `404` where the shared helper
    returns `403` for a member who lacks the permission (`rbac.ts:144`; the convention is
    documented in the helper's doc comment at `:110-116`).
  - `backend/branching/execution-target-observation-scope.ts:12-35` is a fifth copy for
    execution targets, with an any-of over two permissions (`:31-32`) that `rbac.ts` has no
    signature for (`requireWorkspacePermission` takes one permission;
    `requireAnyWorkspacePermission` takes one permission over *any* workspace).
  - `rbac.ts` already exports the sibling resource-scoped gates `requireProjectPermission`
    (`:219`) and `requireMissionPermission` (`:245`); `objective-ref.ts` imports only `db.ts`,
    `errors.ts`, and core (`objective-ref.ts:1-14`), so `rbac.ts` can import it without a cycle.
  - Below the authorization, `getObjectiveEffectiveLaunchConfig` (`:1406-1431`) and
    `getObjectiveLaunchCommand` (`:1481-1507`) are line-for-line identical for 25 more lines:
    `buildWebappServiceContextForWorkspace` → `resolveLaunchExecutionTarget` →
    `resolveLaunchConfig`, with the same seven arguments.
- **Problem**: The RBAC integrity rule in the playbook is that a route reaches either the
  `requires` annotation or a resolver that authorizes against the resource's own workspace.
  These five routes reach a hand-written third thing that has already drifted from the shared
  resolver in three ways. The next change to how resource-scoped authorization works (a new
  token scope, an audit hook in `requireWorkspacePermission`) will land in `rbac.ts` and miss
  `/api/objectives/:id/{prompt,launch-command,effective-launch-config}` and the two observation
  routes.
- **Proposed change**: Move `requireObjectivePermission` from `repository.ts` to `rbac.ts` and
  export it (signature unchanged: `{ objectiveId, permission, db? } → { workspaceId,
  workspaceUserId, objectiveId }`); `repository.ts` imports it. Give `requireWorkspacePermission`
  an additive `permission: Permission | readonly Permission[]` (any-of) so
  `requireExecutionTargetObservationContext` becomes "resolve the target's workspace, then
  `requireWorkspaceScope` with the two permissions" (~8 lines). In `launch.ts`, the three read
  paths call the helper and then select only the columns they need; `launchObjective` calls it
  inside the transaction with `db: tx`. Add a private `resolveObjectiveLaunchResolution(
  objectiveRef, { agent, executionTargetId })` returning `{ row, serviceCtx, launchTarget,
  resolved }` for the command/effective-config pair.
- **Sequenced steps**:
  1. Move and export `requireObjectivePermission`; add the any-of overload with a unit test in
     `backend/rbac` coverage (there is none today — `cross-workspace-authorization.test.ts`
     exercises it through routes). Zero call-site change.
  2. Convert the three read paths and `launchObjective`. `objectives.test.ts` ("copyable
     objective prompts …", "copyable launch commands …", "effective launch config …") and
     `launch.test.ts` pin the happy paths; `mission-secondary-workspace.test.ts` ("surfaces the
     objective-workspace launch config to launchObjective") pins the secondary-workspace case.
  3. Extract `resolveObjectiveLaunchResolution`; convert the pair.
  4. Convert `requireExecutionTargetObservationContext`; `branch-status.test.ts` and
     `branch-selection-worktrees.test.ts` post observations.
- **Contract impact**: None to any route path, DTO, or permission. The one observable change is
  that a *member* of the objective's workspace who lacks `objective:read` now receives `403`
  instead of `404` on the three read routes, matching every other objective route (the PATCH
  route has behaved this way since `requireObjectivePermission` was written). Non-members still
  receive `404`. Record it in the commit message; no version bump.
- **Risk**: Low–medium, because it touches authorization dispatch. The step-1 unit test is the
  guard; `yarn test:backend` (`objectives.test.ts`, `launch.test.ts`,
  `cross-workspace-authorization.test.ts`, `mission-secondary-workspace.test.ts`,
  `token-scope.test.ts`), `yarn check:workspace-scoping`, `yarn lint`.

### F3. One `ServiceError → ApiError` policy for the execution adapters
- **Value / Effort**: Medium / S
- **Dimension**: Abstraction fit (excess); Duplication with divergence
- **Evidence**:
  - `backend/execution/project-execution-target.ts` has five `catch` blocks that each translate
    `ServiceError` differently: `:66-68` (404 → fixed message), `:113-115` (pass-through with
    code), `:138-141` (404 → fixed message; 409 → with code), `:175-178` (404 → fixed message;
    400 → with code; a 409 falls through), `:203-208` (404 → fixed message; **409 → message
    without `code`**; 400 → with code only for one code). `updateWorkspaceExecutionTarget`
    even constructs a `ServiceError` inside its own `try` (`:172`) so that its own `catch`
    will translate it.
  - `backend/branching/execution-target-observation-scope.ts:38-49`
    (`throwObservationServiceError`) is a generic converter — status `?? 409`, message, code —
    used by both branching routes.
  - The app error handler already renders every `ServiceError` as `{ error, code, details? }`
    with the error's own status (`backend/errors.ts:94-101`), and renders `ApiError` as
    `{ error, detail, code }` (`:88-90`). For an `ApiError` built from a `ServiceError`,
    `detail` is `undefined` and JSON serialisation drops it — the bodies are byte-identical.
    This is the same shape as the 2026-10-05 F2 (chat/connections routers), which landed.
- **Problem**: Six copies of transport policy the app owns. They have already diverged (the 409
  on `updateProjectExecutionTarget` loses its `code`, which the webapp cannot branch on), and
  any future `details` payload from core is silently dropped by every converter.
- **Proposed change**: Delete `throwObservationServiceError` and both `try/catch` wrappers in
  `branching/*.ts` — the `ServiceError` propagates to the handler with the same status, message,
  and code. In `project-execution-target.ts`, keep only the translations that *change the
  message* (`'Project not found'`, `'Execution target not found'`) via one small
  `rethrowNotFoundAs(error, message)` in `backend/errors.ts` (`if (error instanceof ServiceError
  && error.status === 404) throw new ApiError(404, message, undefined, error.code); throw
  error;`), and let every other `ServiceError` reach the handler. Drop the synthetic
  `ServiceError` at `:172` in favour of a direct `ApiError(404, …)`.
- **Sequenced steps**: One commit. `execution-target-onboarding.test.ts` and
  `mission-secondary-workspace.test.ts` ("resolves a project execution target through the
  project workspace") assert the status and message paths; add one case asserting the 409 from
  `updateProjectExecutionTarget` carries `code`.
- **Contract impact**: None. Statuses and messages are unchanged; one 409 body *gains* `code`
  (additive).
- **Risk**: Negligible. `yarn test:backend`, `yarn lint`.
