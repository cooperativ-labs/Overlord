## Summary

The backend's transport/persistence separation is clean where it's supposed to be clean: no SQL
in route handlers, no `req`/`res` leaking into `repository.ts`, no extension importing repository
internals in the wrong direction. The one real structural problem is narrower and more consequential
than "some files are big": `backend/repository.ts` re-implements mission and objective creation
from scratch instead of calling `packages/core/service/missions.ts`, even though `CONTRACT.md`
states REST uses "the same service layer as CLI and Protocol." The two implementations have
already drifted — REST-created missions can carry a priority, due date, assignee, and tags that a
CLI/Protocol-created mission cannot; CLI/Protocol-created missions support explicit per-objective
state sequencing and a review-status short-circuit that REST does not — and one internal helper
(`insertObjective`) is a byte-for-byte copy-paste of its core counterpart, including comments.
That's the highest-value finding here. Two smaller, cleanly-scoped findings round out the report:
three job-queue dispatchers hand-roll the same `worker_jobs` claim/finish SQL instead of sharing
it, and two small exports are simply dead. Nothing in this area rises to "leave it alone" scale
of technical debt, and nothing found here should block ordinary feature work.

## Findings

### F1. Mission/objective creation duplicates the service layer instead of using it
- **Value / Effort**: High / L
- **Dimension**: Layering and boundary leaks; Duplication with divergence
- **Evidence**:
  - `backend/repository.ts:4520-4655` (`createMissionTx`) vs. `packages/core/service/missions.ts:454-557` (`createMissionWithObjectives`)
  - `backend/repository.ts:6422-6524` (`insertObjective`) vs. `packages/core/service/missions.ts:255-371` (`insertObjective`) — the launch-preference-fallback comment block is duplicated verbatim between the two ("Editable slots (draft/future) default to the project's last-used … so the agent is always recorded …")
  - Contract text: `CONTRACT.md:563` — "REST API → Database (HTTP Surface) — Transport: Service layer function calls; same service layer as CLI and Protocol"
  - Call sites of the repository.ts duplicate: `backend/repository.ts:3105` (`initializeProject`), `:4735` (`createMission`), `:4929` (`promoteInboxItem`)
  - Call sites of the core duplicate: `packages/core/service/protocol.ts` (Protocol layer `ovld protocol create`), and internally within `missions.ts` itself
- **Problem**: `CONTRACT.md` states plainly that REST and CLI/Protocol share one service layer for database writes. For mission/objective creation they do not: `backend/repository.ts` has its own transactional `createMissionTx` and its own `insertObjective`, independent of `packages/core/service/missions.ts`. Today this shows up as real, user-visible capability drift rather than a hypothetical risk:
  - A mission created through `ovld protocol create` (core service path) cannot set `priority`, `dueDatetime`, `assignedWorkspaceUserId`, or `tagIds` at creation time — those fields exist only in the REST body type.
  - A mission created through `POST /api/missions` (repository.ts path) cannot request the review-status short-circuit or explicit per-objective `state` sequencing (`draft` for the first objective, `future` for the rest, or all `complete` for a review-status mission) that `createMissionWithObjectives` supports for the Protocol/CLI surface.
  - The duplicated `insertObjective` bodies are still in agreement on their core INSERT and the launch-preference fallback, but nothing enforces that going forward — a future change to either (e.g. a new default-agent rule, a new objective validation) is one PR away from being applied to only one surface, silently reintroducing the same kind of drift that already exists in the mission-creation body.
  - This is exactly what `scripts/check-workspace-scoping.mjs` cannot catch: both copies correctly scope their queries by workspace, so the scoping checker is silent about the duplication.
- **Proposed change**: Extend `packages/core/service/missions.ts::createMissionWithObjectives` and `insertObjective` to accept the REST-only fields (`priority`, `dueDatetime`, `assignedWorkspaceUserId`, `tagIds`) as optional parameters with defaults matching current core-service behavior (so existing CLI/Protocol/MCP callers are unaffected). `insertObjective`'s `state` handling already covers what `backend/repository.ts` needs — both validate against the same seven-value closed vocabulary, core by importing the canonical `OBJECTIVE_STATES` from `@overlord/database`, `backend/repository.ts` by re-declaring an identical local `VALID_STATES` array (`backend/repository.ts:6233-6240`) instead of importing it. Then make `backend/repository.ts::createMissionTx` and `insertObjective` thin wrappers that build a `ServiceContext` and delegate to the core functions, deleting the duplicated SQL and the re-declared vocabulary. This is behavior-preserving for every existing caller on both surfaces; it does not add review-status support to REST or add priority/due-date/assignee/tags to Protocol — it only removes the duplicate implementation, once the shared function supports the union of both surfaces' existing parameters.
- **Sequenced steps**:
  1. Add `priority`, `dueDatetime`, `assignedWorkspaceUserId`, `tagIds` as optional parameters to `createMissionWithObjectives` (default to current core behavior: `'normal'`, `null`, `ctx.actorWorkspaceUserId`, none) — landable and testable on its own, since no existing caller passes them.
  2. Replace `backend/repository.ts`'s local `VALID_STATES` literal with the imported `OBJECTIVE_STATES` from `@overlord/database` (already used by `packages/core/service/missions.ts`) as a standalone, trivially-safe first step, and add characterization tests for either duplicate implementation if it's under-tested, so the later switch has a safety net.
  3. Replace the body of `backend/repository.ts::createMissionTx` with a call into the extended `createMissionWithObjectives`, adapting `ServiceContext` construction from the existing `requireProjectPermission` call. Keep `backend/repository.ts::createMissionTx`'s own request validation (the 400s for missing instruction, invalid priority, invalid `dueDatetime`) as REST-specific input validation ahead of the call.
  4. Replace `backend/repository.ts::insertObjective` with a thin wrapper over the core version; remove the now-dead duplicate SQL and its call sites at `:5854`, `:6533`, `:6641`.
  5. Delete `createObjectiveTx` if it becomes a pure pass-through, or keep it as REST's permission-resolution shim calling the shared `insertObjective`.
- **Contract impact**: None at the interface level — `POST /api/missions`, `POST /api/objectives`, and the Protocol `create`/`add-objectives` commands keep their current request/response shapes and current behavior. This is purely an internal consolidation onto the interaction surface `CONTRACT.md` already mandates (`REST API → Database`, `CONTRACT.md:561-568`), so it needs no version bump.
- **Risk**: The highest risk is silently changing REST or Protocol mission-creation behavior while unifying the two paths (e.g. accidentally applying the review-status short-circuit to REST, or accidentally validating `priority` on the Protocol path). Mitigate with characterization tests asserting current behavior on both surfaces before step 3, and by keeping REST's existing 400-validation in `backend/repository.ts` rather than moving it into the shared function. `yarn test:backend` and `yarn test:core` both need to pass, and the mission-creation and objective-creation test files on both sides (`backend/objectives.test.ts`, `packages/core/service/missions.*.test.ts`) should each still assert their surface's current field set works as before.

### F2. Three worker-job dispatchers hand-roll the same claim/finish SQL
- **Value / Effort**: Medium / M
- **Dimension**: Duplication with divergence; Worker and dispatcher shape
- **Evidence**:
  - `backend/delivery-compose-worker.ts:486-539` (`claimNextComposeJob`), `:542-556` (`markJobTerminal`), `:557-580` (`rescheduleJob`)
  - `backend/push-notification-dispatcher.ts:236-273` (`claimNextJob`), `:273-283` (`finishJob`)
  - `backend/live-activity-dispatcher.ts:183-220` (`claimNextJob`), `:220-232` (`finishJob`)
  - All three share the same reclaim-stale-locks → `SELECT … FOR UPDATE SKIP LOCKED`/plain `SELECT` → compare-and-set `UPDATE … WHERE status = 'queued' AND revision = ?` sequence against `worker_jobs`, the same `RETRY_BACKOFF_MS = [15_000, 60_000, 300_000, 900_000, 3_600_000]` array, and the same class shape (`start()`/`pollNow()`/`poll()` guarded by a `polling` flag, `setInterval(POLL_INTERVAL_MS)`)
  - `packages/core/service/worker-jobs.ts` already exists as the shared home for `worker_jobs`-table concerns (currently only `enqueueDeliveryComposeJob`) — the natural target for the extraction, per the playbook's preference for an existing shared home over a new `utils` module
  - Test coverage gap: `push-notification-dispatcher.ts` exports `__testables` and is exercised via `backend/push-notifications.test.ts:24,380-381`; `live-activity-dispatcher.ts` exports no `__testables` and `backend/live-activities.test.ts` has no dispatcher-level coverage at all — its claim/finish/backoff logic is currently untested directly
- **Problem**: The claim/finish pattern (reset stale locks, select-for-update, CAS the running row, back off with the same delay table on failure) is the same job-queue algorithm implemented three times. Today the three copies agree, but they are already not identical in shape — `delivery-compose-worker.ts` splits reschedule out into a separate `rescheduleJob` function while the other two inline the reschedule branch into `finishJob`'s caller — which is exactly the kind of silent divergence the playbook flags: the next change to backoff or locking behavior has three places to land correctly and no test that would catch a fourth dispatcher's future copy from diverging.
- **Proposed change**: Add `claimNextWorkerJob(db, jobType, workerId)` and `finishWorkerJob(db, id, status, lastError)` (plus the reschedule branch, parameterized by the shared `RETRY_BACKOFF_MS` table) to `packages/core/service/worker-jobs.ts`, generic over `jobType` and the row shape already common to all three (`id`, `payload_json`, `attempt_count`, `max_attempts`, `revision`). Update each dispatcher's `processJob`/`poll` to call the shared functions instead of its local copy, keeping each dispatcher's own payload parsing, business logic (APNs send, webhook mapping, compose automation call), and job-type constant untouched.
- **Sequenced steps**:
  1. Add characterization tests for `live-activity-dispatcher.ts`'s claim/backoff/finish behavior first (it currently has none) — mirror the pattern already in `backend/push-notifications.test.ts:380-381`.
  2. Extract `claimNextWorkerJob` / `finishWorkerJob` into `packages/core/service/worker-jobs.ts`, with unit tests covering stale-lock reclaim, CAS-loses-race (`updated.changes === 0`), and the backoff delay calculation.
  3. Migrate `push-notification-dispatcher.ts` to the shared helpers (it has the most test coverage today — safest first migration).
  4. Migrate `live-activity-dispatcher.ts`, now covered by the tests added in step 1.
  5. Migrate `delivery-compose-worker.ts`, folding its separate `rescheduleJob` into the shared reschedule path.
  6. Delete the three now-dead local copies.
- **Contract impact**: None. `worker_jobs` schema, job types, and dispatcher behavior are unchanged; this is an internal implementation detail behind the existing `overlord.push_notification.dispatch.v1` / `overlord.live_activity.dispatch.v1` / `overlord.delivery.compose.v1` job types documented in `database/docs/09-database-schema-contract.md`.
- **Risk**: A subtly wrong generic claim function could stall or double-process jobs across all three dispatchers at once instead of just one, which is why step 1 (tests for the currently-untested `live-activity-dispatcher.ts`) and per-dispatcher migration order matter. `yarn test:backend` plus the Postgres conformance suite should run after each migration step, not just at the end, since `FOR UPDATE SKIP LOCKED` behavior is dialect-sensitive.

### F3. Two dead exports
- **Value / Effort**: Low / S
- **Dimension**: Dead and vestigial code
- **Evidence**:
  - `backend/rbac.ts:50-60` — `requireAdmin` has zero references anywhere in `backend/`, `packages/`, `webapp/`, `cli/`, `mcp/`, `desktop/`, `connectors/`, or `scripts/` outside its own declaration
  - `backend/db.ts:191` — `export const resolveActorForWorkspaceAsync = resolveActorForWorkspace;` has zero references anywhere; `resolveActorForWorkspace` itself (the function it aliases) is used elsewhere and is not affected
- **Problem**: `requireAdmin` looks like a live RBAC gate — an `ApiError(403, 'Admin role required')` guard sitting in `backend/rbac.ts` next to the permission checks that are actually wired into every route. It isn't called anywhere. A future reader either wastes time investigating why it's unused or, worse, assumes some route is admin-gated by it when none is. `resolveActorForWorkspaceAsync` reads as a leftover from a since-completed sync/async rename of `resolveActorForWorkspace` and adds nothing.
- **Proposed change**: Delete both. No replacement needed — nothing calls them.
- **Sequenced steps**: 1. Delete `requireAdmin` from `backend/rbac.ts`. 2. Delete the `resolveActorForWorkspaceAsync` alias from `backend/db.ts`. Both independently landable in one commit each.
- **Contract impact**: None — neither is part of any documented interface.
- **Risk**: Negligible. `yarn typecheck:backend` will catch any reference this search missed (e.g. a dynamic string lookup), but neither name showed up in any string-keyed registry or dispatch table during this review.

## Explicitly not recommended

- **Splitting `backend/repository.ts` by entity group (projects / workspace-statuses / tags / resources / missions / objectives / profile / tokens) as a standalone effort.** The file is large, but each entity group reads and is tested as one coherent unit, fan-in is almost entirely the single `index.ts` route-wiring import, and a size-driven split with no behavior seam would just relocate the same code behind new import paths for no functional gain. The one part of `repository.ts` actually worth moving is the mission/objective creation logic — that's F1, motivated by real duplication, not by line count.
- **Extracting `exportWorkspaceObjectivesCsv` (`backend/workspaces.ts:842-958`) out of `workspaces.ts`.** It's a clean, single-call-site, low-risk seam (CSV reporting bolted onto a workspace-membership file), but it's tidiness with no duplication or drift behind it — Low value, and `workspaces.ts` isn't over its size threshold enough to force the issue. Worth doing opportunistically if someone is already in that file, not worth a dedicated mission.
- **Modularizing `backend/index.ts`'s route table.** It's the largest file after `repository.ts` (2,045 lines) and growing, but it is exactly what the REST API Layer's contract entry says it should be — the URL-path/HTTP-method assembly point — and every route handler already delegates its actual logic to `repository.ts`, `workspaces.ts`, `execution/launch.ts`, etc. There's no SQL or business logic leaking into it (checked directly for this review). Splitting the route table by feature area is plausible future work if it keeps growing, but there's no current pain point driving it.
