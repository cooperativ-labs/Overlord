## Summary

The backend absorbed eight contract versions in thirteen days and every finding from the last
report landed, so the standing debt (repository size, `index.ts`, the worker shape, test bootstrap)
did not grow. The new debt is concentrated in one place: `backend/connections/` now holds two
connection classes, `AccountConnections` (organization-scoped, v152) and `ProfileConnections`
(profile-scoped, v153), that implement the same OAuth authorization, single-use state consumption,
refresh lease, re-seal and reauthorization state machine twice over the same table, with ten
`UPDATE account_connections` statements each and two already-divergent PKCE AAD formats. That is
the highest-value refactor available (**F1**) and the one most likely to bite, because every
credential rule change (v156 platform key, v158 write scope) has had to be made in two places and
checked by two conformance suites. Below it: provider adapters register themselves into a
module-level map at import time, so the set of available providers depends on import order and
tests must register by hand (**F2**); `GeminiRunSession` has grown from 600 to 1,050 lines and now
carries a diagnostics decorator and a summarization procedure that are separable with no behavior
change (**F3**); the three chat conformance suites each carry their own `ScriptedGemini`,
`world()` and Knowledgebase-connect harness (**F4**); two exports in the connections module are
dead while `index.ts` re-derives one of them inline (**F5**); and the area's conventions document
does not name the three test-support file kinds the cycle introduced (**F6**).

## Findings

### F1. Extract the OAuth authorization and credential-lease state machine shared by `AccountConnections` and `ProfileConnections`
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Module size and cohesion
- **Evidence**:
  - `backend/connections/service.ts:80-85` and `backend/connections/profile.ts:180-185` — two `verifierAad` functions with different formats: `…:${row.organization_id}:${row.id}:…` versus `…:-:${row.id}:…`. For every row each class can own, `organization_id ?? '-'` reproduces both byte-for-byte, so one function already covers both.
  - `service.ts:209-286` (`start`) and `profile.ts:520-578` (`beginOAuth`) — the same transaction: find the live row or insert a `pending` one, prune consumed/expired `account_connection_authorizations`, count open ones against `MAX_OPEN_AUTHORIZATIONS` → `limit_exceeded`, insert `hashSecret(state)` plus a PKCE verifier sealed under `verifierAad`, return `{ connectionId, authorizeUrl, expiresAt }`.
  - `service.ts:288-387` (`complete`) and `profile.ts:584-700` (`completeOAuth`) — the same `^[A-Za-z0-9_-]{40,80}$` state check, the same consume-once transaction (`UPDATE … SET consumed_at … WHERE consumed_at IS NULL AND expires_at > ?` then `fresh: result.changes === 1`), the same 2,048-character code bound, the same "disconnected while signing in → revoke the new grant" tail.
  - `service.ts:443-520` (`accessToken`) and `profile.ts:706-770` (`oauthAccessToken`) — the same lease loop: `deadline = now + REFRESH_LEASE_MS * 2`, `ACCESS_EXPIRY_SKEW_MS` freshness, `staleRevision` coalescing, the lease `UPDATE … refresh_lock_owner/refresh_lock_until … WHERE … credential_revision = ? AND (refresh_lock_owner IS NULL OR refresh_lock_until <= ?)`, `sleep(100)`, `unavailable` at the deadline.
  - `service.ts:522-557` and `profile.ts:772-818` — two `refreshLeased` with the same `invalid_grant → requireReauthorization`, `refresh_unavailable` lease release, and persist-before-use `UPDATE`.
  - `service.ts:558-565` / `profile.ts:905-911` (`requireReauthorization`) and `service.ts:573-578` / `profile.ts:913-919` (`recordError`) — byte-identical SQL. `service.ts:428-436` and `profile.ts:891-903` (`erase`) differ only by a `state <> 'disconnected'` guard.
  - `service.ts:73-77` and `profile.ts:150-153` — `AUTHORIZATION_TTL_MS`, `MAX_OPEN_AUTHORIZATIONS`, `ACCESS_EXPIRY_SKEW_MS` declared twice (only `REFRESH_LEASE_MS` is shared).
  - `service.ts:593-608` — private `readKey` and `missingKeyIsConfiguration` re-implement `keyring.ts:keyById` / `keyring.ts:missingKeyIsConfiguration` with a narrower rule ("fallback keys never apply to Knowledgebase"); `profile.ts:430-445` uses the `keyring.ts` versions. The narrowing is intentional, but it lives in a class method instead of next to the rule it narrows.
  - `service.ts:212` — the organization-scoped class special-cases `provider === 'github'` to explain why a profile provider reached it; the router (`routes.ts:97`) already decides which class serves a provider.
- **Problem**: The contract says the account-connections module is "the only writer of `account_connections` and the only reader of credentials"; in code that module is two 650–930-line classes with twenty `UPDATE` statements between them. v156 (platform key re-seal) and v158 (write scope) each had to be reasoned about twice, and the PKCE AAD has already drifted into two formats. The next change to lease timing, authorization pruning, or reauthorization erasure is two edits and two conformance suites, and a one-sided fix will not fail any test.
- **Proposed change**: Two small shared modules, both taking `db` and a row (no class state):
  - `backend/connections/authorizations.ts` — `beginAuthorization(tx, { row, state, verifier, key, returnTo, returnUrl, ttlMs, maxOpen, now })` (prune, count, insert) and `consumeAuthorization(tx, { state, providerFilter?, now })` (lookup by hash with the optional `c.provider = ? AND c.organization_id IS NULL` join, consume-once, return `{ auth, row, fresh }`), plus the single `verifierAad` using `organization_id ?? '-'`. The validation regex and code bound become exported constants.
  - `backend/connections/credential-rows.ts` — `requireReauthorization(db, rowId, code, now, lockOwner?)`, `recordError(db, rowId, code, now)`, `eraseCredential(tx, rowId, now, { onlyIfLive })`, `acquireRefreshLease(db, row, lockOwner, now)`, `releaseRefreshLease(db, rowId, lockOwner, code, now)`, and `withRefreshLease(db, row, lockOwner, { now, sleep, deadlineMs }, refresh)` holding the retry loop. The shared constants move here.
  Each class keeps its own `seal`/`open` (the `Credentials` vs `OpenedCredential` shapes differ for a reason) and its own row scoping predicates (`organization_id = ?` vs `organization_id IS NULL`). `AccountConnections.readKey`/`missingKeyIsConfiguration` become `keyring.ts:knowledgebaseKeyById(ring, id)` and a `scope: 'organization'` argument on the existing `missingKeyIsConfiguration`, so the narrowing is one line next to the rule. `service.ts:212` is deleted once the router owns provider dispatch (F2).
- **Sequenced steps**:
  1. Add `credential-rows.ts` with `requireReauthorization`, `recordError`, `eraseCredential`; point both classes at them (pure SQL move, nine call sites). Run both connection conformance suites.
  2. Add `withRefreshLease` and move both `accessToken`/`oauthAccessToken` loops and `refreshLeased` bodies onto it; the provider-specific parts (`KnowledgebaseOAuth.refresh` vs `ProfileOAuthAdapter.refresh`, scope checks, `onAccessLost`) stay as callbacks.
  3. Add `authorizations.ts` with the single `verifierAad`; add a unit test asserting it equals both old formats for an organization row and a profile row; convert `start`/`beginOAuth`, then `complete`/`completeOAuth`.
  4. Move `readKey`/`missingKeyIsConfiguration` into `keyring.ts`; delete the duplicate constants.
- **Contract impact**: None. No route, DTO, stored envelope, AAD string, or table changes; `CONTRACT.md` §"Backend → Outbound MCP" and the v153 "two connection scopes" text describe behavior this preserves.
- **Risk**: The PKCE verifier AAD and the credential AAD are the two places where a refactor could silently break decryption. Step 3's unit test pins the former; `connectionCredentialAad` already pins the latter. Verification: `yarn test:backend` (SQLite), then `yarn test:conformance` with `TEST_DATABASE_URL` — `connections.postgres-conformance.test.ts` (1,536 lines), `profile-connections.postgres-conformance.test.ts`, `github-connections.postgres-conformance.test.ts`, and `chat/knowledgebase-writes.postgres-conformance.test.ts` exercise every path above on both dialects.

### F2. Pass profile-connection providers to the connections runtime instead of registering them at import time
- **Value / Effort**: Medium / M
- **Dimension**: Abstraction fit (excess indirection); Layering and boundary leaks
- **Evidence**:
  - `backend/connections/profile.ts:139-148` — a module-level `providers` map with `registerProfileConnectionProvider` / `profileConnectionProvider`.
  - `backend/ext/github/user-oauth.ts:24` — `registerGitHubConnectionProvider()` runs as a top-level side effect of importing the module; `backend/ext/everhour/service.ts:259` — `registerEverhourConnectionProvider(async apiKey => …)` likewise. Both reach the map only because `index.ts:70-72` imports the extension routers.
  - `backend/connections/github-connections.postgres-conformance.test.ts:57` — the test has to call `registerGitHubConnectionProvider()` by hand; `profile-connections.postgres-conformance.test.ts` depends on importing `ext/everhour/service.ts` for its adapter.
  - `backend/connections/routes.ts:97` and `:276` consult the registry to route `POST /api/connections` and to label the callback page; `backend/connections/service.ts:212` guards against a provider that "is not registered".
  - `backend/connections/index.ts:36` — `createConnectionsRuntime(options)` already assembles `AccountConnections`, `ProfileConnections`, the MCP client and the source checkers from explicit options; providers are the one input it receives implicitly.
- **Problem**: Which providers exist is decided by import order rather than by the runtime's constructor, so a `ProfileConnections` built in a test, a script, or a future second entry point sees an empty or partial provider set with no error. The direction of the dependency is right (extensions reach into the core registration point; core never imports `ext/`), but the mechanism is a string-keyed global that defeats both the type checker and the dead-code sweep, and it leaves a provider-specific guard (`'github'`) inside the organization-scoped class.
- **Proposed change**: `ext/github/connection-provider.ts` exports `githubConnectionProvider(): ProfileConnectionProvider` and `ext/everhour/connection-provider.ts` exports `everhourConnectionProvider(validateApiKey)`; neither registers anything. `createConnectionsRuntime` takes `providers: ProfileConnectionProvider[]` and passes them to `new ProfileConnections(db, ring, providers)`; `ProfileConnections` exposes `provider(name)` for the router, replacing the free `profileConnectionProvider`. `index.ts:641-664` supplies both adapters (the Everhour validation closure moves to an exported function in `ext/everhour/service.ts`). The `profileConnections(db, env)` convenience used by the extensions (`user-oauth.ts:45`, `everhour/service.ts:248`) is built the same way, so it is created once in `index.ts` and handed to the extension routers rather than reconstructed per call.
- **Sequenced steps**:
  1. Add the `providers` constructor argument with a default of the current registry (no behavior change); convert the two tests to pass adapters explicitly.
  2. Convert `index.ts` and the two extension modules; delete the module-level map, `registerProfileConnectionProvider`, and `service.ts:212`.
  3. Thread the single `ProfileConnections` instance into the extension routers in place of the `connections(client)` factories.
- **Contract impact**: None. Routes, DTOs and provider identifiers are unchanged; the v153 "account-connection provider extension point" becomes a constructor argument instead of a registration call, which the contract does not specify either way.
- **Risk**: Step 3 touches the ambient-`db` pattern the extensions still use (`requireDatabaseClient()` defaults); keep it as the last step and run `yarn check:workspace-scoping`. Verification: `yarn test:backend`, the three connection conformance suites, `backend/ext/everhour/service.test.ts`, `backend/ext/github/*.test.ts`.
