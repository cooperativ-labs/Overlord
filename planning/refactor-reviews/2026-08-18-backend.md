## Summary

Backend absorbed 30 contract versions of new feature surface (Latch terminal sessions, the
virtual-target gateway, Live Activities, standard push notifications, agent-session channels,
webhooks, the cross-workspace activity feed) since the last review, and the size growth is
almost entirely explained by that shipped work rather than accretion — `execution/launch.ts`'s
+409 lines map cleanly onto three named features, and no dead code turned up anywhere in the
newer subsystems. The dispatcher and APNs code is now well-factored (shared claim/finish logic,
shared signing/transport helper), confirming F2's fix held under further use.

The recurring problem is the same shape as last cycle's F1, just on different entities:
`backend/repository.ts` still hand-rolls SQL for entities that CLI/Protocol/MCP also write
through `packages/core/service/*`, and the two implementations have already diverged in a
small but real way for both artifacts (a validation check that exists on one write path and not
the other two) and shared-context (an inconsistent workspace-scoping predicate). The other
notable finding is new and more structural: `backend/repository.ts` reaches directly into the
GitHub extension's tables and functions during composite project initialization, which is the
serious-direction layering violation the playbook warns about ("core must not know its
extensions") and also does not match what `CONTRACT.md` itself says this flow does. Fixing that
one is the highest-value item in this report.

## Findings

### F1. Composite project initialization writes bypass the GitHub extension boundary
- **Value / Effort**: High / L
- **Dimension**: Layering and boundary leaks
- **Evidence**:
  - `backend/repository.ts:149` — `import { createPrivateGitHubRepository } from './ext/github/user-oauth.ts';`
  - `backend/repository.ts:3231` (`SELECT ... FROM ext_github_project_initializations`), `:3314` (`INSERT INTO ext_github_project_initializations`), `:3361` (`UPDATE ext_github_project_initializations`), `:3398`, `:3459` (further `SELECT`s), `:3405` (`SELECT id FROM ext_github_project_links`), `:3411` (`INSERT INTO ext_github_project_links`) — all inside `initializeProject` (`:3243`) and its helper `persistInitializedRepository` (:3384)
  - `backend/repository.ts:13` imports the extension's own DTO type `CreatedGitHubRepositoryDto` from `@overlord/contract/ext/github`
  - Contract text this contradicts — `CONTRACT.md:293` (Composite project initialization): "optional private GitHub provisioning runs outside that transaction through the already connected user OAuth credential... **On success the extension records one GitHub project link** and the core service records one non-primary read-only `git` resource for the HTTPS clone URL." Today core (`repository.ts`) records that link itself, not the extension.
  - `CONTRACT.md:699` ("Extension → Core (Extension Surface)"): "Reactions: Via service APIs, `entity_changes`, and `outbox_messages`; no direct writes to core tables" — constrains the extension's writes into core tables; there is no equivalent sanction anywhere in the contract for core writing into `ext_`-namespaced tables, which is what happens here.
  - `backend/ext/github/service.ts` already has the sanctioned pattern for a *different* GitHub-link flow: `linkProjectGitHub` (`:366-450`) reads/writes `ext_github_project_links` through the extension's own module, taking an optional `tx` for transaction participation (mirroring `readProjectLink(projectId, workspaceId, tx)` at `:191`) — proof the "extension owns writes to its own tables" pattern is already established elsewhere in this codebase, just not followed here.
- **Problem**: `ext_github_project_initializations` and `ext_github_project_links` are namespaced extension tables (`ext_<name>_` per `CONTRACT.md`'s Extension System section, `:373-390`), but `backend/repository.ts` — the core persistence layer — reads and writes both directly and imports the extension's repository-creation function directly, rather than going through any extension-owned entry point. This is the more serious of the two isolation directions the backend playbook calls out ("core must not know its extensions"): the GitHub extension cannot currently be disabled, replaced, or have its table shape changed without touching `backend/repository.ts`, and `repository.ts` already carries a comment (`:3238`, "The mobile composite creation boundary...") that treats this as core business logic rather than an extension interaction. It also means the contract's own description of this flow — "the extension records one GitHub project link" — is currently false; either the code or the contract text is wrong, and the code is what should change, since the extension already has the pattern (`linkProjectGitHub`) this flow should be following.
- **Proposed change**: Move the `ext_github_project_initializations` CRUD (read/insert/update) and the `ext_github_project_links` insert currently inline in `persistInitializedRepository` into `backend/ext/github/service.ts` as new exported functions (e.g. `createProjectInitialization`, `readProjectInitialization`, `recordProvisioningFailure`, `recordPrivateRepositoryLink`), each accepting an optional `tx: DatabaseClient` the same way `readProjectLink` already does. `backend/repository.ts::initializeProject` and `persistInitializedRepository` call these instead of running SQL against `ext_` tables directly. Keep the direct call to `createPrivateGitHubRepository` from `backend/ext/github/user-oauth.ts` — invoking an extension's exported function to perform its side effect is the sanctioned "service API" shape; the violation is the table access, not that call.
- **Sequenced steps**:
  1. Add `createProjectInitialization`, `readProjectInitialization` (matching the existing local helper's signature at `backend/repository.ts:3222`), and `recordProvisioningFailure` to `backend/ext/github/service.ts`, each a thin wrapper over the same SQL currently inline in `repository.ts`, with unit tests covering insert/read/failure-update — landable with zero behavior change since the SQL is copied, not rewritten.
  2. Add `recordPrivateRepositoryLink(tx, { project, repo })` to `backend/ext/github/service.ts`, covering the `ext_github_project_links` insert and the paired `entity_changes` row currently in `persistInitializedRepository` (`repository.ts:3405-3437`).
  3. Replace the six direct `ext_github_*` SQL call sites in `backend/repository.ts:3231-3461` with calls to the four new functions, deleting `readProjectInitialization` (the private helper at `:3222`) once its callers are switched.
  4. Delete the now-unused inline `ext_github_project_links` INSERT and its `recordChange` call from `persistInitializedRepository`.
- **Contract impact**: None to any interface — `POST /api/projects/initialize`'s request/response shape and behavior are unchanged; this makes the implementation match what `CONTRACT.md:293` already says. No version bump needed.
- **Risk**: `initializeProject`'s outer flow and `persistInitializedRepository` both run inside `db.transaction`; every extracted function must accept and honor the passed `tx` so the composite create/provisioning-record write stays atomic with the mission/project creation. `project-initialization.test.ts` and the GitHub extension's own tests should both pass unchanged since no SQL text changes, only its module location; run both plus `yarn test:backend`.

### F2. Artifact and shared-context writes are hand-duplicated across REST and Protocol/CLI, and have already diverged
- **Value / Effort**: High / L
- **Dimension**: Duplication with divergence; Layering and boundary leaks
- **Evidence**:
  - Artifacts — three independent `INSERT INTO artifacts` implementations: `backend/repository.ts:4533-4674` (`createArtifact`, used by REST and by `backend/protocol.ts`'s `add-artifact`/`update-artifact` handlers at `:909-953`), `packages/core/service/protocol.ts:1928-1949` (inside `deliverSession`), `packages/core/service/protocol.ts:2455-2472` (inside `recordWork`)
  - Divergence: `backend/repository.ts:4505-4525` validates `type` against a locally declared `CORE_ARTIFACT_TYPES` set before inserting (with a comment acknowledging namespaced extension values), returning a clean `ApiError(400, ...)`. Neither `deliverSession` nor `recordWork`'s artifact-insert loop performs any such check — an invalid `type` from `protocol deliver`, `record-work`, or the MCP tools that call the same core functions falls through to the raw Postgres `CHECK` constraint on `artifacts.type` instead of a clean validation error.
  - Shared context — two independent implementations against `shared_context_entries`: `backend/repository.ts:4412-4501` (`upsertMissionSharedContext`, used by REST) vs. `packages/core/service/missions.ts:1135-1219` (`writeSharedContext`, used by Protocol/CLI/MCP via `backend/protocol.ts:896-905`)
  - Divergence: `backend/repository.ts:4450-4455`'s `UPDATE` is scoped `WHERE id = ? AND workspace_id = ?`; `packages/core/service/missions.ts:1171-1176`'s `UPDATE` is `WHERE id = ?` only. Not currently exploitable — both are preceded by a workspace/mission-scoped `SELECT` — but it is direct evidence the two copies are being maintained independently, exactly the failure mode the contract's "same service layer" language is meant to prevent.
  - Contract text: `CONTRACT.md:611` — "REST API → Database... Transport: Service layer function calls; same service layer as CLI and Protocol." This is not true today for either artifacts or shared context.
- **Problem**: This is the same root pattern as the prior report's F1 (mission/objective creation), recurring on two entities that fix did not touch. Today the three artifact-insert copies still agree on shape, and the two shared-context UPDATEs are not exploitably different — but nothing enforces that going forward. A future change to either (a new artifact field, a new shared-context validation rule) is one PR away from landing on only one or two of the three/two surfaces, silently reintroducing the exact kind of drift the last review's F1 already found and fixed once for missions.
- **Proposed change**: For artifacts — extract one `insertArtifactRow` (or extend `createArtifact`'s existing type-validated path into a shared function) that both `packages/core/service/protocol.ts`'s `deliverSession`/`recordWork` and `backend/repository.ts`'s `createArtifact` call, carrying `CORE_ARTIFACT_TYPES` validation into the shared function so all three write paths get the same check. For shared context — make `backend/repository.ts::upsertMissionSharedContext` a thin wrapper over `packages/core/service/missions.ts::writeSharedContext` (mirroring how `createMissionTx` now wraps `createMissionWithObjectives`), after widening `writeSharedContext`'s `UPDATE` to include `AND workspace_id = ?` so REST's stricter scoping becomes the one shared behavior rather than being lost in the merge.
- **Sequenced steps**:
  1. Add the missing `AND workspace_id = ?` predicate to `writeSharedContext`'s `UPDATE` in `packages/core/service/missions.ts:1171-1176` — a self-contained, behavior-preserving-for-callers hardening, landable and testable alone.
  2. Move `CORE_ARTIFACT_TYPES` and the artifact-insert SQL out of `backend/repository.ts::createArtifact` into a new `insertArtifactRow` in `packages/core/service/missions.ts` (or a small `packages/core/service/artifacts.ts` if that reads cleaner alongside `missions.ts`'s other entity groups), taking the same fields both `createArtifact` and the two `protocol.ts` sites already pass.
  3. Point `packages/core/service/protocol.ts`'s `deliverSession` and `recordWork` artifact loops at `insertArtifactRow`, so the type check now applies uniformly; add characterization tests asserting `protocol deliver`/`record-work` with an invalid `type` now returns the same clean validation error REST already returns.
  4. Replace `backend/repository.ts::createArtifact`'s body with a thin wrapper over `insertArtifactRow` plus REST's own request-shape validation (label/content presence), the same "keep REST-specific 400s in repository.ts, delegate the write to core" split used for `createMissionTx`.
  5. Replace `backend/repository.ts::upsertMissionSharedContext`'s body with a thin wrapper over `writeSharedContext`, keeping REST's own body-shape validation ahead of the call.
- **Contract impact**: None at the interface level — no route, Protocol subcommand, or MCP tool changes shape or behavior for any currently-valid input; step 1 only rejects a shared-context update that today would incorrectly succeed across workspace boundaries (recall: currently unreachable in practice since the preceding `SELECT` is already scoped). No version bump needed.
- **Risk**: The main risk is accidentally changing which artifact types each surface accepts, or applying REST's stricter validation somewhere it previously wasn't enforced and breaking an existing agent/connector that relied on the looser core-service path. Mitigate with characterization tests on both `backend/artifacts.test.ts` and the relevant `packages/core/service/protocol.*.test.ts` files before steps 2–4, and run `yarn test:backend` plus `yarn test:core` after every step, not just at the end.

### F3. Four closed-vocabulary values are hand-copied instead of imported in `agent-session-routes.ts`
- **Value / Effort**: Medium / S
- **Dimension**: Types and contracts
- **Evidence**:
  - `backend/agent-session-routes.ts:463-467` re-derives the exact member list of `DELIVERY_OUTCOMES` (`packages/core/service/agent-session/pure/inject.ts:9-14`) as four chained `===` comparisons instead of importing the array.
  - `backend/agent-session-routes.ts:396` — `const allowed = ['emitted', 'applied', 'not_applied', 'unknown'] as const;` duplicates the parameter type of `recordRequestApplication` (`packages/core/service/agent-session/requests.ts:465`).
  - `backend/agent-session-routes.ts:363` — `const allowed = ['timeout', 'local_activity', 'policy', 'interrupt'] as const;` is a deliberately-narrowed subset of `releaseRequestToTerminal`'s `reason` type (`packages/core/service/agent-session/requests.ts:334`, which also allows `'channel_ended'` — an internally-produced value this human-facing route correctly excludes), but is still an unenforced hand-copy rather than a type-checked `Exclude<...>`.
  - `backend/agent-session-routes.ts:274` — `kind !== 'question' && kind !== 'permission' && kind !== 'choice' && kind !== 'retry'` duplicates `AgentRequestKind` (`packages/core/service/agent-session/requests.ts:48`), which is already re-exported through the barrel this file imports from (`packages/core/service/agent-session/index.ts:14`, `export * from './requests.js'`) — this one could be fixed with a type import alone, no core change needed.
- **Problem**: This is the same F1-adjacent pattern the previous review found in `backend/repository.ts`'s `VALID_STATES` (since fixed) — a closed vocabulary re-declared as a local literal list instead of imported. None of the four is exploitable today (all four gate a 400/opaque rejection, not a silent business-logic branch), but each is an unenforced copy: if core adds or renames a member, these checks go stale with no compiler error, silently rejecting (or worse, silently accepting) a value the type system should have caught.
- **Proposed change**: Import `DELIVERY_OUTCOMES` (exporting it from the barrel first, since only the type is currently re-exported — add `export { DELIVERY_OUTCOMES }` alongside the existing `DeliveryOutcome` type export in `packages/core/service/agent-session/inputs.ts:10`) and use `(DELIVERY_OUTCOMES as readonly string[]).includes(deliveryOutcome)` in place of the four-way `===` chain. Import `AgentRequestKind` and check membership against a small `AGENT_REQUEST_KINDS` array (export one from `requests.ts` alongside the type, mirroring `DELIVERY_OUTCOMES`'s shape) in place of the four-way `!==` chain. For `applicationState` and `release` `reason`, export the same kind of `as const` array from `packages/core/service/agent-session/requests.ts` next to each type, and derive this file's `allowed` list from it (narrowing with `.filter`/an explicit exclude-list for the `release` case, so the intentional subset stays visible in code rather than as an implicit literal match).
- **Sequenced steps**: 1. Add and export the four `as const` arrays in core (`DELIVERY_OUTCOMES` already exists — just export it from the barrel; add `AGENT_REQUEST_KINDS`, `APPLICATION_STATES` next to their types in `requests.ts`). 2. Swap each of the four call sites in `agent-session-routes.ts` to import and check against the shared array. Each of the four is independently landable in one commit.
- **Contract impact**: None — these are internal validation checks; the set of values each route accepts is unchanged.
- **Risk**: Low. `yarn typecheck:backend` will catch any accidental mismatch introduced while swapping; `backend/agent-session-routes.test.ts` should be extended with one case per field asserting the boundary (last valid value, first invalid value) still behaves identically before and after.

- **Dimension**: Module size and cohesion
- **Evidence**:
