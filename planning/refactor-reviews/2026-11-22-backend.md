## Summary

The protocol surface has a good skeleton. One table maps each subcommand to `{ handler,
permission }`. It is merged with a duplicate-name guard (`protocol.ts:200-217`), and its permissions
are pinned by `protocol-subcommand-table.test.ts`. The handlers are thin adapters over core services.
The debt sits in the rules that live **outside** that table:

- **The `project_automation` allowlist.** It is a string `Set` inside the dispatcher, plus a regex
  in the REST route guard. It is the only gate for hosted MCP, and no test asserts that the two
  copies agree.
- **Addressing flags.** The workspace derivation reads them in a different normalisation from the
  handlers it routes to.
- **Scalar flags.** These are parsed by five different integer rules and two `--connection-method`
  readers.

`protocol/missions.ts` is over 1,000 lines because about 330 lines of objective-input parsing and a
search adapter share a file with the mission table. Those are clean seams.

The highest-value refactor is **F1**: put the `project_automation` admission on each table entry,
and derive both the MCP/protocol gate and the REST route-guard pattern from it. That gives the
contract's security allowlist one code declaration and a test that pins it.

## Findings

### F1. Declare `project_automation` admission (and the other name-keyed dispatch rules) on the subcommand table, and derive both gates from it
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence risk; Types and contracts
- **Evidence**:
  - `contract/authorization.md:69-90` is normative. It admits `POST /api/protocol/:subcommand` for a
    `project_automation` token for exactly `create` (project form only), `load-context`, `search`,
    `discover-project` (`--project-id` form only), `statuses`, `list-deliveries`,
    `objective-changes`, `attachment-list`, `attachment-download-url`, and `auth-status`.
  - That list is written twice in code:
    - `backend/protocol.ts:239-255` is an inline `new Set([...10 names])` inside
      `runProtocolSubcommand`. `:256-262` adds the `discover-project` "needs `--project-id`" rule.
    - `backend/project-automation-routes.ts:21-24` is a regex alternation of the same 10 names,
      inside the route guard's `ALLOWED` table.
  - The two copies guard **different transports**. The REST guard only sees
    `POST /api/protocol/...`. Hosted MCP calls `runProtocolSubcommand` in-process
    (`mcp/server.ts:6,514,529,543,555,563`) behind the generic `POST /mcp` admission
    (`project-automation-routes.ts:20`), so for MCP the inline `Set` is the only gate.
  - The two lists agree today, but nothing asserts it:
    - `project-automation-routes.test.ts:24-37` spot-checks `/api/protocol/create` only.
    - `project-automation-token.e2e.test.ts:959-997` checks six MCP denials and not the admitted
      list.
    - `protocol-subcommand-table.test.ts:16-71` pins every subcommand's permission, but not its
      `project_automation` admission.
  - Three more dispatch rules are keyed by subcommand name outside the table:
    - `protocol.ts:188`: `update-objective` skips mission/objective pair validation.
    - `protocol.ts:258`: the `discover-project` `--project-id` rule.
    - `protocol.ts:275`: `search` is not permission-gated at dispatch, although its entry says
      `PERMISSIONS.MISSION_READ` (`protocol/missions.ts:723-725`). The comment that explains why
      is on the entry, but the behaviour is in the dispatcher.
- **Problem**:
  - Adding a read-only subcommand that automation tokens should reach means editing two lists in
    two files, in two syntaxes, plus the contract. Missing the `Set` silently denies it over MCP.
    Missing the regex denies it over REST.
  - Renaming a subcommand leaves a stale name in a security allowlist.
  - `SubcommandEntry` was built so that "a subcommand cannot be registered without deciding its
    permission" (`protocol/flags.ts:18-27`), but admission and the dispatch-gate exemption are
    decided elsewhere, by string.
- **Proposed change**:
  - Extend `SubcommandEntry` (`protocol/flags.ts:24-27`) with three fields:
    - `projectAutomation: 'denied' | 'admitted' | 'admitted-with-project-id'`. It is required, so
      every entry states it, exactly as `permission` is stated.
    - `dispatchGate?: 'permission' | 'handler'`. The default is `'permission'`. `search` sets
      `'handler'`, and its `permission` stays `MISSION_READ`, so the exported
      `SUBCOMMAND_PERMISSIONS` is unchanged.
    - `addressing?: 'mission-and-objective' | 'objective-only'`. The default is the former, and
      `update-objective` sets `'objective-only'`.
  - In `protocol.ts`:
    - export `PROJECT_AUTOMATION_SUBCOMMANDS`, derived from the merged table;
    - replace `:239-262` with one lookup on `entry.projectAutomation`, done after the entry is found;
    - replace `:188` and `:275` with reads of `entry.addressing` and `entry.dispatchGate`.

    The unknown-subcommand 404 keeps its current precedence: a scoped token still gets the bare
    `Not found` for an unknown name, as it does today.
  - `project-automation-routes.ts` builds its protocol pattern from
    `PROJECT_AUTOMATION_SUBCOMMANDS`. `app.ts` already imports both modules, and `protocol.ts` does
    not import the guard, so there is no cycle.
  - Keep `create`'s in-handler rejection of `--unassigned-to-project` (`protocol/missions.ts:582`).
    It is a flag-combination rule the table cannot express, and it stays as defence in depth.
- **Sequenced steps**:
  1. Characterization tests, first:
     - Add `EXPECTED_PROJECT_AUTOMATION` to `protocol-subcommand-table.test.ts`. It is the
       contract's 10 names, written out by hand like `EXPECTED_PERMISSIONS`.
     - Add a test that runs every table name through `runProtocolSubcommand` under
       `setActiveTokenAuth({ projectIds: [...] })` and asserts admitted versus 404.
     - Add a guard test in `project-automation-routes.test.ts` that does the same for
       `POST /api/protocol/<every name>`.

     These pass against today's code.
  2. Add the entry fields, setting each explicitly in all five group modules. Derive the dispatcher
     gate from them, and delete the `Set` and the three name checks. The step-1 tests must still pass
     unchanged.
  3. Point the route guard at `PROJECT_AUTOMATION_SUBCOMMANDS`. The step-1 guard test must still
     pass.
- **Contract impact**: None. The admitted set, the 404 bodies and the permission table are
  unchanged. The contract list becomes checkable against one code declaration.
- **Risk**: Medium in kind, low in practice. This changes how a security allowlist is assembled, so
  a typo would widen or narrow token reach. The step-1 tests are written before the change and pin
  both transports. Verification: `yarn test:backend`
  (`protocol-subcommand-table`, `project-automation-routes`, `project-automation-token.e2e`,
  `token-scope`, `token-project-selection.postgres-conformance`), `yarn test:conformance`, `yarn
  typecheck:backend`, `yarn lint`.

### F2. One protocol-address reader, shared by workspace derivation and the handlers; move the derivation out of the dispatcher
- **Value / Effort**: Medium / M
- **Dimension**: Duplication with divergence (ID resolution); Layering
- **Evidence**:
  - `protocolWorkspaceId` (`protocol.ts:53-128`) chooses the workspace whose permissions and
    `ServiceContext` the handler runs under. It reads its addressing flags with raw `strFlag`, so
    values are untrimmed and an empty string counts as absent:
    - `--execution-request-id`, `:60`
    - `--session-key`, `:70`
    - `--objective-id`, `:83`
    - `--mission-id`, `:94`, as `strFlag(…) ?? missionDisplayIdFromObjectiveRef(objectiveRef)`
    - `--project-id`, `:119`
  - The handlers read the same addresses through `protocol/flags.ts`:
    - `objectiveRefFlag` (`:137-140`) trims, and blank becomes `null`.
    - `missionRefFlag` (`:123-134`) lets an explicit value win **only when it is non-blank after
      trimming**, otherwise derives the mission from the objective display id. It returns the
      explicit value untrimmed.
  - A third normalisation sits between them. `validateObjectiveAddressing` (`protocol.ts:189-194`)
    uses `objectiveRefFlag` but pairs it with the raw `strFlag(…) ?? derived` mission form.
    `run-queue.ts:87` also reads `--mission-id` raw.
  - These rules already disagree. `--mission-id " " --objective-id coo:756.k7xm` derives no
    workspace from the mission, because `" "` is truthy and `??` never reaches the derivation. The
    request then falls through to the anchor workspace (`protocol.ts:135-151`). The handler's
    `missionRefFlag` ignores the blank and resolves `coo:756`, in the wrong workspace when the
    mission lives in a secondary one. `contract/protocol-commands.yaml:31-37` says the display id
    supplies the mission "when --mission-id is absent".
  - The derivation embeds five raw SQL reads in the dispatcher (`protocol.ts:62-107`), across
    `execution_requests`, `agent_sessions`, `objectives` and `missions`. A sixth address lookup,
    `resolveSessionId` (`protocol/missions.ts:134-143`), queries `agent_sessions` by key hash again.
- **Problem**:
  - Workspace derivation is ID resolution that decides the authorization workspace. The playbook
    ranks duplicated ID resolution as the highest drift risk, and these copies have drifted on
    blank and whitespace handling.
  - Each new addressing flag (the next one will be another `--*-id`) must be added to the
    derivation and to a handler reader, with no shared definition of "absent".
  - `protocol.ts` mixes dispatch with persistence. That hides the derivation's SQL from anyone who
    reads the protocol modules for data access.
- **Proposed change**: Add `backend/protocol/addressing.ts`:

  ```ts
  type ProtocolAddress = {
    executionRequestId: string | null; sessionKey: string | null;
    objectiveRef: string | null; missionRef: string | null;   // derived from objectiveRef when absent
    projectRef: string | null; workspaceHint: string | null;
  };
  readProtocolAddress(body): ProtocolAddress                  // the one normalisation
  deriveProtocolWorkspaceId(address, workspaceIds): Promise<string | null>  // moved from protocol.ts with its SQL
  ```

  - `missionRefFlag` and `objectiveRefFlag` become thin readers over `readProtocolAddress`, and
    keep their error messages.
  - `protocolWorkspaceId` becomes `deriveProtocolWorkspaceId(readProtocolAddress(body),
    workspaceIds)`.
  - `validateObjectiveAddressing` and `run-queue.ts:87` read the address too.
  - `resolveSessionId` moves next to the session-key lookup in `addressing.ts`, so there is one
    `agent_sessions`-by-hash read in the protocol layer (see Adjacent).
- **Sequenced steps**:
  1. Characterization tests in `protocol-objective-addressing.test.ts`. Pin today's results for a
     blank or whitespace `--mission-id` combined with a display-id `--objective-id`, for a padded
     objective UUID, and for a padded `--session-key`, each in a secondary workspace
     (`secondary-workspace-fixture.ts`).
  2. Add `addressing.ts` with a `{ legacyDerivation: true }` reading mode that reproduces the
     derivation's raw reads exactly. Move the SQL and switch every reader over. Step 1's tests pass
     unchanged, and there is no behaviour change.
  3. A separate, recorded behaviour-alignment commit drops the legacy mode, so the derivation uses
     the handlers' normalisation. Update the step-1 expectations to the contract-consistent result,
     where a blank `--mission-id` is treated as absent, and say so in the commit message.
- **Contract impact**: None. Step 3 brings behaviour into line with
  `protocol-commands.yaml` `objectiveAddressing` and changes no described flag or response.
- **Risk**: Medium. The derivation selects the authorization workspace, but every lookup stays
  membership-filtered (`IN (${placeholders})` over `callerWorkspaceMemberships()`), so a wrong
  derivation yields a 404, never cross-workspace access. Verification: `yarn test:backend`
  (`protocol-objective-addressing`, `mission-secondary-workspace`, `cross-workspace-authorization`,
  `project-reference-resolution`, `protocol-run-queue`), `yarn test:conformance`
  (`workspace-isolation`, `token-project-selection`), `yarn check:workspace-scoping`.

    | raw `Number(x ?? default)` | `--limit`/`--offset` on `project-items`, `mission-items` (`session.ts:144-145,155-156`) | `NaN` to the service, which then 400s (`core/service/protocol.ts:4543-4550`) | same | 0 |

  - **Two `--connection-method` readers.** `connectionMethodFlag` (`session.ts:67-79`) validates
    against `ATTACH_CONNECTION_METHODS` and 400s on anything else. `publicationStyleFlag`
    (`session.ts:48-50`) maps anything that is not `mcp` to `cli` silently. It re-implements core's
    `instructionStyleFor` (`core/service/protocol.ts:208-210`), which `objective-changes` already
    calls through the validating reader (`missions.ts:688`). So
    `delivery-summary-context --connection-method bogus` succeeds and
    `attach --connection-method bogus` is a 400.
- **Problem**:
  - The protocol is agent-facing through the CLI and hosted MCP. A malformed number gets a
    different answer, or none, depending on which subcommand received it.
  - The "Missing required flag: --expected-revision" answer to `--expected-revision abc` sends an
    agent to retry with the same value.
  - This is the protocol-side twin of the REST query-reader duplication that 2026-11-15 F2 fixed
    in `backend/http/query.ts`.
- **Proposed change**: In `flags.ts`, replace `intFlag` with
  `integerFlag(body, name, { min?, max?, fallback? }): number | undefined`. It parses strictly
  (`/^-?\d+$/`, safe integer) and answers 400 `invalid_input` naming the flag. Route all ten
  integer sites through it. Delete `publicationStyleFlag`, and call
  `instructionStyleFor(connectionMethodFlag(body))` at `session.ts:364,387` (after F3 moves
  `connectionMethodFlag` to `flags.ts`).
- **Sequenced steps**:
  1. Add `integerFlag` with a `{ lenient: 'parseInt' | 'number' }` escape hatch that reproduces
     the two lax rules exactly. Convert every site, preserving each site's current behaviour, and
     add unit tests for the table above. There is no behaviour change.
  2. A recorded behaviour-alignment commit:
     - remove the lenient modes;
     - make `--connection-method` validated on the two publication subcommands;
     - give `--expected-revision` an "invalid" rather than "missing" message.

     Add cases in `protocol-mission-summary.test.ts` and `artifacts.test.ts`.
- **Contract impact**: None for step 1. Step 2 turns malformed input that was silently
  reinterpreted into 400 `invalid_input`. `protocol-commands.yaml` already describes these flags as
  integers and `cli|mcp`, so no described shape changes. Record it in the commit message.
- **Risk**: Low. Verification: `yarn typecheck:backend`, `yarn test:backend`, `yarn lint`.

### F5. Type the Run Queue adapters on the generated DTOs and match entry references once
- **Value / Effort**: Low / S
- **Dimension**: Types and contracts; Duplication (no divergence yet)
- **Evidence**:
  - `protocol/run-queue.ts:41-54` hand-declares `QueueEntryProjection` and `QueueProjection`,
