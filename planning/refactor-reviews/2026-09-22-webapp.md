## Summary

`webapp` is in noticeably better shape than the area playbook's own baseline suggests. The two
largest hot spots the playbook calls out — `lib/queries.ts` (~1860 lines) and
`ResourcesPage.tsx` (~1500 lines) — have already been decomposed: `queries.ts` is now an 18-line
barrel re-exporting a `lib/queries/` directory split by resource family exactly as recommended,
and `ResourcesPage.tsx` no longer exists under that name. The query-key factory
(`lib/query-keys.ts`) is used consistently; only a handful of local, non-realtime queries
(desktop-bridge probes, mention-path lookups) use literal keys, which is appropriate since they
don't participate in invalidation. The API access boundary, hook location, contract-type reuse,
and desktop-parity boundaries are all clean — no violations found in any of those dimensions.
The two real findings are: (1) five components and two exports (~540 lines) that are completely
unreferenced anywhere in the repo, almost certainly left behind by decommissioned or superseded
UI, and (2) `QuickTaskBar.tsx`, which already delegates its presentational pieces to sibling
panel components but keeps all state, effects, and mutation wiring inline in one 723-line
component — the same container/presentation split that was already applied successfully to
`MissionBranchControl.tsx` (via `use-branch-actions.ts` / `use-branch-panel-view.ts`) has not yet
been applied here. Also recommended: refreshing the playbook's own hot-spot table, which is
actively misleading in its current form.

## Findings

### F1. Delete five fully unreferenced components and two dead exports
- **Value / Effort**: High / S
- **Dimension**: Dead and vestigial code
- **Evidence**:
  - `webapp/web/components/settings/CustomizationsPage.tsx` (110 lines, whole file, single export `CustomizationsPage`)
  - `webapp/web/components/agent-session/PermissionRequestCard.tsx` (161 lines, whole file, single export `PermissionRequestCard`)
  - `webapp/web/components/agent-session/RetryIntentCard.tsx` (124 lines, whole file, single export `RetryIntentCard`)
  - `webapp/web/components/workspaces/WorkspaceCreationFields.tsx` (91 lines, whole file, single export `WorkspaceCreationFields`)
  - `webapp/web/components/theme-toggle.tsx` (53 lines, whole file, single export `ThemeToggle`)
  - `webapp/web/components/ui.tsx:263` — `Modal` (one export among several used ones; only this one is dead)
  - `webapp/web/components/everhour/ProjectTimerButtons.tsx:52` — `ProjectTimerPill` (sibling export `useProjectTimerControls` in the same file is used elsewhere and stays)
  - `webapp/web/components/everhour/MissionTimerButtons.tsx:98` — `MissionTimerPill` (sibling exports `useMissionTimerControls` and `MissionTimerCircleButton` are used elsewhere and stay)
- **Problem**: Each symbol was verified with a repo-wide search (`webapp`, `cli`, `mcp`,
  `connectors`, `desktop`, `backend`, `packages`, `database`, `automations`, `auth`, including
  `.md` docs) and has zero references outside its own declaration — not even in tests, route
  tables, or lazy-loaded bundles. These read as remnants of features that were replaced or
  removed (a settings customizations panel, agent-session permission/retry card variants,
  a workspace-creation field group, a standalone theme toggle, timer "pill" variants) without a
  final cleanup pass. Dead exported components are actively misleading during future work: they
  look like available building blocks and cost a reader time to rule out.
- **Proposed change**: Delete the five whole files and their imports (there are none, by
  definition). Remove the `Modal`, `ProjectTimerPill`, and `MissionTimerPill` exports from their
  shared files, keeping the other exports in those files intact.
- **Sequenced steps**:
  1. Delete `CustomizationsPage.tsx`, `PermissionRequestCard.tsx`, `RetryIntentCard.tsx`,
     `WorkspaceCreationFields.tsx`, `theme-toggle.tsx`. Run `yarn typecheck:webapp` to confirm no
     hidden reference was missed by the grep-based search.
  2. Remove `Modal` from `ui.tsx`, `ProjectTimerPill` from `ProjectTimerButtons.tsx`,
     `MissionTimerPill` from `MissionTimerButtons.tsx`. Typecheck again.
  3. `yarn lint && yarn test:webapp` to confirm nothing else was quietly depending on these via a
     re-export barrel.
- **Contract impact**: None — none of these are referenced from `CONTRACT.md`, and they carry no
  REST/DTO surface of their own.
- **Risk**: Low. The main risk is a reference this review's grep missed (e.g., a dynamic
  `import()` keyed by a string built at runtime). None of these five components appeared in any
  `lazy(...)`/dynamic-import search during this review, and the typecheck/lint/test pass in the
  steps above is the guard.

### F2. Extract `QuickTaskBar`'s state/mutation logic into a dedicated hook
- **Value / Effort**: Medium / M
- **Dimension**: Module size and cohesion (container/presentation split)
- **Evidence**: `webapp/web/components/quick-task-bar/QuickTaskBar.tsx:61-723` (whole exported
  component body). The file already imports four presentational panels from sibling files —
  `AgentModelPickerPanel`, `ProjectPickerPanel`, `ResourcePickerPanel`, `StagedFilesRow` (all in
  `webapp/web/components/quick-task-bar/`) — but the orchestrating `QuickTaskBar` function itself
  holds 7 `useState` calls, 8 `useEffect` calls, half a dozen `useCallback` handlers, and the
  mutation hooks `useCreateMission`, `useLaunchObjective`, `useCreateInboxItem`,
  `useUpdateLaunchPreference`, `useUpdateObjective` (lines 91-334 for the state/effects block
  alone), interleaved with the composing JSX for those same panels.
- **Problem**: This is the same shape the playbook names as the recurring problem here: a screen
  component owning data fetching, form state, and mutation side effects alongside layout. The
  project's own established fix for this pattern is visible one file over —
  `MissionBranchControl.tsx` (856 lines) already extracted its decision/action logic into
  `use-branch-actions.ts` and `use-branch-panel-view.ts`, leaving the component itself as
  presentation composing named sub-pieces. `QuickTaskBar.tsx` did that for its rendered panels
  but not for its own state, so the component is still expensive to read or touch: any change to
  submit/staging/agent-selection behavior requires holding the whole 723-line function in your
  head, and any change to layout risks touching unrelated state wiring in the same diff.
- **Proposed change**: Extract a `useQuickTaskBar(defaultProjectId)` hook (new file
  `webapp/web/components/quick-task-bar/use-quick-task-bar.ts`) that owns the state
  (`objective`, `selectedProjectId`, `stagedFiles`, `isSubmitting`, `activeMenu`,
  `selectedResourceKey`, `submitError`, agent-model selection state), the effects that derive
  from them, the file-selection/removal handlers, and the mutation calls, and returns the values
  and handlers the component needs. `QuickTaskBar.tsx` becomes the composition of that hook's
  return value with the four existing panel components plus its own layout markup.
- **Sequenced steps**:
  1. Add `use-quick-task-bar.ts` and move the state/effect/handler block (current lines ~91-334)
     into it verbatim, exporting the same values under one return object. No behavior change.
  2. Update `QuickTaskBar.tsx` to call the hook and destructure its return value in place of the
     inline declarations; keep the JSX untouched except for the substituted references.
  3. Add or extend a `QuickTaskBar` render test (or a focused hook test if one doesn't already
     assert on staged-file add/remove and submit-error behavior) before landing, since this is
     the area's primary create-mission entry point.
- **Contract impact**: None — pure client-side restructuring, no REST/DTO surface touched.
- **Risk**: Medium. The effects have implicit ordering dependencies on each other (multiple
  `useEffect` blocks keyed off overlapping state) — moving them verbatim into a hook is safe, but
  don't reorder or merge them as part of this change. Cover with the render test in step 3 before
  landing; the existing `MissionBranchControl` extraction is a working precedent for the same
  move.

## Explicitly not recommended
- **Splitting `MissionBranchControl.tsx` into per-component files.** At 856 lines it's the only
  file over 800 lines in the area, and the playbook's original complaint — "branch UI plus branch
  decision logic" — is already resolved: the decision/action logic lives in
  `use-branch-actions.ts` and `use-branch-panel-view.ts`, and the file itself is seven cohesive,
  single-purpose UI components (`CopyIconButton`, `BranchCopyMenu`, `BranchModeToggle`,
  `BranchIdentity`, `MissionBranchSetupForm`, `BranchPanel`, `MissionBranchControl`) reading
  top-to-bottom in composition order. Splitting it into seven files would trade one readable file
  for seven that must be opened together to follow the same flow, for no cohesion gain. Leave it
  alone unless it grows further.
- **Consolidating `webapp/web/hooks/` and `webapp/web/lib/hooks/`.** The playbook flags this as a
  standing duplication risk, but `webapp/web/hooks/` no longer exists — all shared hooks already
  live under `webapp/web/lib/hooks/`. Nothing to do here; worth reflecting in F3's doc refresh.
