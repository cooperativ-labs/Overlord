## Rotation choice

The routine prompt scoped this run to `backend`. The rotation's override rule ("the user names
an area — always honor it") puts that ahead of the oldest-missing-report default. By that default
`webapp`, `core`, `cli`, `database`, `desktop`, and `platform-services` are all more overdue (none
has a report yet), and `agent-surfaces` (2026-07-29) is the oldest area that has one. This is the
eighth backend report in a row. The next unscoped run should take `webapp`.

seven previous backend reports. Those reports deep-read:

- the repository/service seam (08-04, 08-18)

landed in this range:

## Summary

The new REST boundary is well built and well placed. ADR 0051's request validation and response
conformance sit in `backend/http/` as small, single-purpose modules, and each module's header says
exactly what it does. The generated operation table removed a whole class of hand-maintained DTOs.
The route table in `app.ts` is still mostly wiring.

The debt is in the **route-wrapper layer around that boundary**, which grew by copying:

- **The `handle()` wrapper.** It is the one place where `requires`, the mutation nudge, and the JSON
  default live, and it is private to `app.ts`. The two extension routers re-declare its type, the
  agent-session routers carry a second wrapper that renders errors itself, and the two extension
  route suites run against hand-copied wrappers. Those copies authorize `requires` through
  `requirePermission` on the active workspace instead of production's
  `requireAnyWorkspacePermission`.
- **Test servers.** Twelve test files build their own Express app around a router, and only five of
  them mount the conformance and validation layers that `backend/AGENTS.md` step 8 asks for.
- **Query reading.** Query strings are read 32 times by hand, and `workspaceId` alone is read in
  four normalisations.

The highest-value refactor is **F1**: one exported route-handler factory in
`backend/http/route-handler.ts`, used by the app, the extension routers, and their tests. F1 removes
the one place where a test exercises a different authorization gate from production. **F3** (one
router test-app fixture) builds on it.

## Findings

### F1. One route-handler factory in `backend/http/`, used by the app, the extension routers and their tests
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Test structure; Abstraction fit (missing)
- **Evidence**:
  - `backend/app.ts:561-578` defines `handle(fn, { mutates, requires })`. It runs
    `requireAnyWorkspacePermission(options.requires)` (`rbac.ts:201-240`), awaits the handler,
    calls `pollAfterMutation()` (`:552`, over the eight loops at `:542-551`), and writes
    `res.json(result ?? { ok: true })`. It is module-private. `app.ts` passes it by value into
    `createEverhourExtensionRouter(handle, …)` (`:1745`) and `createGitHubExtensionRouter(handle,
    …)` (`:1751`).
  - Both extension routers re-declare its type by hand, identically:
    `ext/everhour/routes.ts:9-12` and `ext/github/routes.ts:21-24` (`type RouteHandler = (fn,
    options?: { mutates?; requires? }) => …`).
  - Both extension route suites replace it with a hand-written copy, `makeHandle()`
    (`ext/everhour/routes.test.ts:27-48`, `ext/github/routes.test.ts:35-56`). The copies have
    drifted from production in two ways:
    - They authorize `requires` with `requirePermission(options.requires, { workspaceId:
      getActiveWorkspaceId(), … })`, which is the ambient active-workspace gate, where production
      uses the organization-snapshot gate `requireAnyWorkspacePermission`.
    - They never call the mutation nudge.

    `ext/github/routes.ts:60` (`GET /ext/github/callback`, `requires: WORKSPACE_UPDATE`) is
    therefore tested under a gate that production does not use.
  - `agent-session-routes.ts:156-174` is a second production wrapper of the same shape. It renders
    `ServiceError` itself (`res.status(err.status).json({ error, code })`) where `apiErrorHandler`
    (`errors.ts:112-119`) would also carry `details`. It serves the three agent-session routers (19
    `handle(` calls).
  - Five route bodies in `app.ts` open-code the same async error forwarding that `handle` wraps,
    because they stream or set headers: `:619` (`/mcp`), `:1230` (storage serve), `:1293`
    (`streamRealtime`), `:1323` (`/sync/changes`), plus the try/catch callbacks at `:425` and
    `:456`. The pattern repeats at `connections/routes.ts:153` and `chat.ts:152`; those two have
    their own catch policies and stay as they are.
- **Problem**:
  - The wrapper is where route-level RBAC runs: the `requires` annotation that the playbook's RBAC
    integrity check names as one of the two sanctioned authorization paths. Any change to that gate
    (an audit hook, a token-scope rule) lands in `app.ts` and misses both test copies, which already
    use a different gate.
  - A route mounted through an injected `handle` has no compile-time link to the real signature.
    Adding an option means editing three type literals.
  - The agent-session wrapper is a second error renderer, and it has already dropped one envelope
    member.
- **Proposed change**:
  - Add `backend/http/route-handler.ts`. It exports:
    - `type RouteHandler`, the current signature;
    - `asyncRoute(fn: (req, res, next) => Promise<void>): RequestHandler`, which is the try/catch
      → `next` primitive;
    - `createRouteHandler({ onMutation }: { onMutation: () => void }): RouteHandler`, the current
      body of `handle`, built on `asyncRoute`.
  - In `app.ts`, define `handle` as `const handle = createRouteHandler({ onMutation:
    pollAfterMutation })`. All 186 call sites stay as they are.
  - The two extension routers import `type RouteHandler` and delete their copies.
  - The two extension suites call `createRouteHandler({ onMutation: () => {} })` and delete
    `makeHandle()`.
  - `agent-session-routes.ts`'s `handle` keeps its `ChannelRequest` cast but forwards every error
    with `next(err)`. The app's `apiErrorHandler` is mounted last and already serves this router,
    which is mounted at `app.ts:637`.
  - The five open-coded bodies in `app.ts` use `asyncRoute`.

  Import graph: `http/route-handler.ts` → `rbac.ts` (already imported by `app.ts` and both extension
  routers through `ext/resource-routes.ts`). Nothing in `rbac.ts` imports `http/`, so there is no
  cycle.
- **Sequenced steps**:
  1. Add `http/route-handler.ts` with a unit test that pins `requires` (403 via
     `requireAnyWorkspacePermission`), `mutates` (calls `onMutation` once, after success only), the
     `{ ok: true }` default, and `headersSent` passthrough. Point `app.ts` at it, with no call-site
     change.
  2. Point both extension routers and both extension suites at it. Expect
     `ext/github/routes.test.ts`'s `/callback` cases to now exercise production's gate. If a case
     fails, that is a real production behaviour the old copy hid. Record it and route it to
     `code-review`; do not change production to make the test pass.
  3. Make the agent-session wrapper forward errors. `agent-session-routes.test.ts` (which mounts
     `apiResponseConformance`) checks that the bodies still conform.
  4. Convert the five open-coded bodies to `asyncRoute`.
- **Contract impact**: None. No route, permission, status, or message changes. One body becomes
  closer to the contract: a `ServiceError` raised under the agent-session routers gains `details`
  when the core service supplies them. That is an additive member that `ErrorEnvelope` already
  declares. `agent-session-routes.ts` itself raises none with `details`.
- **Risk**: Low to medium, because it touches the route-level RBAC dispatch. The step-1 unit test
  is the guard. Verification: `yarn test:backend` (`ext/*/routes.test.ts`,
  `agent-session-routes.test.ts`, `api-boundary.test.ts`, `cross-workspace-authorization.test.ts`,
  `token-scope.test.ts`), `yarn contract:parity` (route registration order is unchanged),
  `yarn lint`.

### F2. Read query parameters through one helper module instead of 32 hand-written `typeof` checks
- **Value / Effort**: Medium / S
- **Dimension**: Duplication with divergence
- **Evidence**:
  - 32 `typeof req.query.<x> === 'string'` reads: `app.ts` 23, `agent-session-routes.ts` 4
    (`:744-746`, `:908-910`), `ext/github/routes.ts` 3 (`:27,56,70`), `chat.ts` 2 (`:76,92`).
  - `workspaceId` alone is read 12 times in four normalisations:

    | Shape | Sites |
    |---|---|
    | trimmed, `''` when absent | `app.ts:772` (diagnostics), `ext/github/routes.ts:27` (throws 400) |
    | raw, `null` when absent | `app.ts:1108` (webhooks; the service then trims, `webhooks.ts:187`) |
    | trimmed, `null` when empty | `app.ts:1195` (uploads) |
    | raw, `undefined` when absent | `app.ts:2081,2089,2100,2108,2118,2129,2140,2151` (agent catalog, launch settings) |

    So `?workspaceId=%20` reaches `resolveCatalogWorkspaceId` (`agent-catalog.ts:57-65`) and
    `resolveLaunchSettingsScope` (`execution/launch-settings.ts:90-98`) as a truthy `' '`. The
    webhooks and uploads routes treat the same value as absent.
  - Four query parsers are private to `app.ts`: `parseSeqCursor` (`:1266`), `parseProjectListLifecycle`
    (`:1274`, which re-spells `ProjectListLifecycle`'s three values), `isTruthyQueryFlag` (`:1282`),
    and the trimmed-or-null idiom at `:1696-1703` and `:2238-2241`.
  - `agent-session-routes.ts:175` has its own `optionalString` (trimmed, empty → null).
- **Problem**:
  - This is ID and scope input. The playbook ranks duplicated ID resolution as high drift risk, and
    the copies already disagree on whitespace and on empty-vs-absent.
  - The next route that takes `workspaceId` will copy whichever site is nearest.
  - The ADR 0051 validation layer checks these parameters but by design never hands the handler a
    parsed value, so the handler-side read stays, and it should be one read.
- **Proposed change**: Add `backend/http/query.ts`:

  ```ts
  queryString(req, name, { trim = true } = {}): string | null  // first value; non-strings → null
  queryFlag(req, name): boolean                                // the current isTruthyQueryFlag
  queryCursor(req, name): number | null                        // the current parseSeqCursor
  queryEnum<T>(req, name, values: readonly T[], fallback: T): T  // 400 on anything else
  ```

  Move `parseSeqCursor`, `isTruthyQueryFlag`, and `agent-session-routes.ts`'s `optionalString` there.
  `parseProjectListLifecycle` becomes `queryEnum(req, 'lifecycle', PROJECT_LIST_LIFECYCLES, 'active')`,
  with the tuple exported beside `ProjectListLifecycle` in `@overlord/contract`, or the generated
  schema's `.options`.
- **Sequenced steps**:
  1. Add the module with unit tests. Convert every site with options that **preserve** its current
     normalisation exactly (`{ trim: false }` where it is raw today; `?? undefined` /
     `?? ''` at the call). This step changes no behaviour.
  2. A separate, recorded behaviour-alignment commit: make `workspaceId` trimmed-or-absent
     everywhere. This changes `' '` from a 404/403 into the documented implicit-workspace fallback on
     the eight catalog and launch-settings routes. `launch-settings-persist.test.ts`,
     `agent-catalog-workspace.test.ts`, and `mission-secondary-workspace.test.ts` pin the explicit
     and fallback paths. Add one case for the whitespace value.
- **Contract impact**: None for step 1. Step 2 touches no described parameter shape, because
  OpenAPI types `workspaceId` as a string either way. Record the alignment in the commit message.
- **Risk**: Low. `yarn typecheck:backend`, `yarn test:backend` (the request-validation suites log any
  accepted-but-invalid request), `yarn lint`.

- **Dimension**: Test structure
- **Evidence**:

    - `ext/github/routes.test.ts:64-72`

  - Four suites mount **real, OpenAPI-described** routers without it, so their responses are never

    - `connections/connections.postgres-conformance.test.ts:1124-1142`, `:1482-1489`
    - `connections/profile-connections.postgres-conformance.test.ts:546`
    - `connections/github-connections.postgres-conformance.test.ts:583`

- **Problem**:
  - Whether a router's responses are conformance-checked depends on which file the test author

  - The connections routers are the newest described surface (contract 169.x, "Describe account

- **Proposed change**: Add `backend/http/test-app-fixture.ts`, following the `*-test-fixture.ts`

  `runner-session-auth.test.ts`, `execution/runner-claim-http.test.ts`,
  `poll-loop-shutdown.test.ts`) keep their own minimal app and use only `listenForTest`.
- **Sequenced steps**:
  1. After F1 step 1, add the fixture. Convert the five suites that already mount the sandwich
     (`chat.test.ts`, both extension suites, `agent-session-routes.test.ts`, and
     `response-conformance.test.ts`'s mounted case). This is a pure move.
  2. Convert the `app.listen(0…)` blocks to `listenForTest`. This is mechanical, with one commit
     per directory.
  3. Convert the four connections sites to `routerTestApp`. This enables checks that were never
     run. **A non-conforming response found here is a contract defect to route to `code-review`
     or `drift-review`, not something this refactor fixes**. If one appears, land the fixture for

### F5. One path-template parser, one member-path formatter and one malformed-JSON body inside `backend/http/`
- **Value / Effort**: Low / S
- **Dimension**: Duplication (no divergence yet)
- **Evidence**:
  - **Two parsers of the OpenAPI path-template syntax.** `request-validation.ts:116-130`
    (`pathParameters`) splits `operation.path` and the request path by `/` and maps `{name}`
    segments by index. `api-operations.ts:22-55` (`templateSegments`, `matchOperation`) splits the
    same templates and compares segments with a `{` test. A third helper,
    `express-routes.ts:20-22` (`toOpenapiPath`), converts the Express syntax and is a different
    job, so it stays.
  - **Two `memberPath` formatters** for Zod issue paths, with different output:
    `request-validation.ts:88-95` writes `objectives[0].title`, and `response-conformance.ts:83-89`
    writes `body.objectives[0].title`.
  - **Two copies of the malformed-JSON answer.** `request-validation.ts:61-67` (`isMalformedJson`)
    and `:198-201` (`MALFORMED_JSON_ERROR`) duplicate `errors.ts:53-63`
    (`apiErrorFromBodyParser`'s `entity.parse.failed` branch), with the same message and code.
- **Problem**: These are small, but they sit on the boundary that defines how a request maps to an
  operation. A change to the template syntax (for example, a future `{name*}` wildcard), or to the
  wording of the `invalid_json` message, would have to land twice.
- **Proposed change**:
  - Export `templateSegments` and a `bindPathParameters(operation, requestPath)` from
    `api-operations.ts`, and have `request-validation.ts` use them.
  - Export one `issuePath(path, prefix?)` from `request-validation.ts` for `response-conformance.ts`.
  - Export an `INVALID_JSON` `ApiError` factory and an `isBodyParserError(error, type)` predicate
    from `errors.ts`. The validation layer renders through them.
- **Sequenced steps**: One commit. `http/request-validation.test.ts` and
  `http/response-conformance.test.ts` pin both message formats, and `errors.test.ts` pins the
  envelope.
- **Contract impact**: None.
- **Risk**: Negligible. Do this alongside the next change in `backend/http/`, not as its own
  mission if the queue is full.
