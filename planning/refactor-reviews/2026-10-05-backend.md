## Summary

The backend is in the best shape of the four reports: every finding from the last cycle landed
within a week, `protocol.ts` left the over-800 list, `db.ts` lost its ambient accessors, and the
4,300 non-test lines added since are all the contract v152 feature. That feature was built the way
the last three reports asked for — rules in `packages/core/service/chat/`, thin routers, injected
`db`, Kysely-derived row types, Postgres-conformance tests from day one — so the structural
findings here are small seams it left at its edges rather than decay. The single highest-value
refactor is **F1**: the workspace agent catalog is now read by six functions with three different
fallback and validation rules (two in the backend, three in core, one of them the chat proposal
path that decides whether a proposal is creatable), and the chat feature added two of those copies
in one week. Below it: the two new routers re-implement the `{ error, code }` envelope the app's
error handler already produces for every `ServiceError` (F2); the backend now has seven hand-rolled
poll timers and only the two chat ones can be stopped (F3); and the eight backend Postgres
conformance tests each carry their own schema-per-test bootstrap (F4).

## Findings

### F1. Give the workspace agent catalog one reader, in core, with the instance-default fallback injected from the backend
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence; Layering and boundary leaks
- **Evidence**:
  - `backend/chat/engine.ts:66-78` — fifth and newest copy: raw `SELECT settings_json FROM workspaces WHERE id = ? AND deleted_at IS NULL`, an **unguarded** `JSON.parse`, and a fallback to `resolveInstanceAgentCatalog({ configCatalog: loadConfig().agentCatalog })` from `cli/src/agent-catalog.ts` / `cli/src/config.ts` (`:4-5`) when `stored.agents` is absent.
  - `backend/execution/launch.ts:134-178` — the original: `readWorkspaceSettings` (guarded parse, 500 on a missing row), `readStoredCatalog` (shape check on `agents`), `instanceAgentCatalog()` fallback, plus `persistCatalog` which *seeds* the instance default into `settings_json`.
  - `packages/core/service/project-execution-target.ts:608-630` — third copy: guarded parse, `deleted_at IS NULL`, no instance fallback, projects only `launchDefaults`.
  - `packages/core/service/chat/tools.ts:505-516` and `packages/core/service/chat/proposals.ts:110-118` — the two core fallbacks used when `ChatOptions.assignmentCatalog` is not injected: no `deleted_at` filter, unguarded `JSON.parse(row?.settings_json ?? '{}')`, no instance fallback. `ChatProposals.validateAssignment` (`:119-`) rejects a proposal with `proposal_not_creatable` when `catalog.agents[assignment.agent]` is missing, so a workspace with no stored `agentCatalog` behaves differently depending on which caller constructed the service.
  - `backend/workspace-settings.ts:19-26` — sixth reader of the same column (`readSettingsJson`, 404 on a missing row) for an unrelated key.
  - `backend/index.ts:701` and `:2424` inject `chatEngine().assignmentCatalog` into `Conversations` and `ChatRuns`; `GeminiRunSession.read` (`backend/chat/gemini-runtime.ts:408`) constructs `new ChatProposals(this.runs.db, this.runs.options)` and so inherits whichever option the caller passed.
- **Problem**: "The effective agent catalog for a workspace is the stored one, else the instance default" is a rule with one owner in the contract (REST API Layer owns the workspace agent catalog routes) and five implementations in code, two of which disagree on the fallback and three of which disagree on what a malformed or soft-deleted row means. The chat feature had to re-derive the rule to validate proposals, and did so twice. The next consumer (the MCP server exposing the catalog, or a CLI command) will copy it a seventh time.
- **Proposed change**: One `readStoredWorkspaceAgentCatalog(db, workspaceId): Promise<StoredAgentCatalog | null>` in `packages/core/service/workspace-agent-catalog.ts` (new, ~40 lines) owning the `SELECT`, the `deleted_at IS NULL` predicate, the guarded parse, and the `agents` shape check (`launch.ts:170-178` moved verbatim). The instance default stays a backend concern because `cli/src/config` cannot be imported from core: a `backend/agent-catalog.ts` (new, ~25 lines) exports `resolveWorkspaceAgentCatalog(db, workspaceId)` = stored ?? `instanceAgentCatalog()`, which both `launch.ts` and `engine.ts` call. `project-execution-target.ts`, `tools.ts`, and `proposals.ts` call the core reader and drop their inline SQL; `engine.ts` loses its SQL and its two `cli/src` imports.
- **Sequenced steps**:
  1. Add the core reader with SQLite + Postgres unit tests mirroring `launch.ts`'s current semantics (missing row → `null`, malformed JSON → `null`, missing `agents` → `null`). Zero call-site changes.
  2. Point `project-execution-target.ts:608-630`, `tools.ts:505-516`, `proposals.ts:110-118` at it. `yarn test:core` plus the chat and proposals Postgres conformance suites.
  3. Add `backend/agent-catalog.ts`; point `launch.ts` (`readStoredCatalog`, `instanceAgentCatalog`) and `engine.ts:66-78` at it; delete `engine.ts:4-5`. `persistCatalog` keeps its seeding behavior untouched.
- **Contract impact**: None — no route, DTO, or stored shape changes. Step 3 makes `engine.ts` tolerate a malformed `settings_json` the way `launch.ts` already does (fallback instead of a thrown parse error that fails every chat run for that workspace with `provider_error`); flag it in the PR as the intended divergence fix.
- **Risk**: The chat Postgres conformance tests (`packages/core/service/chat/chat.postgres-conformance.test.ts`, `proposals.postgres-conformance.test.ts`, `backend/chat/gemini-runtime.postgres-conformance.test.ts`) exercise both the injected and the fallback catalog paths; `backend/launch.test.ts` covers seeding. Run `yarn test:core`, `yarn test:backend`, and `yarn test:conformance`.

### F2. Let the chat and connections routers use the app error handler instead of re-implementing the `{ error, code }` envelope and the owner gate
- **Value / Effort**: Medium / S
- **Dimension**: Abstraction fit (excess); Duplication with divergence
- **Evidence**:
  - `backend/chat.ts:22-27` and `backend/connections/routes.ts:29-34` — byte-identical `owner()` gate (`chat_unavailable` when not Cloud, `not_found` when no owner).
  - `backend/chat.ts:28-36` (`route`) and `:43-51` (middleware) and `backend/connections/routes.ts:20-24` (`sendError`) and `:35-41` (`route`) — three copies of "if `ChatError` then `res.status(e.status).json({ error: e.message, code: e.code })` else 500" with two different 500 messages (`'Chat request failed'` / `'Connection request failed'`).
  - `ChatError extends ServiceError` (`packages/core/service/chat/store.ts:63`), and the app error handler at `backend/index.ts:2353-2360` already renders every `ServiceError` as `{ error: message, code, details? }` — the same body — for every other route, including the sibling `POST /api/projects/:id/repository-reads` (`index.ts:1685`) that the same feature added through `handle()`.
  - `backend/chat.ts:132-205` (the SSE route) legitimately keeps its own error path because headers may already be sent; it is not part of this finding.
- **Problem**: Two routers carry a private copy of transport policy the app already owns, so the body shape, the 500 text, and (if it is ever added) `details` handling can drift between `/api/chat/*`, `/api/connections/*`, and every other `/api` route. The contract's "Error bodies are `{ error, code }` with the closed `ChatErrorCode` set" is enforced in three places instead of one.
- **Proposed change**: Add one `backend/chat/router-support.ts` exporting `chatOwnerGate(options)` (the shared `owner()` closure) and `chatRoute(fn)` = `(req, res, next) => fn(req).then(v => res.json(v)).catch(next)`; both routers use them and delete their local `route`/`sendError`/middleware copies. The app handler produces the envelope. The 500 fallback becomes the app handler's `{ error: message, detail: message }` (`index.ts:2380-2382`), which is what every other route already returns; if the chat routes must keep a generic 500 text for privacy, add that one rule to the shared helper, not to each router.
- **Sequenced steps**: 1. Add the helper with a unit test asserting a `ChatError` reaches `next` unchanged. 2. Convert `connections/routes.ts` (3 routes). 3. Convert the JSON routes in `chat.ts` (14 routes), leaving the SSE handler as is. `backend/chat.test.ts` and `backend/connections/connections.postgres-conformance.test.ts` build their own Express apps and must mount the app error handler (or an equivalent) — that is the one test edit.
- **Contract impact**: None; status codes and `{ error, code }` bodies are unchanged for every `ChatError`. Only the body of a non-`ChatError` 500 changes shape (gains `detail`), which the contract does not specify.
- **Risk**: Low. `yarn test:backend`; the two test files above assert status and `code` on every error path.

### F3. One poll-loop base with `stop()` for the backend's seven timers
- **Value / Effort**: Medium / M
- **Dimension**: Duplication with divergence (worker shape); Abstraction fit (missing)
- **Evidence**:
  - Seven timer owners: `backend/worker-job-poller.ts:54-62` (four workers extend it: delivery compose, run-queue dispatch, live activity, push, notification), `backend/realtime.ts:167-178`, `backend/webhook-dispatcher.ts:65-75`, `backend/run-queue-dispatch-worker.ts:324` (sweep), `backend/chat-worker.ts:67-82`, `backend/chat-notification-dispatcher.ts:90-100`.
  - Each has the same `timer`/`polling|running` guard/`start()`/`poll|tick()` quartet. Only the two new chat loops have `stop()` and `unref()` their timer; `WorkerJobPoller`, `RealtimeHub`, and `WebhookDispatcher` have no `stop()` at all.
  - `stopOnTermination` (`backend/chat-worker.ts:39-51`) installs SIGTERM/SIGINT handlers that stop the two chat loops and re-raise the signal (`backend/index.ts:2432-2435`); the other five loops keep running until the process dies.
  - `ChatNotificationDispatcher.tick()` (`chat-notification-dispatcher.ts:102-117`) is `WorkerJobPoller.poll()` with `ChatNotifications.claimDue` in place of `claimNextWorkerJob` — the claim differs by contract (`backend/AGENTS.md`: "Conversation notifications use `chat_notifications`, not `worker_jobs`"), the loop does not.
  - `backend/index.ts:564-569` and `:619-624` — the two hand-maintained lists of six `pollNow()` nudges after a mutation; the chat loops are (correctly) not on them, but any future loop must be added in two places.
  - The 2026-09-28 report declined a shared `PollingLoop` for `RealtimeHub` + `WebhookDispatcher` as Low/S with two loops; this week added two more loops with a third shape (stoppable, unref'd).
- **Problem**: Graceful shutdown exists for 2 of 7 loops because the mechanism was written inside the chat feature instead of where the loops live. A deploy's SIGTERM stops chat work and then the other dispatchers die mid-job (their leases recover them, but that is the recovery path, not shutdown). Each new loop copies ~20 lines and chooses its own stop/unref policy.
- **Proposed change**: Add `backend/poll-loop.ts`: `abstract class PollLoop { constructor({ intervalMs, unref? }); start(); stop(); pollNow(); protected shouldPoll(); protected abstract tick(): Promise<void> }` holding the timer, the re-entrancy guard, and the catch-and-log. `WorkerJobPoller extends PollLoop` (its `poll()` becomes `tick()`; subclasses unchanged); `RealtimeHub`, `WebhookDispatcher`, `ChatNotificationDispatcher`, and `ChatWorker` (keeping its concurrency map and `renew` timer) move onto it. `stopOnTermination` moves to `backend/poll-loop.ts` and takes the list of loops; `index.ts` registers all seven. The `pollNow()` nudge lists can then become one array.
- **Sequenced steps**: 1. Add `PollLoop` with a unit test (start idempotent, stop clears, re-entrancy, `shouldPoll`). 2. `WorkerJobPoller` extends it — pure move, `worker-job-poller.test.ts` unchanged. 3. `ChatNotificationDispatcher` and `ChatWorker`. 4. `RealtimeHub` and `WebhookDispatcher` (keep their 500 ms / `POLL_INTERVAL_MS` values and the realtime heartbeat timer as a second loop or a separate timer). 5. Move `stopOnTermination`, register every loop, collapse the two `pollNow()` lists.
- **Contract impact**: None. `CONTRACT.md` §6 describes the webhook dispatcher as "a `RealtimeHub`-style singleton polling loop", which this preserves.
- **Risk**: `unref()` must stay opt-in (the chat loops unref; the others do not and tests rely on the process staying alive). `yarn test:backend` — `worker-job-poller.test.ts`, `chat-worker-shutdown.test.ts`, `realtime*.test.ts`, `webhook-dispatcher*.test.ts`, `chat-notifications.postgres-conformance.test.ts`.

### F4. One Postgres schema-per-test bootstrap for the backend conformance suites
- **Value / Effort**: Medium / S
- **Dimension**: Test structure
- **Evidence**:
  - Eight backend test files open a `pg.Pool`, `CREATE SCHEMA <random>`, build a scoped client with `search_path`, run `migratePostgres`, and `DROP SCHEMA … CASCADE` on cleanup: `backend/chat-notifications.postgres-conformance.test.ts:55-80`, `backend/chat/gemini-runtime.postgres-conformance.test.ts:130-155`, `backend/connections/connections.postgres-conformance.test.ts:35-66`, `backend/token-project-selection.postgres-conformance.test.ts:50-72`, `backend/token-workspace-consent.postgres-conformance.test.ts:40-62`, `backend/workspace-isolation.postgres-conformance.test.ts:57-83`, `backend/workspaces.postgres-conformance.test.ts:53-78`, `backend/mission-project-move.test.ts:45-69`.
  - Two idioms: the three new chat/connections files use a `session` connection plus a second scoped `Pool` (`options: -c search_path=…`, `max: 6`); the five older files use an `admin` client. Six more copies exist in `packages/core` and `database/src` (outside this area's roots).
  - `backend/test-helpers.ts` has no Postgres helper; the SQLite branch (`openInMemoryDatabase` + `createSqliteClient`) is also repeated in each file's `adapters` loop.
- **Problem**: The three chat conformance suites (2,354 lines, the deepest tests the new feature has) each start with 30 lines of infrastructure that the previous report's F6 removed from the SQLite side. A change to how conformance schemas are provisioned (pool size, `search_path` quoting, ledger pruning) is eight edits in the backend alone, and the two idioms will diverge the first time one of them needs a fix.
- **Proposed change**: `createConformanceDatabase(adapter: 'sqlite' | 'postgres', prefix: string): Promise<{ db: DatabaseClient; cleanup(): Promise<void> }>` in `backend/test-helpers.ts`, plus `conformanceAdapters()` returning `['sqlite', …('postgres' when TEST_DATABASE_URL)]`. Convert the eight files. If the `core` review wants the same helper, it is a one-file move to `packages/core/test-support/`.
- **Sequenced steps**: 1. Add the helper, modelled on the newer `session` + scoped-pool idiom (it is the one that bounds `max`). 2. Convert the three chat/connections files (same idiom, pure move). 3. Convert the five older files one per commit, watching for a test that depended on the `admin` idiom's connection semantics.
- **Contract impact**: None.
- **Risk**: Test-only. `yarn test:backend` (SQLite path) and `yarn test:conformance` with a `TEST_DATABASE_URL`.
