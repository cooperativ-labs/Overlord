## Summary

The area playbook's own baseline (recorded at contract v35) is largely stale in a good way: both
of its two worst hot spots have already been fixed by the team without a formal review —
`lib/queries.ts` is now a 19-line barrel re-exporting a `lib/queries/*` directory split by
resource family (missions, projects, webhooks, run-queues, …), and the legacy `web/hooks/`
directory the playbook flagged for consolidation no longer exists at all. `MissionCard.tsx` has
likewise been split into eight small, single-purpose files (`MissionCardBody`,
`MissionCardPrimitives`, `MissionCardSurface`, `MissionCardHoverFooter`,
`MissionCardStateOverlay`, `SortableMissionCard`, …), which is genuinely the target shape the
playbook asks other screens to copy. The remaining debt is smaller and more scattered than the
baseline suggested: one real boundary-scope gap (webapp reaches directly into `packages/core/`
service internals that CONTRACT.md scopes to protocol/REST/CLI/database), a handful of
independently-reimplemented small helpers that have already drifted (member display name,
date formatting), one component that never got the `MissionCard`-style split
(`InboxMissionCard.tsx`), and one copy-pasted permission check. None of this requires touching a
stable interface; all of it is landable in isolated, low-risk steps. Component-level test coverage
is thin (47 test files total, concentrated in `lib/`), which is noted as a precondition rather
than a separate finding — it does not block any of the sequenced steps below, but it means the two
component-level findings should land with a smoke test added first.

## Findings

### F1. `webapp` reaches directly into `packages/core/service/` internals CONTRACT.md doesn't scope to it

- **Value/Effort**: High / M
- **Dimension**: Layering and boundary leaks (#2); Types and contracts (#5)
- **Evidence**:
  - CONTRACT.md §1 (Protocol Layer, "Owns"), line 1098: "The `packages/core/` protocol/service
    core source package: shared service functions, repository helpers, and generated database
    types used by **protocol, REST, CLI tests, and database harnesses**." Webapp is not listed.
  - 17 import sites across 10 webapp files reach directly into `packages/core/service/` via
    3–5-level relative paths:
    `webapp/web/components/projects/ProjectRepositoryContext.tsx:7`,
    `webapp/web/components/projects/project-settings/LaunchPage.tsx:18`,
    `webapp/web/components/objectives/AgentLaunchFooter.tsx:15`,
    `webapp/web/lib/local-target-client.ts:3-4`,
    `webapp/web/lib/local-target-client.test.ts:4,8`,
    `webapp/web/lib/latch-session-client.ts:3,11`,
    `webapp/web/lib/latch-discovery-client.ts:13`,
    `webapp/web/lib/api/local-target.ts:1-2`,
    `webapp/web/lib/local-target-branch.ts:3-4`,
    `webapp/web/lib/useRepositoryMentionOptions.ts:4`,
    `webapp/web/lib/resource-observations.ts:4`,
    `webapp/web/lib/device-identity.ts:1`.
  - Almost all are `import type` (compile-time only), but
    `webapp/web/lib/latch-session-client.ts:3` imports the runtime function
    `isLatchSessionAbsentMessage` from `packages/core/service/latch-session-absent.ts` — that
    file's own docstring ("Kept free of Node imports so the mission-panel client can classify
    prune/remove without bundling spawn") shows the original author already knew it would be
    bundled into the webapp, i.e. this is a deliberate, working pattern, just an undocumented one.
  - `desktop/src/preload.ts` and `desktop/src/local-target-bridge.ts` import the *same*
    `packages/core/service/local-target/*` types to implement the other end of the
    `window.overlord.invokeLocalTarget(call)` bridge that CONTRACT.md §10 (Desktop Shell)
    documents — confirming this is a real, shared, three-party (core/desktop/webapp) type
    contract for the local-target/Latch bridge that just isn't named as one anywhere.
- **Problem**: `packages/core` is the one module CONTRACT.md explicitly says "no component may
  directly access another's internals" applies to, scoped to a named consumer list that omits
  webapp and desktop. In practice both already depend on it for the local-target/Latch bridge
  types, through brittle multi-level relative paths that will silently break (a TS error, not a
  runtime one, since it's mostly types) the next time `packages/core/service/` is reorganized —
  which is a live risk, since `packages/core` is core's own rotation-review target next.
- **Proposed change**: Do not try to eliminate the dependency (there is no sanctioned public
  package for it today, and manufacturing one is a `packages/contract`-sized effort out of scope
  for a behavior-preserving pass). Instead, collapse the 17 scattered import sites into one
  declared seam and document it as what it already is.
- **Sequenced steps**:
  1. (S) Add `webapp/web/lib/local-target-types.ts` that re-exports exactly the types and the two
     pure helpers webapp consumes (`LocalTargetBridgeCall`, `CapabilityResult`,
     `BranchObservationResult`, `BranchListResult`, `RepositoryTreeResult`, `ResourceObservation`,
     `DiscoverLatchResult`, `InspectLatchSessionResult`, `OpenLatchSessionResult`,
     `StopLatchSessionResult`, `CapabilityFailure`, `LocalTargetErrorCode`,
     `isLatchSessionAbsentMessage`, `ClientDeviceIdentity`, and the `latch-invocation.ts` exports
     used by `AgentLaunchFooter.tsx`/`LaunchPage.tsx`), mirroring the existing
     `webapp/shared/contract.ts` re-export pattern.
  2. (S) Update the 10 files above to import from that one facade instead of their own deep
     relative path. Pure import-path substitution — no signature or behavior changes.
  3. (Doc only) Amend CONTRACT.md §1's `packages/core` "Owns" bullet to add "and the
     local-target/Latch bridge type surface consumed read-only by `desktop` (bridge
     implementation) and `webapp` (bridge caller, type-only plus the two pure classifier
     functions in `latch-invocation.ts` / `latch-session-absent.ts`)". This documents
     already-shipped, already-tested behavior — no interface changes, so no version bump.
- **Contract impact**: Additive documentation only; no version bump. If the team later decides
  this dependency should be cut instead of documented, that is a separate, larger change (extract
  a `packages/local-target-contract` sibling to `packages/contract`) and would need its own
  proposal — flagging it here as the alternative, not recommending it now.
- **Risk**: Low. Step 1–2 are mechanical import-path edits with no runtime change (verified by
  `yarn typecheck:webapp` and `yarn webapp:build:prod`, which already exercise every one of these
  files transitively).

### F2. Member display-name/initials logic duplicated and already diverged

- **Value/Effort**: Medium / S
- **Dimension**: Duplication with divergence (#3)
- **Evidence**: `webapp/web/components/MissionMemberSelect.tsx:21-26` —
  `memberLabel` falls back `displayName → email → 'Member'`. `webapp/web/pages/MissionCardPrimitives.tsx:158-163`
  — the same-named `memberLabel`/`memberInitials` pair falls back
  `displayName → handle → email → 'Member'`. Both compute `memberInitials` as
  `memberLabel(member).slice(0, 2).toUpperCase()`.
- **Problem**: Two independent copies of the same "how do we label a workspace member" rule have
  already drifted: a member with no `displayName` but a `handle` shows their handle in the mission
  card family and shows their email (or "Member") in the assignee-select dropdown. This is exactly
  the drift the review looks for — same rule, two owners, silently different behavior depending on
  which screen renders it.
- **Proposed change**: Extract one `memberLabel`/`memberInitials` pair into a shared module (e.g.
  `webapp/web/lib/member-display.ts`) and have both call sites import it. Preserve the *more
  complete* fallback chain (`displayName → handle → email → 'Member'`) as the single
  implementation, since that is the one already shipped in the mission-card surfaces.
- **Sequenced steps**:
  1. (S) Add `webapp/web/lib/member-display.ts` with `memberLabel`/`memberInitials`, using the
     3-way fallback from `MissionCardPrimitives.tsx`.
  2. (S) Point `MissionMemberSelect.tsx:21-26` and `MissionCardPrimitives.tsx:158-163` at the
     shared module; delete both local copies.
- **Contract impact**: None — internal UI helper, no DTO or REST surface involved.
- **Risk**: Low, but behavior-visible: `MissionMemberSelect.tsx`'s dropdown will start showing a
  member's handle where it previously showed their email or "Member". Call this out in the PR
  description as an intentional behavior unification, not a silent side effect.

### F3. Four independent, diverging `formatDate`/`formatTimestamp`/`relativeTime` implementations

- **Value/Effort**: Medium / S
- **Dimension**: Duplication with divergence (#3); Abstraction fit — missing (#4)
- **Evidence**:
  - `formatDate`: `webapp/web/components/MissionSharedStateFooter.tsx:9-12` and
    `webapp/web/components/MissionArtifactsSection.tsx:35-38` are identical
    (`toLocaleString()`, falls back to the raw ISO string on an invalid date).
    `webapp/web/components/settings/UserTokensPage.tsx:85-90` and
    `webapp/web/components/settings/WebhooksPage.tsx:87-96` both handle `null` and invalid dates
    with an em-dash, but format differently (`toLocaleDateString` short date-only vs
    `toLocaleString` with a time component) and are not shared with each other or with the first
    pair.
  - `relativeTime`: `webapp/web/components/runner/RunnerStatusModal.tsx:43` vs
    `webapp/web/components/activity-feed/activity-feed-model.ts:96` (different signatures —
    the latter takes an explicit `nowIso` for testability, the former reads `Date.now()` inline).
  - `formatTimestamp`: `webapp/web/components/LiveActivityFeed.tsx:50` vs
    `webapp/web/components/LiveFileChangeCard.tsx:16`.
  - `webapp/web/lib/` has no shared date-formatting module today (confirmed by listing
    `webapp/web/lib/*date*`/`*time*`/`*format*`, which returns only `due-datetime.ts`, an
    unrelated due-date parser).
- **Problem**: Six call sites, three name patterns, at least two genuinely different rendering
  rules for the null/invalid case. This is exactly the kind of "missing abstraction" the review
  looks for: an open-coded three-line sequence repeated with small, uncoordinated variations.
- **Proposed change**: Add `webapp/web/lib/format-date.ts` exporting `formatDate` (date-only) and
  `formatDateTime` (with time), each taking the nullable-ISO input and the em-dash-on-invalid
  convention already used by the two settings pages, plus `relativeTime(iso, nowIso)` using the
  already-testable signature from `activity-feed-model.ts`. Migrate call sites one at a time,
  matching each site's current output.
- **Sequenced steps**:
  1. (S) Add `webapp/web/lib/format-date.ts` with `formatDate`/`formatDateTime`/`relativeTime`.
  2. (S) Migrate `UserTokensPage.tsx` and `WebhooksPage.tsx` to `formatDate`/`formatDateTime`
     (no output change — same format strings, now shared).
  3. (S) Migrate `MissionSharedStateFooter.tsx` and `MissionArtifactsSection.tsx` to
     `formatDateTime` (their existing behavior, `toLocaleString()` with raw-string fallback,
     becomes an explicit third variant if it needs to stay distinct — or unify with
     `WebhooksPage.tsx`'s variant if the raw-string fallback isn't load-bearing anywhere).
  4. (S) Migrate `RunnerStatusModal.tsx`, `LiveActivityFeed.tsx`, `LiveFileChangeCard.tsx` to the
     shared `relativeTime`/`formatTimestamp`.
- **Contract impact**: None.
- **Risk**: Low; each step is independently landable and each site's rendered output is easy to
  diff before/after in a snapshot or manual check.

### F4. Workspace operator/admin check copy-pasted across four settings pages

- **Value/Effort**: Medium / S
- **Dimension**: Abstraction fit — missing (#4)
- **Evidence**: The identical three-line sequence —
  `const members = useWorkspaceMembers(workspaceId); const operator = (members.data ?? []).find(m => m.isOperator); const isAdmin = operator?.isAdmin ?? false;`
  — appears at
  `webapp/web/components/workspaces/workspace-settings/GeneralPage.tsx:20-23`,
  `webapp/web/components/workspaces/workspace-settings/ExecutionTargetsPage.tsx:205-208`,
  `webapp/web/components/workspaces/workspace-settings/DangerZonePage.tsx:31-33`, and (as
  `operatorIsAdmin`) `webapp/web/components/workspaces/workspace-settings/MembersPage.tsx:52-55`.
- **Problem**: Four call sites re-derive the same "am I an admin of this workspace" fact from
  first principles. It hasn't drifted yet (unlike F2), but it is the same rule with four owners,
  which is exactly the setup that produces the next drift the moment one page's requirements
  change (e.g. someone adds a manager-role carve-out to one page and not the others, as
  `MembersPage.tsx` already partially does with its separate `operatorIsManager` check).
- **Proposed change**: Extract a `useWorkspaceOperatorRole(workspaceId)` hook in
  `webapp/web/lib/hooks/` returning `{ members, operator, isAdmin }`, and use it at all four call
  sites (and any future one).
- **Sequenced steps**:
  1. (S) Add `webapp/web/lib/hooks/use-workspace-operator-role.ts`.
  2. (S) Swap the four call sites to use it; delete the four inline copies.
- **Contract impact**: None.
- **Risk**: Low — one hook, four mechanical call-site swaps, identical output.

### F5. `InboxMissionCard.tsx` bundles two full container components the sibling `MissionCard` family already shows how to split

- **Value/Effort**: Medium / M
- **Dimension**: Abstraction fit — container/presentation split (area playbook check)
- **Evidence**: `webapp/web/components/InboxMissionCard.tsx` is 752 lines holding
  `UnassignedInboxMissionCard` (lines 80-288, ~208 lines: form state, project/resource pickers,
  save/run/delete mutations, and layout all inline) and `PromotedInboxMissionCard` (lines
  288-511, ~223 lines: a second, largely parallel form-state-plus-mutation-plus-layout block),
  plus a shared `InboxCardShell` (from line 511). Compare with
  `webapp/web/pages/MissionCard.tsx` (35 lines) delegating to `MissionCardBody.tsx` (165),
  `MissionCardPrimitives.tsx` (274), `MissionCardSurface.tsx` (72),
  `MissionCardHoverFooter.tsx` (161), `MissionCardStateOverlay.tsx` (31), and
  `SortableMissionCard.tsx` (139) — the target shape the area playbook names explicitly.
- **Problem**: This is the one place in the reviewed hot-spot list where the established
  container/presentation split pattern wasn't applied, even though a near-identical card family
  right next to it (`pages/MissionCard*`) demonstrates the shape to copy. No test file exists for
  either `InboxMissionCard.tsx` or the two components inside it.
- **Proposed change**: Split along the existing internal seam — it is already two seams, not one:
  1. Extract `UnassignedInboxMissionCard`'s form state and mutations into a
     `useUnassignedInboxCard(item)` hook, leaving a presentational component for layout.
  2. Extract `PromotedInboxMissionCard`'s equivalent state/mutations into
     `usePromotedInboxCard(mission)`.
  3. Keep `InboxCardShell` as the shared presentational wrapper (it already is one).
- **Sequenced steps**:
  1. (M, precondition) Add one rendering test per variant (`InboxMissionCard.test.tsx`) covering
     the current save/run/delete happy paths, since neither variant has coverage today and the
     playbook's precondition rule (dimension #7) applies directly here.
  2. (M) Extract `useUnassignedInboxCard` / `usePromotedInboxCard`, moving state and mutation
     wiring out of the two components without changing rendered output.
  3. (S) Split the file into `InboxMissionCard.tsx` (barrel), `UnassignedInboxMissionCard.tsx`,
     `PromotedInboxMissionCard.tsx`, matching the `MissionCard*` file-per-component convention.
- **Contract impact**: None.
- **Risk**: Medium until step 1 lands — this is the one finding in this report where the
  "add tests first" precondition is load-bearing rather than a nice-to-have, because the
  save/run/delete mutation wiring is exactly what a slip during extraction would silently change.

### F6. `webhooks.ts` invalidates with a hand-written literal key instead of the `keys` factory

- **Value/Effort**: Low / S
- **Dimension**: Types and contracts / query-key hygiene (area playbook's "queries.ts
  decomposition" check, dimension #5 adjacent)
- **Evidence**: `webapp/web/lib/queries/webhooks.ts:28,37,45,53` all call
  `qc.invalidateQueries({ queryKey: ['webhooks'] })` as a bare literal, even though
  `webapp/web/lib/query-keys.ts:14` already defines `keys.webhookSubscriptions(workspaceId)` as
  `['webhooks', workspaceId]`. `webapp/web/lib/realtime-invalidation.ts:217-218` uses the same
  `['webhooks']` literal for the realtime path, so the two are currently consistent — but only
  because both were hand-written to match, which is the precise hazard the area playbook calls
  out under "Invalidation coupling."
- **Problem**: Not a live bug (TanStack Query's default prefix-match invalidation means
  `['webhooks']` does invalidate `['webhooks', workspaceId]`), but it is a literal repeated in two
  unrelated files (mutation-side and realtime-side) instead of being named once.
- **Proposed change**: Add `keys.webhooks` (or reuse `keys.webhookSubscriptions` with the
  workspace id omitted via a documented "prefix" convention already implicit in the factory) and
  point both `webhooks.ts` and `realtime-invalidation.ts` at it.
- **Sequenced steps**:
  1. (S) Add a `keys.webhooksPrefix` entry (`['webhooks'] as const`) to `query-keys.ts`.
  2. (S) Swap the 4 sites in `webhooks.ts` and the 1 site in `realtime-invalidation.ts` to use it.
- **Contract impact**: None.
- **Risk**: Very low — same literal, now named once.

## Explicitly not recommended

- **`MissionBranchControl.tsx` (856 lines) full restructure — Low/L, not recommended.** It is the
  single largest in-scope file, but it already delegates its decision logic to
  `useBranchActions`/`useBranchPanelView` hooks and its rendering to named sub-components
  (`BranchIdentity`, `BranchCopyMenu`, `MissionBranchSetupForm`) — it is long because it has many
  branch-status conditional-render paths, not because it is unfactored. A further split would
  mean threading many of the same status flags through more file boundaries for little
  readability gain. Revisit only if it grows past ~1000 lines or gains new state, not on size
  alone.
- **`MentionableTextarea.tsx` (775 lines) split — Low/L, not recommended.** Mention-parsing logic
  is already extracted into `lib/helpers/file-mentions.ts` and `lib/useRepositoryMentionOptions.ts`;
  what remains is one cohesive keyboard-interaction state machine with no test coverage. Splitting
  an untested keyboard-handling component is exactly the "L effort, no incremental path without
  tests first" case the review should decline rather than force — add a rendering/interaction test
  first if this file is touched for a feature reason, but don't restructure it as a standalone
  refactor.
- **Extracting a standalone `packages/local-target-contract` package (F1's larger alternative) —
  not recommended now.** It would properly formalize the three-party type contract F1 documents,
  but it is an XL change (new package, publishing setup, contract version bump for a "stable
  interface" CONTRACT.md would then need to name explicitly) for a problem the type-only facade in
  F1 already resolves at S/M effort. Reconsider only if `packages/core/service/local-target/`
  itself is being restructured for other reasons (i.e., during core's own rotation review).
