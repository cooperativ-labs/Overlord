## Summary

The webapp's two hard architectural rules hold: no raw `fetch()` bypasses `lib/api*.ts` (a
repo-wide grep found only unrelated `.refetch()` matches), and no component locally
re-declares a contract DTO shape or status/phase union — the contract is the single source
of type truth here, which is the cleanest finding of this review. The area's real problems
are narrower and more consequential than its file sizes suggest. First, `webapp/AGENTS.md`
and `webapp/README.md` — both edited within the last three weeks — describe a `webapp/server/`
Express REST implementation that no longer exists; the REST API Layer moved to `backend/`
(confirmed against `CONTRACT.md`'s Component Registry) with no equivalent `backend/AGENTS.md`
left behind, so the only documented "how to add a REST endpoint" procedure in the repo points
future agents at a directory that will 404. Second, the query-key factory that
`realtime-invalidation.ts` depends on for cache-correctness lives inside `queries.ts` itself,
and because `queries.ts` imports from `local-target-branch.ts`, that module cannot import the
factory back without a cycle — so it duplicates a query key as a literal instead, silently
depending on `queries.ts` never changing that key's shape. Third, `window.overlord` desktop
bridge detection — the exact leak the playbook calls out as the mechanism by which
browser/Electron behavior diverges — is inlined in nine components instead of confined to
`lib/desktop-chrome.ts`. The highest-value single fix is extracting the query-key factory
(F1): it is contained, low-risk, and is also the prerequisite the playbook specifies before
any `queries.ts` split, which is otherwise unsafe today — the file has 152 hooks, 12 commits
in the last 60 days, and zero direct test coverage.

## Findings

### F1. Query-key factory is trapped inside `queries.ts`, forcing literal keys downstream
- **Value / Effort**: High / S
- **Dimension**: Layering and boundary leaks / Abstraction fit
- **Evidence**: `webapp/web/lib/queries.ts:105-172` (the `keys` factory), `webapp/web/lib/local-target-branch.ts:1-26` (imports nothing from `queries.ts`) and `:374` (`invalidateQueries({ queryKey: ['mission', mission.id] })` — a hand-written literal matching `keys.mission(id)` at `queries.ts:142` exactly by convention, not by import), `webapp/web/lib/queries.ts:80-89` (`queries.ts` imports `local-target-branch.ts`, which is why the reverse import would cycle)
- **Problem**: `realtime-invalidation.ts` and the mutations in `queries.ts` invalidate the cache by matching key tuples built from the `keys` factory, and the playbook's own guidance is explicit that keys must "stop being written as literals at both the producer and the invalidator." `queries.ts` imports `local-target-branch.ts` for local-target branch helpers, so `local-target-branch.ts` cannot import `keys` back without a circular dependency — it is forced into a hand-written `['mission', mission.id]` literal that happens to match `keys.mission(id)`'s current shape with no compiler or test enforcing that match. If `keys.mission` ever changes shape (e.g. gains a third segment), this call site silently stops invalidating and a branch-observation write goes unreflected in the UI with no error.
- **Proposed change**: Extract the `keys` object (`queries.ts:105-172`) verbatim into a new dependency-free module, e.g. `webapp/web/lib/query-keys.ts`. `queries.ts`, `realtime-invalidation.ts`, and `local-target-branch.ts` all import `keys` from there instead. This also removes the only structural obstacle to splitting `queries.ts` itself (F3).
- **Sequenced steps**:
  1. Create `webapp/web/lib/query-keys.ts` containing the `keys` export, moved as-is from `queries.ts:105-172`.
  2. Update `queries.ts` to `import { keys } from './query-keys.ts'` and re-export `keys` for existing external importers (grep `from '.*lib/queries'` importing `{ keys }` first to confirm the re-export is needed).
  3. Update `realtime-invalidation.ts:3` to import from `./query-keys.ts`.
  4. Update `local-target-branch.ts:374` to import `keys` from `./query-keys.ts` and replace the literal with `keys.mission(mission.id)`.
  5. Sweep the other four literal-key call sites found in this review (`AccountPage.tsx:117`, `local-target-client.ts:62,75`, `useRepositoryMentionOptions.ts:56`, `ProjectRepositoryContext.tsx:70`) — only fold these into `query-keys.ts` if they are genuinely shared/invalidation-relevant; module-local ephemeral keys (e.g. `meta-local-target-capability`) can stay literal, note that explicitly rather than over-centralizing.
- **Contract impact**: None — internal module boundary only, no REST/DTO/CLI surface touched.
- **Risk**: Low. `realtime-invalidation.test.ts` already asserts key shapes end-to-end and will catch a broken import or a missed rename immediately.

### F3. `queries.ts` is a 2,077-line, 152-hook module with no direct test coverage and above-average churn
- **Value / Effort**: High / L
- **Dimension**: Module size and cohesion / Test structure
- **Evidence**: `webapp/web/lib/queries.ts` (2,077 lines, `grep -c "useQuery(\|useMutation("` → 152); no `queries.test.ts` or equivalent exists anywhere under `webapp/web`; `git log --since="60 days ago" -- webapp/web/lib/queries.ts` → 12 commits (4× `ResourcesPage.tsx`'s 3 in the same window)
- **Problem**: Every query and mutation hook in the SPA lives in one file, spanning at least ten resource families (missions, projects, workspaces, webhooks, everhour, github, notifications, tokens, inbox, execution targets). It is the single highest-churn file in the area and the single largest, and none of that surface has direct unit tests — coverage that exists (`realtime-invalidation.test.ts`, `query-invalidation.ts`'s callers) tests the invalidation predicates, not the hooks themselves. Splitting a file this size and this central without tests first risks a silent behavior change in a mutation's `onSuccess`/`onSettled` cache handling that nothing catches.
- **Proposed change**: Split along resource families following the existing `keys` factory groupings (once F1 lands): `queries/missions.ts`, `queries/projects.ts`, `queries/workspaces.ts`, `queries/webhooks.ts`, `queries/everhour.ts`, `queries/github.ts`, etc., each re-exported from `queries.ts` (or from a barrel `queries/index.ts`) so existing `import { useX } from './queries'` call sites are unaffected in this pass.
- **Sequenced steps**:
  1. Land F1 (query-key factory extraction) first — it is an independent prerequisite, not part of this finding's effort estimate.
  2. Add characterization tests for the mutations with the most complex `onMutate`/`onSettled` cache logic first (the branch-action and mission-move optimistic updates around `queries.ts:1540-1732` are the highest-risk candidates — they do manual `cancelQueries`/optimistic-write/`invalidateQueries` sequencing).
  3. Extract one resource family at a time, smallest first (e.g. `everhour`, `github` — already visually grouped at the end of the file) to validate the split mechanics before moving the larger `missions`/`projects` groups.
  4. Re-run `realtime-invalidation.test.ts` after each extraction to confirm no key-shape drift.
- **Contract impact**: None — internal module structure only.
- **Risk**: Medium. The mutations' optimistic-update ordering is exactly the kind of thing a naive split can silently reorder; step 2 (tests before extraction) is not optional for this finding, per the "Test structure" dimension's precondition rule.

### F4. Desktop/Electron bridge detection is inlined in nine components instead of confined to `lib/desktop-chrome.ts`
- **Value / Effort**: High / M
- **Dimension**: Duplication with divergence / Layering (desktop parity)
- **Evidence**: `webapp/web/components/auth/AuthScreen.tsx:95,151,154`, `auth/BackendLoginPanel.tsx:34`, `runner/RunnerStatusModal.tsx:74`, `notifications/NotificationRenderer.tsx:61`, `settings/DesktopUpdatesPage.tsx:27`, `settings/SettingsModal.tsx:87`, `settings/McpPage.tsx:60,195`, `settings/BackendPage.tsx:61`, `settings/HotkeysPage.tsx:33,48` — each repeats a variant of `typeof window === 'undefined' ? undefined : window.overlord` or `window.overlord?.isDesktop === true` inline, versus the existing `webapp/web/lib/desktop-chrome.ts:19` (`getDesktopChrome()`), which none of these nine call
- **Problem**: This is precisely the leak the playbook's "Desktop parity" check warns about: "host detection inlined in components rather than confined to those modules ... is what makes browser-vs-desktop behavior diverge." Nine independent copies of the same `window.overlord` presence check mean a future change to how the bridge is detected (e.g. adding a readiness flag) has to be found and updated in nine places, and any one of them drifting produces a component that behaves correctly in the browser but wrongly in Electron (or vice versa) with no single place to fix it.
- **Proposed change**: Add a `useDesktopBridge()` hook (or extend `getDesktopChrome()`) to `lib/desktop-chrome.ts` returning the typed bridge or `undefined`/`isDesktop` boolean, and replace each inline check with it.
- **Sequenced steps**:
  1. Add `useDesktopBridge()` / `isDesktopHost()` to `desktop-chrome.ts`, matching the existing `getDesktopChrome()` return shape.
  2. Replace the nine call sites one component at a time (each is an independently landable, single-file change).
  3. Grep for `window.overlord` after the sweep to confirm no remaining inline checks outside `desktop-chrome.ts` and the preload bridge's own type declaration.
- **Contract impact**: None — `window.overlord` is a Desktop Shell preload surface (`CONTRACT.md:679`, "feature-detected `window.overlord` preload bridge"), not a REST/contract interface; this only touches how the SPA reads it.
- **Risk**: Low; each replacement is behavior-preserving by construction if the new helper returns the identical value the inline check computed. Exercise `AuthScreen.tsx` and `SettingsModal.tsx` manually in the packaged Electron shell after the sweep, per the playbook's "exercise the change in the running app" rule for desktop-parity modules.

### F5. `navigator.clipboard.writeText` duplicated raw in seven components despite an existing `useCopyToClipboard` hook
- **Value / Effort**: Medium / S
- **Dimension**: Duplication with divergence
- **Evidence**: `webapp/web/lib/hooks/use-copy-to-clipboard.ts` (the shared hook — copy + timed `copied` reset); raw duplicate call sites at `components/app-banners/AppBannerStack.tsx:85`, `components/MissionBranchControl.tsx:116,154`, `components/projects/project-settings/GeneralPage.tsx:105`, `components/projects/project-settings/LaunchVariableLibrary.tsx:42`, `components/objectives/AgentLaunchButton.tsx:185`, `components/settings/UserTokensPage.tsx:308`, `components/settings/WebhooksPage.tsx:672`
- **Problem**: Seven components each hand-roll their own `copied` state and `navigator.clipboard.writeText` call instead of using the hook built for exactly this. None have diverged in a way that's currently broken, but each is an independent place a future fix (e.g. a clipboard-permission fallback) has to be applied by hand.
- **Proposed change**: Replace each inline copy implementation with `useCopyToClipboard()`.
- **Sequenced steps**: One component per commit; each is independently landable and low-risk (visual "copied" state only).
- **Contract impact**: None.
- **Risk**: Low. Verify the `resetMs` default (2000ms) matches or intentionally differs from each site's current timeout before replacing — `MissionBranchControl.tsx`'s two call sites should be checked individually since the file defines its own local `copied` state twice (`CopyIconButton` and `BranchCopyMenu`).
