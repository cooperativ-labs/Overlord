# Security Audit - 2026-11-21

## Executive Summary

- **What was reviewed.** Codex app-server mode: Overlord runs a private `codex app-server` for an
  Overlord-launched Codex objective, drives it from a local supervisor, and turns Codex's command
  and file-change approvals into Overlord cards. The review covered the server's listening surface
  and authentication, who can connect, secret handling, who can answer approvals, folder trust and
  process cleanup. It also covered the change made during the review that lets people answer these
  approvals from the Overlord web app.
- **Overall posture: acceptable for opt-in use.** No Critical or High findings. The server listens
  only on an owner-only Unix socket, no credential is passed on a command line or into the agent's
  environment, and the channel credential the supervisor holds cannot answer any request.
- **Most important findings.**
  - Medium, accepted: commands the agent runs execute as the person's own OS user, so with network
    access they could read the person's `ovld` login and answer the session's own cards. This is
    the same-user boundary every local coding agent has. It is documented, not fixed.
  - Medium, fixed: a supervisor killed with SIGKILL left its Codex server running the turn with no
    supervision.
  - Medium, fixed: a second approval Codex asks about the same item (for example, to rerun a
    command outside the sandbox) could inherit an earlier "allow". This was latent until approvals
    became answerable from Overlord.
  - By design: only the member who launched a session can answer its approvals in Overlord. The
    route permission alone (`session:attach`) is held by every default role.
- **Customer action.** None required. App-server mode is off unless chosen. People who turn it on
  should use it only on repositories they would trust in Codex (see "Folder trust").

## Product Surface Reviews

### Local listening surface and connection authentication

#### Finding: Remote-control status was checked too narrowly, and only after work started
- Severity: Low (fixed)
- Why it matters: Codex remote control lets a remote party drive the server. The supervisor
  stopped only on the statuses `connecting` and `connected`, not `errored`. It also bound the
  thread and sent the first prompt before acting on a status report.
- Evidence: `supervisor.ts` remote-control handler (previously checked
  `status === 'connecting' || status === 'connected'`). The status enum at 0.170 is
  `disabled | connecting | connected | errored`.
- Recommendation (done): treat any status other than `disabled` as enabled. Wait briefly after
  `initialize` for the status report Codex sends there, and start no thread unless the status
  is `disabled`. Test: "remote control that is not disabled at connect starts no thread".

#### Finding: The real socket's directory was not checked before connecting
- Severity: Low (fixed)
- Why it matters: Codex puts the real socket in `/tmp/codex-daemon-<uid>/`. Another local user
  could create that name first in a shared `/tmp` and stand in for the server.
- Evidence: `transport.ts` `connectWebSocket` connected to `realpath(socket)` without checking
  who owns it.
- Recommendation (done): before connecting, require the socket and its directory to belong to the
  current user, and the directory to be neither group- nor world-writable
  (`assertOwnedSocketTarget`). Verified live against a Codex 0.171.0 socket.

Reviewed without finding:
- The listening surface is `unix://` only, in `~/.ovld/cx/`. That directory is created `0700`,
  and the supervisor refuses one that is a symlink, is group- or world-accessible, or is owned by
  someone else (`server.ts` `prepareSocketDirectory`).
- There is no TCP listener.
- Overlord never uses the person's shared Codex daemon socket.

### Who can connect, and secret handling

#### Finding: Commands the agent runs can reach the person's Overlord credentials
- Severity: Medium (accepted, documented)
- Why it matters: agent commands run as the person's OS user, and Codex's `workspace-write`
  sandbox allows reading the whole filesystem. With network access, which is granted per command
  or by a looser sandbox, a command could:
  - read `<ovld home>/auth.json` or the channel credential cache, then answer the session's
    question cards or (as the launching member) its approvals through Overlord;
  - connect to the session's own socket and answer approvals directly.
- Evidence: `server.ts` `buildServerEnv`, which correctly drops every Overlord credential; the
  credential files in `cli/src/auth-credentials.ts` and `cli/src/agent-session/channel.ts`; the
  Codex sandbox read scope.
- Recommendation: this is the same-user boundary of any local agent, and it is accepted. It is
  documented in the adapter README, the public docs, and the `same-user-agent-reaches-credentials`
  hazard. Where Codex supports it, a thread sandbox that denies reading `~/.ovld` is the stronger
  control. Tagging resolutions made from inside a session would make such answers visible.

#### Finding: The person's user token stayed in the supervisor's environment
- Severity: Low (fixed)
- Why it matters: a long-lived process's environment is readable by same-user processes
  (`ps eww`), and the supervisor never uses a user token.
- Evidence: `launch.ts` `supervisorEnv` removed only the channel token.
- Recommendation (done): also drop `OVERLORD_USER_TOKEN`, `OVLD_USER_TOKEN` and `USER_TOKEN`. Test
  updated.

Reviewed without finding:
- No token appears in argv. Supervisor and attach arguments are paths and ids, and the channel
  token travels only in an Authorization header.
- The state file holds paths, pids and the thread id, `0600` in a `0700` directory.
- The channel credential cache is `0600` in a `0700` directory, written by temp file and rename.
- The server environment is an allowlist without Overlord credentials or objective scope, and
  Codex plugin hooks are silenced inside it.
- Codex account email and ids from `account/read` never leave the machine.

### Approval answering and authorization

#### Finding: A re-asked approval could inherit an earlier answer
- Severity: Medium (fixed)
- Why it matters: Codex can ask twice about one item, for example to rerun a sandbox-blocked
  command outside the sandbox, with the same item id. Cards are deduplicated by native request
  id, so the second request got the first, already resolved card, and the supervisor applied its
  "allow" at once to a broader action. This was latent while nobody could answer approvals from
  Overlord, and became live with this change.
- Evidence: `decisions.ts` `routeToPerson` (immediate application of a resolved existing card) and
  `requests.ts` `createRequest` dedupe on `(channel, native_request_id)`.
- Recommendation (done): a request for an item whose earlier approval already settled gets its own
  occurrence id (`<item>#2`), so it opens a new card. A replay of a still-open card keeps its id.
  Unit test plus the `reasked-approval-occurrence` fixture.

#### Finding: Any workspace member could have approved commands on a colleague's machine
- Severity: Medium (prevented by design in this change)
- Why it matters: answering a command or patch approval runs code on the launching member's
  machine. The resolve route's permission, `session:attach`, is held by every default role
  (`MEMBER` grants `session:*`).
- Evidence: `overlord.rbac.toml`; `POST /api/agent-requests/{id}/resolve`.
- Recommendation (done, ADR 0094): a `permission` request on a control-plane channel can be
  answered only by the member who created the channel. Anyone else sees it read-only
  (`not_session_owner`) and gets 403. An answer must be exactly one of the card's own options, so
  no client can add a standing grant. A channel credential can never resolve a request. Tests:
  `backend/control-plane-request-answer.test.ts`.

Reviewed without finding:
- Every thread is started and resumed with `approvalsReviewer: "user"`. Live on 0.171.0, with
  `approvals_reviewer = "auto_review"` in the person's Codex config and the TUI attached through
  `resume`, approvals still reached Overlord.
- The supervisor sends only `accept`, `decline` or `cancel`, never `acceptForSession` or policy
  amendments.
- Policy may auto-answer only plain `command` approvals, and production configures no policy.
- Unknown server requests are refused.
- Question and choice cards stay answerable by any workspace member with `session:attach`, as for
  every other agent (Informational).

### Folder trust

#### Finding: Trust cleanup could replace a symlinked config, and had a wider race window
- Severity: Low (fixed in part)
- Why it matters: the entry `thread/start` adds is removed by rewriting `~/.codex/config.toml`.
  Renaming over a symlinked config (common with dotfile managers) replaced the link with a plain
  file. A concurrent write between the check and the rename could be lost.
- Evidence: `trust.ts` `removeImplicitTrustEntry`.
- Recommendation (done): edit the symlink's target, and move the concurrent-change check to just
  before the rename. A small stat-to-rename window remains and is accepted. The removal still
  touches only a table that holds nothing but `trust_level = "trusted"`. Test added.

#### Finding: The working directory is trusted while a session runs
- Severity: Informational (documented)
- Why it matters: while the session runs, the checkout's own Codex config, hooks and MCP servers
  load and can run code, as if the person had chosen "Trust" in Codex.
- Evidence: plan §3.8; live: the entry appears during a session and is gone afterwards. The
  person's `config.toml` was byte-identical before and after both live app-server runs.
- Recommendation: documented as the trust caveat in the adapter README and public docs. Use the
  mode only on repositories you would trust in Codex.

### Process cleanup

#### Finding: A supervisor killed outright left the server running its turn
- Severity: Medium (fixed)
- Why it matters: the server runs detached in its own process group. After a SIGKILL of the
  supervisor it kept running the turn with nobody answering approvals or posting events, until
  the next supervisor start or `ovld doctor` reaped it.
- Evidence: `server.ts` `spawnPrivateAppServer`, which uses `detached: true`.
- Recommendation (done): start a detached `sh` watchdog with the server. Its arguments are two
  pids and its environment is a fixed `PATH`. It ends the server's process group within about a
  second of the supervisor's pid disappearing. Real-process test plus the `supervisor-watchdog`
  fixture.

#### Finding: Unbounded memory for file-change diffs
- Severity: Low (fixed in part)
- Why it matters: the supervisor kept every file change's diff, including full file contents,
  until that change asked for approval, which auto-applied edits never do.
- Evidence: `supervisor.ts` `recordDiffs`.
- Recommendation (done): drop a change's diffs when it completes. The WebSocket fragment buffer is
  still uncapped, which is accepted because the peer is the person's own Codex.

#### Finding: The orphan reaper's pid check matches any Codex app server
- Severity: Low (accepted)
- Why it matters: a reused pid that happens to be another Codex app server of the same user could
  be stopped.
- Evidence: `state.ts` `reapOrphanedSessions` checks that the command line contains
  `codex … app-server`.
- Recommendation: accepted. The watchdog now covers the common case. Matching the socket path in
  the command line would narrow it further.

Live cleanup check: after each app-server run, no supervisor, server or watchdog remained,
`~/.ovld/cx/` was empty, and the channel ended `codex_app_server_objective_ended`.

## Positive Controls

- Owner-only Unix socket with directory checks, no TCP listener, and remote control must be off.
- An allowlisted server environment and no credential in argv. The channel credential is staged
  `0600` and is hashed server-side with a short lease.
- The channel credential cannot resolve requests, and adapter routes check the channel of every
  request they touch.
- Approvals are owner-only in Overlord, limited to the card's options, and never a standing grant.
- `approvalsReviewer: "user"` is forced, and was verified live with an `auto_review` user config.
- Card text is bounded and redacted: patch cards show paths and line counts, never diff text, and
  protocol session keys are redacted in event summaries (seen live).
- Version gate, pinned method list, and fallback to the hooks launch on any failure.

## Recommended Next Steps

1. Ship the Overlord-side follow-up controls (send an instruction, steer, interrupt) through the
   session-input route for control-plane channels, with the same owner rule.
2. Let the mobile app answer `control_plane` approval cards.
3. Where Codex supports it, deny reading `~/.ovld` in the thread sandbox.
4. Re-record the app-server fixtures with `scripts/codex-app-server-record.mts` on each Codex
   upgrade before raising the verified version.
